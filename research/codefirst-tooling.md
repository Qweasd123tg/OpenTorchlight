# Инструменты строгого переноса функций

Статус: `port-native tooling`. Действующая цель и приёмка:
[code-first.md](code-first.md). Это локальные скрипты без модели, ключей,
сетевого сервиса или запуска оригинальной игры. Они экономят подготовку,
навигацию и повторные проверки; смысл неизвестной ветви не угадывают.

## Единый маршрут

После принятия контракта доступен полный локальный путь `check.py --recover`:
source extraction/check → production C++ generation → real consumer build →
original/resource/regression/registry gates по всей зарегистрированной CPU
цепочке. Принятые UI/RNG и [gameplay рецепты](recovery-gameplay.md) уже входят
в обычную CMake сборку; [точный контракт и команда](recovery-automation.md).
Неизвестные типы/вызовы не получают шаблон по сходству. Completion остаётся
отдельным whole-function review; generated outputs его не повышают.

1. `tools/work_frontier.py` — текущий UI scope, уже существующие реализации,
   открытое полное закрытие, связанные семейства.
2. `tools/prepare_family_packet.py` — ограниченный пакет семейства из pinned
   ELF; одна загрузка индексов, каждое тело декодируется один раз, отдельные member deltas.
   Карточки находят локальные vendor-source spelling candidates собственных
   символов и прямых callees, включая external names без сигнатур в старом графе.
   Source corpus читается один раз на batch; namespace библиотеки разделяет
   одинаковые Class::method. Хеши исходников и доступных version manifests
   входят в packet fingerprint. Spelling hit может быть вызовом или другой
   перегрузкой; source/binary contract автоматически не аттестуется.
3. `tools/prepare_integration_packet.py` — повторное использование уже
   написанного общего кода, включая функции с частичным `wired=true`.
4. Содержательное ревью и перенос всего контракта — работа по пакету.
   Подключение устанавливается по callers, полям и производственным consumers.
   Сравнение с ASM/библиотекой фиксирует адреса и границу вывода; стенд или
   трасса отвечают на конкретный оставшийся вопрос.
5. `tools/audit_registry_sync.py` и узкие проверки — формат, согласованность и
   актуальность явно оформленной приёмки. Не доказательство всей семантики.

`function_package.py` остаётся нижним уровнем для 1–64 точных адресов.
Не нужен второй реестр, отдельный сервис очередей или новый LLM-оркестратор.
Ghidra headless, GNU binutils и CTest/Ninja остаются используемыми механизмами;
установка нового набора инструментов для этого цикла не требуется.

Для одного запуска подготовки текущей цепочки:

```sh
python3 tools/prepare_family_packet.py createMenus \
  --elf /path/to/game/Torchlight.bin.x86_64 \
  --class-regex '^(CMainMenu|CDropdownMenu)$' \
  --build-dir build-cegui --check --out /tmp/menu-create-packet
```

`--build-dir` читает существующую CTest discovery и Ninja graph без изменения
CMake cache. `test-plan.json` содержит команды сборки/CTest для test files,
уже записанных в карточках, и fixture closure через общий `check_selection`.
Файлы без зарегистрированного соответствия и исключённые render/desktop/UI
сценарии перечисляются отдельно. Без `--check` план ничего не исполняет.
С `--check` этот же запуск собирает выбранные цели и выполняет ограниченные
проверки, сохраняя `checks.json`, `checks.log` и JUnit `checks.xml`.
Используются общие правила `check.py`/`automation_state.py`: skip не PASS,
имена результатов должны совпасть с выбором, изменение tracked/nonignored
входов во время проверки делает результат FAILED. Пустой выбор — NOT RUN.
Текущий CMake cache не перенастраивается; `--jobs` по умолчанию 2.
Этот прогон не заменяет общую проверку изменений.
Если `--callsites` не задан, существующий build-каталог получает автоматически
создаваемый/проверяемый `research/original-callsites.tsv`. `--reuse` экспортёра
принимает кеш только при совпадении ELF SHA-256, кода экспортёра/ELF-helper,
версии objdump, TSV hash и ожидаемого header. Cache hit не вызывает nm/full
objdump и не переписывает артефакты; отсутствие, старый формат или повреждение
приводят к экспорту. Явно заданный отсутствующий индекс остаётся ошибкой.
Оригинал проверяется по содержимому, не mtime. Если build-dir не задан,
сохраняется прежний маршрут с явным missing-index warning.

Для экономии контекста сначала читать `summary.json`: он теперь содержит
счётчики открытых вопросов, local-source hit/missing hints представителей и
выбранные contract tests. Затем открывать только нужные карточки и member
deltas. Полные исходные данные остаются в пакете; механическая подготовка,
кеширование, выбор проверок и их исполнение не вызывают модели/сеть.
Проверенный пример и актуальная граница сортировки:
[menu-preparation-automation.md](menu-preparation-automation.md).

Проверка готовых механизмов: [BSim/FID + static refs pilot](library-match-pilot.md).
В 20 запросах BSim дал 7 однозначных ожидаемых top-кандидатов и 3 ties;
результат используется для навигации, статусы переноса остаются отдельными.
Направление binary → IR → C и готовые rev.ng/cozy/angr описаны в
[обзоре детерминированных инструментов](deterministic-reconstruction-tools.md).

## Область и очередь

Активный пакет — MAIN/ENTRY MENU: `CMainMenu::createMenus`, `update`,
CDropdownMenu и путь от свойств окон до кадра. Остаток и производственные
потребители записаны в [mainmenu-controller-painter.md](mainmenu-controller-painter.md).

```sh
python3 tools/work_frontier.py --top 12 \
  --out build-verification/codefirst-frontier.md \
  --json build-verification/codefirst-frontier.json
```

По умолчанию выбираются префиксы классов и explicit entries из
`research/ui-contour.json`, а не подсистема `frontend`: UI-методы в карте
могут относиться к `items`, `interaction` или `other`.
`--scope all` явно расширяет отчёт, но не даёт разрешения менять область реализации.
Классификация общей очереди пересчитывается, а не берётся из старого JSON.

Остаток внутри функции не исчезает из отчёта из-за четырёх `true`.
`unassessed` означает отсутствие отдельного whole-function review, а не
отсутствие реализации. Число таких адресов не равно числу задач или срокам.
Весь raw UI contour включает технические методы; они не превращаются в
самостоятельные ручные задачи только из-за попадания в scope.

## Пакет семейства и ограничение контекста

```sh
python3 tools/prepare_family_packet.py handle_CloseButton \
  --elf /path/to/game/Torchlight.bin.x86_64 \
  --callsites build-verification/research/original-callsites.tsv \
  --out build-verification/codefirst/close-pass-1
```

Индекс callsites сначала создаётся командой из
[scripted-automation.md](scripted-automation.md). Флаг необязателен: отсутствие
индекса остаётся явным предупреждением. Но явно запрошенный отсутствующий
индекс отклоняется, а его sidecar проверяется на ELF/TSV SHA-256.

Выход должен быть новым или пустым каталогом. Повторный проход писать в новый
каталог: старые и новые файлы не смешиваются. Генераторы не пишут поверх
исходников, реестров или оригинального ELF. По умолчанию максимум 64 члена и
64 представителя; `--max-members` / `--max-representatives` позволяют уменьшить
бюджет. При превышении нет молчаливого усечения: требуется сузить `--class-regex`.
Неудачный проход может оставить диагностические артефакты, но не готовый `ENTRY.md`.

Содержимое:

- `ENTRY.md` — короткий вход, ссылки и последовательность проверки;
- `FAMILY.md` — все члены и их отдельные стадии/полное закрытие;
- `members.json` — границы, поля карточек, входящие/исходящие связи и unresolved
  indirect sites **всех** членов, не только представителей;
- `representatives/*.md` и `functions.json` — подробные пакеты представителей;
- `members/*.asm` — исходные тела всех членов, снятые один раз;
- `member-deltas/*.diff` — различия конкретных инструкций с константами,
  смещениями и целями вызовов; условия/CFG/контекст всё равно проверяются;
- `clusters.json`, `ASM_CLUSTERS.md`, `summary.json` — способ группировки и идентичность входов.

Не отправлять весь пакет целиком модели и не перечитывать все корпуса для
каждого метода. Начинать с `ENTRY.md`, открывать нужную карточку и её зависимости.
Группировка exact normalized shape — подсказка. Совпадающий шаблон без
проверенных member deltas не разрешает общий исполнитель.

Дорогие попарные approximate comparisons включаются только через `--near 0.9`.
Отказ от них по умолчанию ничего не закрывает и не теряет исходные тела.
Если exact-группировка дала 22 разных представителя, это нормальный результат,
а не повод ослабить критерий и объявить методы одинаковыми.

Для существующей реализации:

```sh
python3 tools/prepare_integration_packet.py --group src/inventory_menu.cpp \
  --out build-verification/codefirst/inventory-integration-1
```

Лексический аудит потребителей — только по конкретной необходимости:

```sh
python3 tools/audit_sinks.py --root . --symbol panel_profile
```

Он читает исходники один раз; header declarations не считаются production
потребителями. Выдаёт кандидатов с нулём/одним src-файлом, **не wired/unwired**.
Комментарии, перегрузки, вызовы внутри того же файла и косвенные вызовы требуют
проверки. Не запускать весь аудит механически перед каждой функцией.

## Полное закрытие отдельно от legacy-стадий

В `research/function-transfer.json` у функции может быть отдельное поле:

```json
"completion": {
  "status": "partial",
  "open_items": ["OPEN animation and viewport renderer consumer remain open"]
}
```

При отсутствии поля результат `unassessed`; прежние стадии не переписываются.
Для `status: full` обязательны:

- все четыре стадии строго `true` и явно пустой `open_items`;
- `review` с непустыми свидетельствами по каждому ключу:
  `branches`, `state`, `calls_and_effects`, `library_contracts`, `family_deltas`,
  `integration`, `original_comparison`;
- если аспект неприменим, содержательное объяснение, а не пропуск поля;
- `inputs`: отображение относительного пути файла в его SHA-256, включая
  реализацию (`src/` или `include/`) и тесты (`tests/`). Ревьюер включает все
  значимые локальные зависимости/evidence; оригинальный ELF уже закреплён
  верхним полем реестра. Не включать саму карточку в её собственный хеш.

Валидатор возвращает `reviewed_full` только для структурно полной и актуальной
**явной заявки ревьюера**. Это не автоматическая аттестация поведения:
скрипт не знает, забыта ли ветвь, правильно ли прочитана инструкция и исчерпывает
ли `inputs` зависимости. `stale` означает изменённый/отсутствующий вход;
`invalid` — некорректную заявку. Эти два состояния отклоняет registry gate.
Частичный перенос обязан оставлять непустой перечень открытого.

Для старых функций не выставлялось автоматически ни одного `full`.
У convertToScreenScale, inventory setOpen/createMenus явно записан `partial`.
Остальные legacy-карточки не обнулялись и требуют отдельной приёмки.

## Что не является готовностью этого проекта

`tools/readiness.py` и `research/capabilities.json` оставлены как вторичный
отчёт smoke/compatibility имеющегося игрового среза. Даже зелёный полный
capability manifest не выставляет готовность восстановления: `release_ready`
остаётся false, `release_readiness` — NOT ASSESSED. Отдельный
`capability_scope_ready` относится исключительно к перечисленному срезу.
Оценки 30/38% и исторические large-N планы не назначают следующую работу.

Обычный транш завершается сборкой затронутого кода и проверками известного
контракта: `tools/check.py --core --test ui_layout_property`.
Повторяемый `--test NAME` выбирает точные проверки и необходимые fixtures.
Результат записывается как частичная проверка выбранной границы.
`--since-report` / `--changed` выбирают проверки по изменениям;
неизвестные зависимости расширяют выбор внутри запрошенных групп.
UI-клики, кадры и сквозные сценарии выполняются отдельной явно запрошенной
задачей через `--render`, `--desktop` или `--all`.

## Локальный замер подготовки, 2026-09-19

На установленном pinned ELF и готовом CALL-индексе, без оригинального процесса:

| Подготовка | Индекс загружен | Время |
|---|---:|---:|
| 22 setOpen-карточки, отдельный FunctionPackageBuilder на каждую (прежняя схема) | 22 | 79.628 s |
| Те же 22 адреса, один batch builder | 1 | 9.055 s |
| Новый полный setOpen-пакет с ASM и файлами | 1 | 9.88 s |

Около 8.8× для данного сбора карточек. JSON без повторённых входных манифестов:
суммарно 2 329 803 символа отдельных документов против 493 737 у batch.
Это единичный локальный замер, не стабильный benchmark, стоимость токенов или
обещание ускорить ручное исследование в 8.8 раза. Пиковая память полного пакета
около 575 MiB; большой CALL-индекс остаётся заметной ценой подготовки.

UI handle_CloseButton: 20 методов → 11 exact structural representatives,
полный пакет 6.90 s. Все остальные члены требуют проверки конкретных различий;
ни одна функция от кластеризации не стала перенесённой или закрытой.

## Проверки инструментария

`tests/codefirst_tools_test.py` зарегистрирован в core как `codefirst_tools`.
Проверяет UI scope, отсутствие auto-closure по четырём стадиям, обязательные
аспекты полного review, изменённые/невалидные входы, сохранение открытого
в очереди, повторное использование индекса, concrete deltas, безопасный output,
отделение declarations от потребителей и smoke от полной готовности.
