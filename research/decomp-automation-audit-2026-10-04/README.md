# Проверка дополнительной автоматизации восстановления

Дата: 2026-10-04. Проверена локальная копия на основе c775b4a с отдельной
проверкой Warper. Результаты других 15 агентов пользователя сюда не поступали.

## Вывод

Дополнительная автоматизация имеет конкретные точки приложения. Полностью
автоматическое восстановление игры, ускорение в разы и срок завершения не
доказаны. Наиболее полезный следующий эксперимент: актуальные поля и точные
сигнатуры на входе Ghidra, затем ограниченные правила контейнеров. Общую
чистку строк не следует делать заново: значительная часть уже реализована.

## Что измерено

Взяты все 23 функции из локального списка принятых с размером исходного
машинного кода не меньше 1024 байт: 51 826 байт. Преобразователь ghidra_cpp.py
сокращает их сохранённые черновики с 6769 до 3624 строк. Счётчик включает
комментарии и пустые строки; это размер текста, не семантическое покрытие.
В 16 исходных черновиках есть маркеры обслуживания строк, после преобразования
они остаются в одном. Маркеры TArrayList остаются во всех 10 исходно содержащих
их функциях, деревьев — во всех трёх.

По сохранённым черновикам крупных игровых функций (фильтр kind=function,
ctor,dtor,static; TU kind=game; size>=1024) найдено 666 функций, 2 797 634 байта.
Маркеры встречаются в следующем числе функций:

- обслуживание строк: 506;
- внутренности деревьев: 70;
- внутренности vector: 37;
- поля TArrayList: 134;
- NAN: 71;
- extraout/in_stack/unaff/return_storage: 46.

Группы пересекаются. Это текстовые индикаторы, не точное число конструкций и
не число функций, которые можно будет автоматически принять. Часть vector
показывается без именованных внутренних полей и этим поиском не обнаруживается.

Восемь черновиков дополнительно скомпилированы оригинальным GCC в копиях TU,
с сохранением уже проверенной сигнатуры и списка инициализации конструктора.
Все восемь не компилируются. Это диагностический тест совместимости текущего
преобразователя со старыми черновиками, не предел возможностей декомпилятора:
черновики местами используют устаревшие поля. Ошибки и адреса приложены.
Перегрузка CFileReader::ReadFile(const std::wstring&) выбрана явно: старый
find_definition различает функции по числу аргументов и сначала выбирает
одноаргументную ReadFile(FILE*). Это ограничение измерительного инструмента,
а не ошибка восстановленной функции.

## Подтверждённые ограничения инструментов

1. types_export.py экспортирует раскладки классов; DecompDrafts.java применяет
   поля, vtable и __thiscall, но не выполняет полный импорт проверенных
   прототипов методов из рукописных заголовков. headers.py распознаёт скрытый
   возврат только когда Ghidra уже пометила __return_storage_ptr__.
   getSkillStats (0xc93b10) — конкретный контрпример: сохранённый черновик
   считает RDI=this вместо хранилища возвращаемой std::wstring, использует
   неверный класс для RSI и оставляет in_ECX. Требуется исправлять ABI до
   повторной декомпиляции, а не только переименовывать локальные переменные.
2. CGraph::loadGraphLine (0xc78930) сохраняет m_iUnknown20/40 из старой
   раскладки, неверный тип поля и нетипизированные 0.0 в перегруженных вызовах.
   Простая замена имён без проверки типа недостаточна.
3. inline_temp_strings передаёт литерал строкой замены в Python re.sub.
   Повторная интерпретация обратных слешей портит C++-литералы. В актуальном
   преобразованном ResourceSettings (0xa60190) это проявляется как неправильные
   пути и незакрытые строковые литералы. Изолированный прототип заменяет строку
   замены на callable, возвращающий литерал без интерпретации. Пять проб:
   пути с обратными слешами, завершающий слеш, escape новой строки, кавычка,
   обычный текст. Текущий код сохраняет 2/5, прототип 5/5. Прототип не внедрён
   в основной преобразователь и не восстанавливает весь ResourceSettings.
4. Удаление refcount-блоков сейчас текстовое, без доказательства времени жизни
   объекта; новые правила должны иметь строгие условия применения. Отдельный
   синтетический пример !NAN(x) && enabled преобразуется в некорректный синтаксис
   'if enabled)'. Это регрессионный пример для tidy_expressions, не доказательство
   ошибочного поведения уже принятых игровых функций.

## Очерёдность экспериментов

- Быстрый локальный ремонт: сохранение литералов, регрессионные тесты на
  экранирование и синтаксис; сравнить результаты на сохранённых черновиках.
- Экспорт проверенных прототипов и инвалидирование черновиков при изменении
  зависимых типов. Сначала 10–20 функций, включая скрытый возврат строки,
  ссылки, перегрузки, float и методы с неиспользуемым this.
- TArrayList: распознавание полного шаблона доступа с проверкой capacity и
  fallback на элемент 0. Не заменять на обычный vector[index]. Затем проверять
  изменение списка во время callback и правила повторного чтения count.
- STL: выбирать конкретные версии и типы, проверять полную структуру операции,
  не заменять произвольную арифметику указателей по одному совпавшему имени.
- Генерацию Descriptor оценивать отдельно: направление зарезервировано под
  генераторы; законченного специализированного генератора в tools/decomp этой
  копии не найдено. Чужие зарезервированные TU не изменялись.

Успех эксперимента измерять новыми MATCH или сильными дифференциальными тестами
на отложенных функциях, временем проверки и отсутствием ложных преобразований.
Число исчезнувших строк и успешная компиляция сами по себе не являются приёмкой.
Пока не измерены доля устраняемой ручной работы и экономия времени/токенов.

## Воспроизведение

Из корня репозитория после настройки env.sh:

1. python3 research/decomp-automation-audit-2026-10-04/measure.py
2. python3 research/decomp-automation-audit-2026-10-04/compile_samples.py
3. python3 research/decomp-automation-audit-2026-10-04/literal_probe.py

Скрипты читают существующие ELF-базу и кэш черновиков. Временные результаты
пишутся только в build-decomp/automation-audit; исходники игры не меняются.
measure.py надо запускать первым: он создаёт converted-файлы для компиляции.
Исходный ELF и ресурсы не включены в этот отчёт.
