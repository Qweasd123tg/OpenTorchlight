# Порядок следующих патчей

Это техническое задание на изменения, **не набор готовых `.patch`**. Диагностические инструменты в комплекте готовы к запуску; игровое исправление в этом исследовательском проходе не выполнялось.

## Принцип приёмки

Для каждого патча нужны одновременно: исходная цепочка оригинала; воспроизведение расхождения на текущем порту; исправление этой цепочки; негативный контроль, показывающий, что возврат старой ошибки ломает сравнение. Собственный green-test без эталонного ожидания — регрессия, но не доказательство соответствия.

Ресурсы не редактировать ради прохождения теста. Неподдержанные ветви не заменять визуально похожими. Не подгонять screenshot-fit коэффициенты. Адреса привязаны к зафиксированному ELF, см. `КАРТА_ИСТОЧНИКОВ.md`.

## P0 — закрепить исходное состояние и типы проверок

**Файлы:** документация, CMake/CI проверки, отдельный минимальный воспроизводитель предупреждений сборки; игровой UI этим пакетом не менять.

Сохранить точные хеши large-14 и применённого ранее patchset. Перенести `results` этого аудита в исследовательский журнал, не выдавая их за тесты исправленной игры. Отделить категории `prototype-regression`, `resource-derived`, `original-code`, `library-derived`, `end-to-end-parity`.

Разобрать остановку Release GCC 14.2 на optional `active_pickup/merchant_entity` в `application.cpp`. Не использовать `-Wno-error` как доказательство исправления и не объявлять предупреждение доказанным UB. Сравнить минимальный reproducer с логикой проверок has_value, исправить реальную причину либо оформить компиляторную особенность отдельно.

**Приёмка:** исходная версия явно названа; команды сборки сохранены; отчёт не смешивает неисполненные тесты с исполненными. Уже исправленные Serif/DPI/UV не возвращаются в список «надо сделать».

## P1 — оригинальный масштаб layout и пересоздание при ресайзе

**Существующие файлы:** `include/torchlight/ui_layout.hpp`, `src/ui_layout.cpp`, `src/ui_hud.cpp`, только подтверждённые места загрузки экранов. В `src/frontend.cpp` не включать глобальный масштаб без исследования контроллера конкретного меню.

**Предлагаемый новый небольшой модуль:** преобразование исходных UDim, например `ui_screen_scale.hpp/.cpp`. Имя — предложение для организации кода порта, не название класса оригинала.

Использовать точный смысл `CGameUI::convertToScreenScale`: неизменные относительные коэффициенты, масштабирование четырёх offset-полей одним выбранным коэффициентом, обход детей до родителя. `false` — YRATIO, `true` — XRATIO. Преобразование одноразовое на экземпляр, не каждый кадр.

Ввести явно проверенную для каждого экрана политику загрузки. Не догадка по размеру/названию: таблица составляется из фактических вызовов оригинала. Подтверждённые false-callsite перечислены в аудите. Хранить исходный документ неизменным либо пересоздавать UI, как `CGameClient::rescaleUI`.

**Эталон:** `tools/probe_original_ui.py`; функции `0xa83ed0/0xa83ea0/0xa83e70`; исходные свойства настоящих layout. В тестируемую библиотеку экспортировать минимальный доступ к результату нового преобразователя и сравнивать его с нативной пробой, а не с копией своей реализации.

**Приёмка:** 1024×768, 1280×720, 1920×1080, 2560×1440 и небазовые нечётные размеры; обе ветви bool; вложенные окна; сохранность scale-членов; нет накопительного масштабирования. Проверка конечного clip/rounding относится к библиотечному слою и не подменяется сравнением этих восьми float. Шрифты не получают второй множитель.

## P2 — исходная фаза события мыши, без клика в игровой мир

**Файлы:** `include/torchlight/ui_hud.hpp`, `src/ui_hud.cpp`, `src/application.cpp`, контракт событий `ApplicationHost` и обе его реализации — обычное окно и сценарный стенд; `tests/ui_hud_input_test.cpp`.

**Оригинал:** `CGameUI::mapEventHandlers @0xa97e00`, `handle_onClick @0xa83690`, событие `CEGUI::Window::EventMouseButtonDown @0x14247e0`; для инвентаря собственный `mapEventHandlers @0xb4f1b0`.

Не использовать пару press/release как единственную форму действия. Сохранять упорядоченные события down/move/up и при необходимости захват. Для указанной цепочки HUD запускать оригинальную команду на down, не дожидаясь up. Игровой мир не должен получить то же нажатие. Сменившееся дерево UI не должно обработать одно событие второй раз.

Разделить визуальные состояния Pushed/PushedOff и вызов игровой команды. Перенести проверенные callback-названия в диспетчер действий напрямую: не изображать их через синтетические клавиши K/F/J. Настоящие клавиши должны вызывать те же действия по восстановленной таблице привязок; текущая PORT-раскладка не является эталоном.

**Приёмка:** на down над InventoryButton ровно один callback, до up; move вне кнопки не отменяет уже прошедшую команду; up не повторяет её; down в мире с последующим up на кнопке не создаёт GUI-команду; исходный down по GUI не вызывает движение/атаку. Для disabled/modal/capture отдельно установить исходные условия библиотеки — не вывести их из общего удобного правила.

В старом тесте снять ожидание «команда только на matching release» для этой ветви. Негативный контроль: возврат старой `hud_click_callback`-политики должен ломать новый тест фазы события.

## P3 — две стороны интерфейса, модальные окна и настоящая пауза

**Файлы:** `src/application.cpp`, `include/torchlight/inventory_view.hpp` как место удаления роли глобального UI-состояния. Предлагаемый отдельный модуль `game_ui_state.hpp/.cpp` с тестируемой логикой, без графических зависимостей.

**Оригинал:** `getIsPaused @0x56e570`, `bothCoveredPartial @0xa82ae0`, `modalDialogOpenPartial @0xa82a80`, `toggleInventory @0xa8ea20`, `togglePet/Stats/Quest/Skill/Journal`, `closeLeft/closeRight`, `togglePause @0xa8e2d0`.

Каждое окно должно иметь сторону/модальность и состояния открытия, закрытия, частичной открытости. Их переходы брать из методов соответствующего окна, а не заранее навязать всем одно enum-поведение. Отдельно явная пауза, флаг клиента, консоль и условие её настройки. Метод вычисления паузы должен повторять оригинальный порядок проверок.

Действия открытия/закрытия и расчёт паузы не смешивать: две панели справа в пробе предиката не означают, что такая комбинация разрешена контроллером. Из `toggleInventory` переносится закрытие нужной стороны и снятие явной паузы, а не `closeAll`.

**Приёмка:** повторить 682 проверенных случая предиката и добавить истинные последовательности toggle; одна сторона не ставит мир на паузу, две противоположные ставят; модальность и явная пауза независимы. Поведение анимации перехода проверить собственным тестом времени. Не распространять результаты на смерть/возрождение без их исследования.

## P4 — runtime-дерево HUD и реальные данные

**Файлы:** `src/ui_hud.cpp`, `include/torchlight/ui_hud.hpp`, `src/application.cpp`; общие операции add/remove/visible/z-order в runtime-слое UI.

**Оригинал:** `CGameUI::create` около `0xaa07bc–0xaa0840`; `togglePause @0xa8e2d0`; `updateIngameUI @0xab8100`.

После загрузки bottomhud воспроизвести удаление PlayButton, сохранив объект для сценария паузы. При открытии паузы восстановить реальный родитель/видимость по аргументам ASM. Не удалять кнопку навсегда из pak и не менять её callback на произвольное открытие Options.

Для цели восстановить ветвь получения target, имя/уровень/описание/HP и условия скрытия. Передавать эти данные из общего игрового цикла, а не только в probe. Уточнить арифметику баров и округление UVector2; не отменять уже подтверждённое отсутствие верхнего clamp.

**Приёмка:** обычный runtime-frame не содержит PlayButton среди присоединённых видимых детей; pause-frame размещает его как оригинал; возврат не оставляет дубликат. Цель появляется/исчезает на установленных оригиналом событиях; тест меняет реальное состояние игрового цикла, не вручную заполняет UiHudValues и объявляет успехом весь путь.

## P5 — исполнение используемых схем и состояний CEGUI

**Файлы:** `ui_layout.hpp/.cpp`, `gles_ui_renderer.hpp/.cpp`; предлагаемые отдельные структуры `ui_skin`/`ui_runtime` для схемы, состояния и операций рисования. Сохранять чистый разбор документа отдельно от изменяемого экземпляра окна.

**Ресурсы:** `.scheme → FalagardMapping`, `.looknfeel → StateImagery/Layer/Section`, `.imageset`, конкретные `.layout`. В `results/resource-manifest.json` есть фактические употребления. Не начинать с реализации всех возможностей современной CEGUI или всех неиспользуемых луков.

Первый замкнутый набор: DefaultWindow, StaticImage, StaticText, ImageButton, StandardButton, WeaponSwitch, RadioTab/RadioButton и компоненты, на которые они действительно ссылаются. Затем необходимые tooltip/scroll/combobox/slider ветви для следующего окна. Вспомогательные Child-контролы включать по их ссылкам, не только по прямой статистике layout.

Выбирать активное состояние и его sections, строить упорядоченные команды рисования с rect/UV/colour/clip. FrameComponent, ImageryComponent и TextComponent не сводить к одному stretched quad. Учитывать image offset/autoscale и наследование свойств в том месте, где это делает оригинальная библиотека. Регистр атрибутов и дубликаты не «нормализовать» без проверки оригинального парсера.

**Эталонный стенд:** отдельный процесс с комплектной CEGUI и проверенным ABI/версиями. Сначала разрешённые размеры и список команд рисования на фиксированном дереве, затем пиксели. Стенд должен явно указывать подменённые renderer/settings/resource-provider зависимости. Его создание — следующая работа, в этом комплекте такого стенда нет.

**Приёмка:** набор golden-traces для normal/hover/pushed/pushed-off/disabled/selected/unselected применимых типов; общий порядок примитивов, координаты/UV/клип. Сравнение текста учитывает версию FreeType; одинаковое число glyphs не доказывает одинаковый растр. Не возвращать выдуманные рамки и fallback-картинки для известных пустых состояний.

## P6 — оригинальная оболочка инвентаря и вид персонажа

**Существующие файлы:** `application.cpp`, ресурсы/скелетная анимация/сцена проекта, `inventory_view.cpp` только как диагностический fallback. **Предлагаемый контроллер:** `inventory_menu.hpp/.cpp`, не огромная дополнительная ветвь в общем игровом цикле.

**Оригинал:** `CInventoryMenu::createMenus @0xb569e0`, `setOpen @0xb4eb70`, `update @0xb4f9d0`. Начать с последовательности загрузки модели, layout, камеры, viewport и overlay.

Загружать настоящие inventory.mesh/material, основной skeleton и связанные open/idle/close. Связать TopFrame/BottomFrame с tag-костями, а не с постоянными экранными координатами. Время, очередь и blending перенести по исходным вызовам. Клип длиной 0.5 с не даёт права самостоятельно выбрать плавность перехода.

Вид персонажа — собственная подтверждённая камера/viewport, а не screenshot основной сцены. Восстановить влияние якоря на положение viewport, aspect ratio, обрезку и уборку после CLOSE. Аргументы, потерянные декомпилятором, уточнить по ASM.

**Приёмка:** известные состояния закрыто/открывается/открыто/закрывается; pose в начале, середине и конце исходных клипов; rect кнопок/слотов следует за видимой частью; после завершённого закрытия нет оставшегося viewport или невидимой блокирующей области. Изменение разрешения следует восстановленному rescaleUI, а не произвольному сохранению состояния.

## P7 — предметы, слоты, вкладки и действия инвентаря

**Файлы:** новый контроллер инвентаря, `inventory.*`, `player_session.*`, взаимодействие/drag/drop; не менять правила расчёта предметов ради UI.

**Оригинал:** `updateLayout @0xb53430`, `setSlotIcon @0xb51bf0`, `mapEventHandlers @0xb4f1b0`, обработчики down/up/rotate, таблица слотов в createMenus.

Сопоставить каждый логический слот с именем UI и типом предмета. Отдельно подтвердить screen-left/character-right: имена EquipLeftHand/EquipRightHand не являются готовой логической схемой. Передавать реальные идентификаторы экземпляров предметов, а не индексы текущего текстового списка.

Восстановить порядок групп/вкладок, Selected-состояния и фильтрацию backpack/spells/fish. Не «чинить» несколько Selected=True в XML без оригинального контроллера. Обработчики удержания поворота — start/stop, не разовый произвольный поворот по клику. Drag/drop, stack split, экипировка, перенос между панелями — самостоятельные цепочки с подтверждёнными условиями.

**Приёмка:** предмет сохраняет GUID/roll/количество после движения; запрещённый перенос не теряет предмет; положение курсора и область слота согласованы во время анимации; предмет в визуальной левой руке соответствует правильному логическому слоту; сохранение/загрузка не выдаёт новый item instance. Неподдержанная операция остаётся зарегистрированной границей разработки, а не получает «похожую» замену.

## P8 — магазин, питомец, умения, журнал и задания

Переносить после P3/P5 и проверенного пути инвентаря. Их внешнее сходство не означает одинаковое состояние, паузу или команды.

**Магазин/услуги:** `merchant_menu.c`, `stash_menu.c`, `enchant_menu.c`, `combine_menu.c`; реальные createMenus/setOwner/updateLayout и исходные ограничения покупок/продажи/выкупа. Текущая покупка зелий — только один поддержанный сценарий, не весь магазин.

**Питомец:** `pet_menu.c` и pethud, логическое содержимое питомца, команды/трансформация/отправка; правая панель игрока и левая питомца должны совместно работать по оригинальным правилам. Не использовать панель игрока с другой надписью.

**Умения:** skillmenu и skillfoldout, описание/ранг/панель назначения; выбор левого/правого действия и хоткеи должны следовать восстановленным командам. Наличие Infuse не разрешает превратить любое остальное умение в тот же эффект.

**Квесты/журнал:** journalmenu, questmenu, questdialogmenu, их контроллеры и QuestManager. Journal и Quests — разные команды. Флаги квестов не заменяют цели, текст, NPC-условия, диалоги, награды и зависимости переходов.

**Приёмка для каждого окна:** реальное игровое действие через оригинальное окно → изменение общей модели → закрыть/открыть → сохранить/загрузить в другом процессе → тот же результат. Не выдавать тестовый seed/выданное тестом золото за прохождение кампании.

## Как распределять работу

Общие интерфейсы P1–P5 должны интегрироваться последовательно: они меняют одни и те же ui_layout/ui_hud/application. Отдельно можно исследовать оригинальные функции и готовить эталонные трассы, не правя эти файлы одновременно. Оконные контроллеры разделять между исполнителями после закрепления общего контракта событий/состояния/рендера.

Следующий конкретный пакет для разработчика — **P1 и P2 отдельными коммитами**, каждый со своим сравнением с оригиналом. Не начинать одновременно магазин, питомца и шесть новых окон: это снова размножит прототипные решения поверх неверного общего слоя.
