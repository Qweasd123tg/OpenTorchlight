# OpenTorchlight — второй аудит: новые связи в расширенном экспорте

## Область и доказательства

Исследован архив `OpenTorchlight-gpt-pro(1).zip`, SHA-256:

`3abe6e8f281d43d0153723a667112e2f0e457ae9de18438d1b696d0b0e3bc4cb`

Изучены `GPT_PRO_REVIEW.md`, `AGENTS.md`, README, тематические исследования, текущий переносимый код, расширенный `research/decompiled-core/`, доступный адресный ASM, `original-callgraph.tsv` и индекс символов. Нумерация строк далее относится к этому архиву. Сокращение `core/` означает `research/decompiled-core/`.

Оригинальный ELF, игровые pak и OGRE-библиотеки в переданном архиве отсутствуют. SHA-256 исходного ELF из сопровождающих материалов: `91b41ae9dfea30aab6bc14dbbfcceaee096d600f39635b8507f5a88b5d41724b`. Его соответствие фактическому бинарнику здесь не перепроверялось. Оригинальные функции и полноценная игра не запускались.

**Изменений в `src/`, `include/`, `tests/` и CMake относительно первого архива нет.** Добавлены 34 экспорта центральных классов; всего в новом core — 70 файлов и 2 630 заголовков функций. Подробное сравнение: `snapshot-diff.txt`. Это новая доказательная база, а не снимок после исправления прежних ошибок.

Собрана неизменённая `torchlight_core`; напрямую запущены `actor_motion_test` и `damage_test` — оба прошли. Повторный запуск старого стенда на новой библиотеке воспроизвёл все семь прежних наблюдений, для которых был сделан исполняемый тест. Они не пересказываются как новые находки.

Здесь используются два разных уровня подтверждения:

- **Воспроизведено в порте:** фактически исполнен код новой переносимой библиотеки на синтетических данных. Это не дифференциальное исполнение оригинала.
- **Вывод по оригиналу:** цепочка восстановлена из предоставленного псевдокода, полей, символов и разрешённых вызовов; для точной реализации указан следующий ASM/числовой тест. Такой вывод не объявляется `original-code` лишь потому, что у функции известен адрес.

Находки расположены по ожидаемому влиянию на обычное прохождение. Зависание на граничном значении входных данных выделено отдельно: его серьёзность не означает, что такая настройка имеется в поставляемых игровых ресурсах.

## 1. Timeline теряет содержимое ещё до runtime; remap только LOGICGROUP недостаточен

**Уверенность: очень высокая для потери данных; высокая для связи с remap и событиями оригинала.**

### Конкретное расхождение

`collect_layout_objects` копирует только скалярные `PROPERTIES`, а из вложенных групп отдельно разбирает `LOGICGROUP`: `src/level_scene.cpp:286–334`, особенно 325–327. В `LayoutObject` нет представления вложенных timeline-данных: `include/torchlight/level_scene.hpp:112–137`. После `load_layout` исходное дерево ADM больше не сохраняется: `src/level_scene.cpp:482–496`.

Это отличается от просто «ещё не реализован Play»: когда обработчик появится, нужных дорожек и ключей у него уже не будет. `activate_level` сейчас действительно отправляет `Play` для START ON LOAD (`src/logic_runtime.cpp:167–169`), но это не доказывает исполнение timeline. Desktop забирает список зарегистрированных вызовов и использует только его размер (`src/linux_desktop_main.cpp:852–853`).

### Цепочка оригинала

`CTimeline::loadTimelineFromDataGroup @0x007bc0d0`, `core/timeline.c:2751–2890`:

```text
TIMELINEDATA
  ID -> getRemappedID -> идентификатор самой timeline
  TIMELINEOBJECT
    OBJECTID -> getRemappedID -> GetObjectInScene
    TIMELINEOBJECTPROPERTY / OBJECTPROPERTYNAME
    TIMELINEOBJECTEVENT / OBJECTEVENTNAME -> GetInputLogicWrapper
    TIMELINEPOINT / TIMEPERCENT / INTERPOLATION / VALUE
```

Чтение TIMELINEDATA: 2754–2757; remap ID: 2771–2786; remap OBJECTID: 2798–2815; имя свойства: 2835–2842; разрешение входного события: 2854–2888. Имена групп/ключей точек дополнительно видны в `CTimeline::saveTimelineToDataGroup`, `core/timeline.c:2400–2626`.

**Неочевидная связь:** timeline — не исключительно визуальная анимация; её дорожка может вызывать вход логического объекта. Значит, потеря timeline может блокировать последовательность открытия двери, активации следующего этапа или другого графа, а не только движение декорации. Конкретный игровой сценарий без pak не установлен.

Вторая связь: повторное использование одного room layout требует remap и собственного ID timeline, и её целевых OBJECTID. Текущий remap меняет object.id/parent и ссылки LOGICGROUP: `src/level_scene.cpp:708–741`. Добавление Play без расширения этого контракта потенциально направит дорожку на неправильный экземпляр комнаты или не найдёт цель.

### Воспроизведение

Два синтетических ADM отличаются значением одной TIMELINEPOINT: 3 против 90. Общий ADM-парсер сохраняет разницу; `LevelSceneLoader::load_layout` выдаёт одинаковые скалярные свойства и метаданные объектов, без timeline-дорожек. Различие `source_path` специально исключено из сравнения. См. `reproduce.cpp`, `reproduction.log`.

### Узкая правка и проверка

Сначала сохранить typed timeline definition либо необходимые вложенные группы вместе с контекстом загрузки. Затем remap только ссылочные идентификаторы, не все числовые значения и не GUID ресурсов. Только после этого реализовать одну property-дорожку и одну event-дорожку.

Проверки: два файла с разными VALUE должны давать разные определения; два экземпляра одной комнаты должны воздействовать каждый на собственную дверь; отсутствующая цель должна давать диагностируемую ошибку, не случайный чужой объект. Следующие адреса для ASM: `0x007bc0d0`, `0x00701d50` (`CDescriptorLoadConfiguration::getRemappedID`), `0x007b7420` (`CTimeline::UpdateTimeline`).

## 2. Категория ресурса подменяет враждебность; два пути создания дают разный NPC

**Уверенность: очень высокая для текущего поведения и игнорирования UNIT-флагов; высокая для разделения оригинальных проверок.**

### Конкретное расхождение

Общий `create_resource` делает любой объект категории `MasterResourceKind::monster` боевой целью: `src/entity_world.cpp:188–278`, итоговое присваивание на 278. Путь Unit Spawner вызывает его без дополнительной корректировки: 343–368.

Путь размещённого layout-объекта, напротив, после того же конструктора требует точный `UNITTYPE == MONSTER` и проверяет только layout-флаги: `src/entity_world.cpp:110–127`. Флаги TARGETABLE/INVINCIBLE из загруженного UNIT не участвуют ни в этом предикате, ни в общем конструкторе.

Далее `EnemyController::update` решает, должен ли персонаж вообще исполнять вражеский AI, через `combat_targetable`: `src/enemy_ai.cpp:99–103`. В одну переменную объединены по меньшей мере три независимых вопроса: можно ли выбрать объект целью, можно ли нанести ему урон и должен ли он атаковать игрока. Собственная фракция/отношение к игроку при этом не проверяется.

### Цепочка оригинала

`CCharacter::unitInit @0x008529a0` читает TARGETABLE в `+0x531` (`core/character.c:28613–28616`), INVINCIBLE в `+0x52e` (28763–28766) и ALIGNMENT (29226–29244). Это отдельные свойства уже загружаемого UNIT, а не только параметры layout.

`CMonster::attackAI @0x008dfd80` проверяет жизнь цели и затем `CCharacter::isFriend` (`core/monster.c:3438–3446`). Сам `isFriend @0x008102d0` использует alignment и дополнительные состояния (`core/character.c:2138–2162`). `updateAI` отдельно проверяет цель, жизнь персонажа и состояния мира: `core/monster.c:4776–4808`.

Не делается вывод «любой NPC оригинала мирный»: UNITTYPE сам по себе этого не доказывает. Более того, чтение ALIGNMENT здесь имеет fallback EVIL. Вывод другой: категория исходного файла и признак доступности для выбора не являются заменой отношению между персонажами.

### Воспроизведение

Один синтетический NPC с одинаковыми характеристиками:

```text
placed:  combat_targetable=0, атак за первый update=0
spawned: combat_targetable=1, атак за первый update=1
```

Отдельный UNIT с `TARGETABLE=false`, `INVINCIBLE=true` принимает урон и при размещении, и при спавне, если этих свойств нет в layout. См. `reproduction.log`.

### Узкая правка и проверка

Объединить применение исходных характеристик для обоих путей создания: сначала наследованный UNIT, затем явные layout-overrides. Разделить alive/enabled/targetable/invincible и отношение к игроку. Не отключать атакующий AI лишь потому, что персонаж не может быть выбран целью; точные запреты на атаку выводить из соответствующих состояний оригинала.

Регрессионный тест должен создавать один и тот же UNIT двумя путями и сравнивать семантические флаги. Отдельно проверить запрещённое получение урона и отношение к игроку. Для переноса alignment-политики нужен ASM `0x008102d0`, а не самодельное правило «NPC всегда друг».

## 3. Обычный переход на этаж пересоздаёт игрока; сохранение мира связано и с timeline

**Уверенность: очень высокая для сброса текущих объектов по коду; высокая для оригинального сохранения логики. Полный warp с ресурсами не запускался.**

### Конкретное расхождение

Каждая итерация внешнего цикла уровня создаёт новый `CombatController` и `PlayerCombatState` из `players.front()`: `src/linux_desktop_main.cpp:689–692`, 735–738. Поднятое оружие меняет локальный `combat`, а броня — локальный `player_combat`, не исходный prototype (`src/linux_desktop_main.cpp:1008–1020`). Поэтому следующий штатный переход теряет эти изменения и заново устанавливает HP из prototype. Это проблема времени жизни сессии, не только отсутствие сохранения на диск.

Там же заново создаются `LogicRuntime` и `RuntimeEntityWorld`: 705–710. Без отдельного состояния этажа заново появляются исходные сущности и первоначальные состояния графов. Одинаковый seed восстанавливает генерацию, но не факт подбора предмета, убийства или срабатывания одноразового узла.

### Новая связь из расширенного экспорта

`CGameClient::performWarp @0x0058d110` вызывает `CPlayer::storeLevelSavedState` (`core/game_client.c:11104`). Затем он сохраняет указатель игрока `this+0x58` вокруг `unloadCurrentLevel`: 11105–11108. Игрок не создаётся заново из начального prototype. Это не исключительно путь ручного Save.

`CPlayer::storeLevelSavedState @0x008f6080` сохраняет также состояние timeline. В `core/player.c:6711–6741` видны относительный прогресс, флаги, данные идентификации и parent hierarchy hash, затем `CLevelState::addLogicState @0x009704b0`.

`CGameClient::restoreLevelState @0x0057f7c0`, `core/game_client.c:5618–5645`, сопоставляет дополнительные поля и иерархию, восстанавливает enabled/playing и в определённой ветке вызывает `Play` и `UpdateTimeline` с сохранённой долей длительности.

**Неочевидный риск будущей реализации:** кешировать только «список живых монстров» недостаточно — двери и последовательности могут вернуться к начальному состоянию. Идентификация узлов между генерациями также не должна без проверки опираться на один новый runtime-id. Из этой ветки пока не выводится универсальное правило воспроизведения или подавления старых событий при восстановлении: это требует отдельного теста.

### Узкая правка и проверка

Первым отдельным коммитом вынести изменяемое состояние игрока за цикл уровня. Не переносить за цикл все level-bound указатели и активную цель; после загрузки мира перепривязать представление и сбросить только контекст текущего действия.

Вторым — ограниченный session-cache состояния подходящих этажей и логических объектов, без обязательной реализации файлового Save. Условия volatile/reset изучить отдельно: нельзя объявить все данжи бессрочно неизменными.

Проверки: получить урон и сменить экипировку, выполнить A→B — HP и предметы сохраняются; выполнить A→B→A в тестовом не-сбрасываемом мире — удалённый предмет не появляется, одноразовый узел не срабатывает повторно. Для timeline отдельно проверить восстановление прогресса и отсутствие непредусмотренного повторного event. Адреса для уточнения: `0x0058d110`, `0x008f6080`, `0x0057f7c0`.

## 4. Глубина этажа используется вместо рассчитанного ранга монстров

**Уверенность: очень высокая для текущего аргумента; высокая для наличия отдельного расчёта ранга. Точная формула требует ASM и CDungeon.**

### Конкретное расхождение

Desktop передаёт `max(1, level.address.depth)` как `spawn_level`: `src/linux_desktop_main.cpp:707–710`. Мир использует его для HP, урона и брони (`src/entity_world.cpp:194–224`), а также при выборе подходящих ресурсов unit type (`src/entity_world.cpp:151`, 323).

**Следствие не ограничено числом HP:** неверный ранг способен изменить и состав выбранных ресурсов/экипировки через уровневые ограничения.

### Цепочка оригинала

`CGameClient::getRankOfMonstersOnFloor @0x005848b0`, `core/game_client.c:8099–8165`, имеет отдельные ветви. При наличии CDungeon видны преобразование аргумента этажа, множитель `dungeon+0x70`, дополнительные параметры `+0x74/+0x78/+0x7c`, а в соответствующей ветке — `hasDungeonHistory`, `getDungeonRank` и состояние игрока.

`CResourceManager::createMonster @0x00d76940`, `core/resource_manager.c:1993–1997`, при отсутствии явно заданного ранга берёт значение из уровня (`level+0x1a8`), а не вычисляет его как номер этажа.

Нельзя свести всё к правке `depth+1`: смысл параметра и индексация у вызывающей стороны ещё должны быть проверены. Неизвестны именованные ключи полей CDungeon и значение `DAT_00fa4810`, используемое перед приведением к целому.

### Связь со сложностью: отдельная доказанная часть, не универсальная формула

Текущий конструктор мира загружает только `DAMAGE_MONSTER.DAT.adm`: `src/entity_world.cpp:83–96`.

`CResourceManager::getGraphDamage @0x00d6f880`, `core/resource_manager.c:301–369`, выбирает DAMAGE_MONSTER_EASY / DAMAGE_MONSTER / DAMAGE_MONSTER_HARD / DAMAGE_MONSTER_VERYHARD для значений сложности 0/1/2/3 соответственно. В графе прямых вызовов этот resolver подтверждён у `CCharacter::applySaveState` и `CMissile::doDamageToCharacter`.

Это **не доказательство**, что каждый путь создания новой melee-атаки напрямую вызывает resolver. Пока порт ограничен одним режимом сложности, normal-graph допустим как явно обозначенное ограничение. Но его нельзя считать универсальным исходным графом для любой сложности, восстановленного персонажа или снаряда.

### Узкая правка и проверка

Ввести `LevelCombatContext` с отдельными `monster_rank` и `difficulty`, не смешивая их с адресом/seed этажа. Прежде чем переносить формулу, экспортировать `CDungeon::loadDungeon @0x00934720` и ASM `0x005848b0`; получить значения констант и реальные ключи dungeon DAT.

Числовой тест: одинаковая глубина, разные разрешённые параметры данжа/история — сверить рассчитанный ранг, значения графов и список кандидатов. Для сложности отдельно тестировать выбор файла графа, не компенсировать всё множителем итогового урона.

## 5. У монстра есть самостоятельный AI_ATTACKCOOLDOWN; это не длительность клипа

**Уверенность: очень высокая для игнорирования свойства в порте; высокая для двух независимых ограничителей оригинала.**

### Конкретное расхождение

Порт читает ATTACKSPEED, но не AI_ATTACKCOOLDOWN: `src/entity_world.cpp:248–259`. `EnemyController` использует один cooldown и после удара присваивает `max(0.1, 100 / attack_speed)`: `src/enemy_ai.cpp:105–107`, 130–144.

### Цепочка оригинала

`CMonster::unitInit @0x008e2ae0`, `core/monster.c:4266–4271`: после CCharacter::unitInit читает `AI_ATTACKCOOLDOWN` с fallback 0 и сохраняет его в `+0x7ec`.

`CMonster::attackAI @0x008dfd80`:

- положительный счётчик `+0x7e8` не допускает новую атаку: 3430;
- отдельно проверяется `CCharacter::performingAttack`: 3493–3494;
- после успешного CCharacter::attack увеличивается cooldown: 3514–3526;
- при выбранной экипировке участвует её поле `+0x408`, затем добавляется `+0x7ec`.

`CMonster::updateAI @0x008e3a40` уменьшает `+0x7e8` сразу при входе, **до** возможного пропуска AI-решения по KAIThinkTime: 4750, 4762–4768.

**Важная оговорка:** это не доказательство схемы «дождаться конца анимации, потом дополнительно ждать AI_ATTACKCOOLDOWN». Счётчик запускается после успешного начала атаки и может идти одновременно с её исполнением. Для новой атаки должны быть выполнены обе проверки. Нельзя просто сложить длину клипа и параметр задержки.

Поле выбранной экипировки `+0x408` пока не приравнивается к SPEED/ATTACKSPEED. Его ресурсное происхождение нужно проследить; экспорт `CEquipment::unitInit @0x00889110` в core не дал тела функции.

### Воспроизведение

Два одинаковых синтетических UNIT, отличающихся только AI_ATTACKCOOLDOWN=0 и 5, при ATTACKSPEED=100 дают **4 атаки за 3 секунды в обоих случаях**. Выполнена последовательность update(0), затем 30 шагов по 0.1. Это измерение порта, не исходного ELF.

### Узкая правка и проверка

Загрузить свойство и хранить отдельный AI-cooldown. Отдельно оставить состояние выполняемой атаки, которое должно быть согласовано с клипом и HIT из первого ревью. Уменьшать AI-счётчик независимо от частоты «мышления».

Проверки: параметр 5 предотвращает прежнее повторение каждые 1 s; короткий AI-cooldown не обрывает длинную активную атаку; прореженный think-step не замораживает счётчик. До связывания оборудования экспортировать ASM `0x008dfd80`, `0x008e3a40`, `0x00889110`.

## 6. Адрес этажа сохраняется, но контекст точки входа теряется

**Уверенность: очень высокая для потери warp_name в текущем переходе; высокая для выбора entry в оригинале.**

### Конкретное расхождение

`WarpRequest` содержит `warp_name`, но `LevelTransitionState::resolve` возвращает только dungeon/depth: `src/level_transition.cpp:66–90`. Сам по себе такой address-helper допустим, но desktop не переносит остальной контекст отдельно: `src/linux_desktop_main.cpp:1419–1430`. Имя выводится в лог, а следующая `load_desktop_level` получает лишь адрес и seed: 689–692.

Выбор spawn-позиции идёт через `layout_player_start`/`generated_player_start`, а не через запрошенную именованную точку: `src/player.cpp:331–394`; для generated берётся первый chunk. Есть fallback на WarperMain, но нет общего выбора по переданному warp_name.

### Цепочка оригинала

`CGameClient::warpLevels @0x005819b0` приводит переданное имя к верхнему регистру и сохраняет его: `core/game_client.c:6606–6608`.

`CLevel::loadRoomLayout @0x0095f150` различает ELevelEntryType: ветви Entrance/Exit/portal в `core/level.c:18629–18786`. В другой ветке он сравнивает имя Warper с переданной строкой и при entry-type 5 сохраняет его world position и направление: `core/level.c:18934–18955`.

Таким образом, место появления — функция не одного dungeon/depth. При движении назад нельзя по умолчанию всегда брать тот же entrance.

### Узкая правка и проверка

Передавать `LevelEntryRequest { address, entry_kind, warp_name }` до разрешения позиции после сборки layout. Не перегружать helper адреса выбором геометрии; сохранить отдельный контекст перехода. Отдельно определить поведение для отсутствующей/неоднозначной именованной точки по оригиналу.

Тест: в одной целевой сцене два warper с разными именами/координатами; разные запросы должны выбирать соответствующие точки. Вход с предыдущего и следующего этажей должен использовать правильный тип entry. Уточняющие адреса: `0x005819b0`, `0x0095f150`, `CWarperDescriptor::Get_getWarpName @0x00692ce0`.

## 7. Уточнение первого ревью: освещение сцены и MATERIAL AMBIENT — разные входы

**Уверенность: высокая для связей полей и вызовов; средняя для точных аргументов цвета и бинарных констант до ASM. Это развитие прежнего пункта №8, не отдельное повторное открытие.**

В первом ревью была установлена дополнительная runtime-стадия CLevel→CGenericModel::setAmbient. Новый экспорт позволяет связать её с конкретными ресурсными полями и отличить от освещения сцены.

`CLevelTemplateData::load @0x009762f0`, `core/level_template_data.c`:

| Ресурсные поля | Поля объекта | Дальнейшее использование |
| --- | --- | --- |
| AMBIENT RED/GREEN/BLUE | +0x720/+0x724/+0x728 | SceneManager::setAmbientLight |
| MATERIAL AMBIENT RED/GREEN/BLUE | +0x730/+0x734/+0x738 | CLevel::updateMaterialAmbient |
| DIRECTIONAL RED/GREEN/BLUE и INTENSITY | +0x740/+0x744/+0x748 | Light::setDiffuseColour |
| DIRECTIONAL X/Y/Z | +0x750/+0x754/+0x758 | Light::setPosition и вычисление направления |

Чтение первых двух групп: 3864–3960; directional RGB: 3962–3994; вектор: 4028–4047; intensity: 4049–4059. **INTENSITY уже умножена на RGB при заполнении +0x740** — повторное умножение в renderer было бы отдельной ошибкой.

`CGameClient::refreshLighting @0x00582e80`, `core/game_client.c:7424–7448`, передаёт ambient и directional в разные объекты OGRE, затем вызывает `CLevel::updateMaterialAmbient`. Этот последний путь берёт группу +0x730 и для соответствующих Room Piece вызывает `CGenericModel::setAmbient`: `core/level.c:11071–11144`. Метод `CGenericModel::setAmbient @0x0089aef0` обращается к **обоим** Ogre::Material::setAmbient и setDiffuse (`core/generic_model.c:824–834`). Точные потерянные аргументы цвета ещё нельзя считать восстановленными.

Текущий `LevelRules` не сохраняет эти поля (`include/torchlight/level_scene.hpp:93–109`, `src/level_scene.cpp:407–478`), а fragment shader использует `0.55 * material_ambient + (0.35 + 0.55 * vertex_light) * diffuse_color`: `src/gles_scene_renderer.cpp:127–129`. Это не подстановка исходных параметров этажа.

**Следствие:** изменение одного общего коэффициента ambient не восстановит две независимые зависимости. Если весь экран слишком тёмный, нельзя автоматически делать «diffuse=ambient» либо добавлять яркость — часть входных данных вообще не дошла до renderer.

Узкая правка: загрузить раздельные поля шаблона уровня и передать их до renderer; затем подтвердить runtime material override и конкретный порядок применения к экземплярам/материалам. Сначала тестировать effective uniforms/material values, затем изображение. Не распространять найденную Room Piece ветку на все модели без проверки.

Следующие адреса: `0x009762f0`, `0x00582e80`, `0x00950a40`, `0x0089aef0`. Нужны исходные байты констант `0x00fa8740`, `0x00fa8780`, `0x00fa87a0`, `0x00fa47fc`; в этом отчёте привычные значения 255/знаковой маски не выданы за измеренные данные ELF.

## 8. Timer с нулевым периодом зацикливает кадр; лимит dispatch не защищает

**Уверенность: очень высокая для зависания порта. Эквивалентное поведение оригинала для TIME=0 не установлено.**

`reset_timer` выбирает TIME, когда MAXTIME не больше него: `src/logic_runtime.cpp:373–377`. `update` выполняет while(timer_remaining<=0), излучает событие, сбрасывает таймер и возвращает overshoot: 379–403.

При `TIME=0`, `MAXTIME` по умолчанию и `LOOPS FOREVER=true` не существует шага, переводящего remaining в положительное число. Без изменяющих этот объект обработчиков цикл не имеет нормального завершения; накопление событий также может привести к исчерпанию памяти.

Защита в `process_events` (`src/logic_runtime.cpp:184–188`) ограничивает одну обработку очереди, а не внешний цикл update. Каждый самостоятельный emit может запускать новую обработку со свежим локальным счётчиком. Поэтому event limit не ограничивает этот случай.

Синтетический Timer действительно не вернулся из update(0.1); отдельный процесс остановлен watchdog через 0.25 s и ограничен памятью. Timeout сам по себе не доказывает бесконечность; доказательство — неизменный неположительный remaining и отсутствие выключающих обработчиков. См. `check_zero_timer.py`, `zero-timer.log`.

Для гарантированной живучести нужен общий бюджет работы update либо отказ от недопустимых периодов. Однако «TIME=0 должен срабатывать один раз за кадр» пока не установлено как правило оригинала. До окончательной семантики экспортировать `CLogicTimer::update @0x00988020` и `resetTimer @0x00987fe0`. Отдельно проверить zero/negative/random диапазон, overshoot и самовыключение через граф. Наличие этой настройки в настоящих ресурсах не проверено.

## Дополнительные проблемы проверок и индексов

### CTest без оригинала зарегистрировал ноль тестов

Несмотря на `BUILD_TESTING=ON`, `ctest -N` показывает `Total Tests: 0`. `add_test(actor_motion)` и `add_test(damage_calculation)` находятся внутри `if(TORCHLIGHT_ORIGINAL)`: `CMakeLists.txt:191`, 225, 270. При этом оба executable работают без оригинальных ресурсов и были успешно запущены вручную.

Узкая правка: зарегистрировать pure tests вне этой ветки; original-dependent tests оставить внутри. Проверка: чистая конфигурация без пути к ELF должна регистрировать и исполнять хотя бы два независимых теста. Это не ошибка алгоритма игры, но текущая конфигурация не обеспечивает ожидаемую проверку переносимого core.

### Граф вызовов — не последовательность исполнения

`tools/ghidra/ExportCallGraph.java` получает Set<Function> и сортирует его по адресу callee. TSV показывает разрешённые связи, но теряет число вызовов, места вызова и порядок внутри функции. Кроме того, он не раскрывает все виртуальные вызовы. Нельзя выводить порядок фаз из порядка строк TSV или объявлять метод неиспользуемым только по отсутствию прямого ребра.

Для значимых связей создан `evidence-edges.tsv` с номером строки исходного файла. В частности, он подтверждает два прямых известных потребителя getGraphDamage, а не выдуманную универсальную цепочку свежего spawn.

### Индекс strings содержит файловые смещения и не все широкие строки

`tools/ghidra/export_analysis_indexes.sh:37–40` использует `strings -a -t x -n 5`. Это индекс обычных строк с **file offsets**, не адресов виртуальной памяти. Отсутствие AI_ATTACKCOOLDOWN или MATERIAL AMBIENT в таком поиске не опровергает их присутствие: широкие литералы видны в декомпиляции.

Следующий отдельный индекс стоит получить с соответствующим wide-encoding режимом (для этого Linux wchar32 сначала проверить little-endian 32-bit, например `strings -a -e L -t x -n 5`). VA для найденного file offset вычислять по ELF-сегментам; не копировать offset как адрес для Ghidra/ASM.

## Проверяемый порядок продолжения

Сначала сохранить ещё неисполняемые timeline-данные и разделить политику создания сущностей — иначе дальнейшие системы получают уже искажённый вход. Независимыми маленькими изменениями вынести состояние игрока за цикл уровня, убрать зависание таймера и зарегистрировать pure tests.

Затем связать две проверяемые части атаки: исходный HIT/клип из первого ревью и отдельный AI-cooldown из этого. Это не один универсальный cooldown.

Ранг монстров и освещение переносить после получения названных небольших экспортов и констант. Не закрывать неизвестные поля коэффициентами, подобранными по картинке или нескольким боям.

Все изменения пока являются предложениями. Исходники проекта этим аудитом не модифицированы.
