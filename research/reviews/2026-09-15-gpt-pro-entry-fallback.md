# OpenTorchlight: резервная точка появления на этаже

## Результат

Локальный патч поверх **OpenTorchlight-gpt-pro(5).zip**. Исходники изменены,
core собран, тесты выполнены. В GitHub ничего не отправлялось. Это один узкий
патч по первому приоритету `NEXT_CHECKS.md`, а не новый общий аудит проекта.

Исправляется резервный выбор места появления при обычном переходе между
этажами одного данжа, когда подходящий обратный Warper не найден. Найденный
Warper сохраняет прежний приоритет. Начальная загрузка без запроса перехода
сохраняет существующий путь выбора старта.

**Граница доказательства:** режим входа, условия ветвей и порядок перезаписи
позиции подтверждены адресными инструкциями. Соответствие трёх ветвей именам
`Player Start`, `Entrance`, `Exit` пока имеет статус **inferred**: исходной
таблицы переходов `.rodata` в текстовом ASM нет. Добавлена отдельная проверка
этой таблицы для машины с оригинальным ELF. Она не заменяется успешными
синтетическими тестами и здесь на оригинале не запускалась.

## Изменение поведения

В прежнем коде после неудачного поиска обратного Warper оставался обычный
старт, выбранный `layout_player_start` или `generated_player_start`. Первый
helper также мог бросить исключение в сцене только с Exit, не дав новому
разрешению точки перехода вообще выполниться.

Добавлен `find_same_dungeon_level_arrival`, возвращающий причину выбора,
необязательный ID узла, мировую позицию и горизонтальное направление.
Загрузчик вызывает его по составленному layout до прототипного стартового
helper. Включён уже существующий поиск обратного Warper; при его отсутствии
выполняется последовательный выбор Property Node.

В обычных относительных переходах спуск предпочитает Entrance, подъём —
Exit. Однако исходный режим определяется именно полями delta/absolute, а не
просто сравнением двух номеров этажей:

```text
Режим 1: delta > 0 ИЛИ (delta == 0 И absolute == 0).
Режим 0: остальные поддержанные сочетания.
```

В режиме 1 выбирается последний Entrance. В режиме 0 выбирается последний
Exit; когда Exit отсутствует, сохраняется первый Entrance. Если основная
точка не выбрана, используется последний Player Start. Когда нет и его —
исходная позиция (0, 0, 0) с направлением +Z. Editor Player Start не подменяет
обычный Player Start. Тип узла берётся из TYPE, а не из NAME. Такое правило
порядка нельзя заменить первым подходящим маркером или сортировкой.

Мировая позиция вычисляется существующим resolver порта с родительскими
преобразованиями. Масштаб узла не переносится на персонажа. Waypoint,
межданжевые переходы, LASTDUNGEON и специальный delta=-99 не входят в новую
ветку. Их прежнее поведение не заменяется этим приближением.

## Воспроизведение

Синтетическая сцена: Editor Player Start в (-100, 0, 0), Entrance в
(10, 0, 20), Exit в (30, 0, 40), обратного Warper нет. Переход Main:2 → Main:1
с delta=-1:

```text
До патча:    (-100, 0, 0)
После патча: (30, 0, 40)
```

Оба результата реально получены запуском C++-стендов на соответствующих
версиях core. Это не измерение оригинальной игры. Исходники находятся в
`reproductions/`, выводы — в `logs/reproduce-before.log` и
`logs/reproduce-after.log`.

## Доказательства и происхождение ASM

Кодовая основа взята только из свежего архива (5). Для узкой цепочки входа
использованы ограниченные диапазоны **ранее приложенного пользователем**
архива (2), `original-analysis/full-intel-disassembly.asm`. Старые реализации
из этого архива не переносились. Полный дамп и оригинальные бинарники не
включены в выдачу; в проект добавлены четыре адресных фрагмента, 258 строк.

Метаданные предоставленных экспортов указывают оригинальный ELF
`Torchlight.bin.x86_64` с SHA-256:

```text
91b41ae9dfea30aab6bc14dbbfcceaee096d600f39635b8507f5a88b5d41724b
```

Самого ELF здесь нет, поэтому этот хеш независимо не пересчитан.

Прослеженная цепочка:

```text
CGameClient::performWarp @0x58d110
  0x58d39f–0x58d3ba: вычисление обычного режима входа
  0x58d562–0x58d571: передача режима в loadLevel
CGameClient::loadLevel @0x585770
  0x585791: сохранение r9d
  0x5860b3–0x5860bf: передача в loadRoomLayout
CLevel::loadRoomLayout @0x95f150
  0x95f169: сохранение режима
  0x960910–0x96095c: ветвь выбора в режиме 0
  0x9609c0–0x960a19: ветвь режима 1 или ещё незаданной точки
  0x960ae3–0x960b25: запоминание запасной точки
  0x960cb1–0x960d1b: применение запаса при отсутствии основной точки
```

Условия этих блоков — `original-code`. Имена узлов для соответствующих
ветвей — `inferred`, по Ghidra и таблице имён. Минимальная оставшаяся проверка:
ячейки 1, 4, 5 таблицы по адресу 0xfd6ad0 должны указывать соответственно на
0x960ad8, 0x9609c0, 0x960910.

Для этого добавлен read-only скрипт:

```bash
python3 tests/verify_original_entry_dispatch.py \
  --original /path/to/Torchlight.bin.x86_64
```

Он сначала проверяет SHA-256, затем читает виртуальные адреса через ELF
PT_LOAD и проверяет три записи, не запуская игру. CTest регистрирует его как
`original_level_entry_dispatch` при заданном `TORCHLIGHT_ORIGINAL`.
Пока он не прошёл на закреплённом ELF, статус inferred снимать нельзя. При
ошибке нужно проверить таблицу и привязку ветвей, а не ослаблять тест.

Полные ссылки на текущий код и исследованные диапазоны приведены в
`research/level-entry-fallback.md` самого проекта.

В sanitizer-сборке включена проверка утечек; исполняемые файлы собраны с

Дополнительная Clang 17-сборка остановилась на существующем предупреждении в
`src/adm_document.cpp:39`, превращённом в ошибку через `-Werror`
(`-Wtautological-constant-out-of-range-compare`). Этот файл не менялся и
предупреждение не подавлялось ради патча. Успешный sanitizer-прогон выполнен
GCC. Логи неуспешной Clang-попытки также сохранены.

### Ограниченное исполнение инструкций

`reproductions/compare_instruction_slices.py` создаёт синтетические ABI-обёртки
и исполняет неизменённые байты четырёх небольших блоков: определение режима,
две ветви выбора и финальное копирование запасной позиции. Затем сравнивает
их с текущим переносимым resolver через C++-обёртку. Нужны Linux x86-64,
Python 3 и C/C++ toolchain.

```bash
python3 /path/to/companion/reproductions/compare_instruction_slices.py \
  --source /path/to/OpenTorchlight \
  --build /path/to/OpenTorchlight/build-portable \
  --work /tmp/opentorchlight-entry-instruction-check
```

Внешний обход узлов и захват последнего Player Start моделируются;
соответствие типов адресам inferred. Это не запуск целого loadRoomLayout,
не чтение оригинальной таблицы switch, не OGRE, не загрузка уровня и не игра.

## Применение

Патч предназначен для чистого содержимого именно архива (5), а не произвольной
текущей ветки GitHub. В корне соответствующего проекта:

```bash
git apply --check /path/to/OpenTorchlight-entry-fallback.patch
git apply /path/to/OpenTorchlight-entry-fallback.patch
bash tools/check.sh --portable
```

Когда установлен оригинал:

```bash
bash tools/check.sh /path/to/Torchlight/game
```

Обычная полная проверка включает новый read-only тест таблицы. Здесь её
результат не заявляется.

В `OpenTorchlight-gpt-pro-5-patched.zip` патч уже применён. Повторно накладывать
его на этот архив не нужно. Portable-режим использует отдельный build-portable
и не перезаписывает cache обычной конфигурации с оригиналом.

## Что не проверено и не исправлялось

Графический `torchlight_desktop` не собран и не запущен: development-зависимости
Wayland/EGL/GLES недоступны. Его вызывающий код изменён, но core-тесты не
подтверждают его компиляцию или поведение графического сеанса.

Оригинальные ELF, pak.zip и игровые ресурсы отсутствуют. Заявленные автором
пакета 37 проверок с оригиналом не повторялись. Совпадение порядка объектов
портового разворачивания layout с обходом всех реальных сцен ещё не проверено.

Межданжевые порталы, waypoint, физическое dropToGround, сохранение HP и
экипировки, AI-cooldown, другие фазы игрового обновления и дополнительные
ветви переопределения материалов этим патчем не восстанавливались.
