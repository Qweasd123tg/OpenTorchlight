# Максимальный этап large-6: автоматический проверочный стенд

Работай поверх `OpenTorchlight-gpt-pro-large-6.zip`. Это снова большой единый
проход: разрешено менять весь проект и реализовывать несколько связанных
подсистем. Не останавливайся после первой константы, функции или узкого патча.
Если одна граница заблокирована, зафиксируй минимально недостающие адреса и
продолжай следующую независимую часть.

Главная цель этапа — убрать ручной запуск игры как обязательный критерий
приёмки. Стенд должен сам исполнять сценарии, измерять состояния и сравнивать
их с оригиналом. Это приоритет выше новой игровой механики; если стенд уже
доведён до воспроизводимой границы, продолжай остаток игры по реестру.

Сначала прочитай `AGENTS.md`, `README.md`, `NEXT_CHECKS.md`,
`FRONTEND_CAMPAIGN_RESULT_RU.md`, `research/frontend-save-evidence.md`,
`research/checkpoint-format.md`, `research/remaining-work-inventory.md`,
`research/reviews/2026-09-15-gpt-pro-verification-plan.md` (полное внешнее
предложение, из которого выросло это задание), `tools/check.sh`,
`CMakeLists.txt`, `tests/` и относящиеся классы `research/decompiled-core/`.

## Три утверждения, которые нельзя смешивать

1. **«Обработали настоящие ресурсы»** — загрузчик открыл и разобрал реальные
   данные без тихой подмены.
2. **«Сценарий проходит»** — цепочка подсистем доводит состояние до конца.
3. **«Поведение совпадает с оригиналом»** — есть сравнение с ELF, оригинальной
   библиотекой или закреплённой трассой.

Собственный кадр/дамп порта может быть только регрессионным эталоном. Он не
доказывает правильность, пока не подтверждён независимым расчётом. Пропущенная
обязательная проверка — это «не выполнено», а не зелёный результат.

## Приоритет 1: независимые группы проверок

Сейчас ресурсные и рендер-проверки связаны с лишними зависимостями. Исправь это
в `CMakeLists.txt` и `tools/check.sh`, не ослабляя существующие тесты.

1. Введи отдельный кеш-параметр `TORCHLIGHT_GAME_DIR` (PATH к каталогу с
   `pak.zip`), независимый от `TORCHLIGHT_ORIGINAL`. Если ELF задан, а каталог
   пуст, каталог можно вывести из пути ELF; обратное не должно требоваться.
2. Перенеси регистрацию тестов, которым нужен только `pak.zip`
   (`original_pak_archive`, `original_collision_meshes`, `original_adm_document`,
   `original_master_resource_index`, `original_unit_definitions`,
   `original_level_scene`, `original_logic_runtime`, `original_random_levels`,
   `original_players`, `original_ogre_meshes`, `original_ogre_materials`,
   `original_ogre_skeletons`, `original_animation_manifests`,
   `original_skeletal_animation`, `original_dds_textures`,
   `original_png_textures`, `original_scene_geometry`, `original_spawn_classes`,
   `original_entity_world`, `original_equipment`, `original_enemy_ai`,
   `original_unit_types`, `original_combat`, `original_level_transitions`,
   `original_item_cycle`, `original_frontend_checkpoint`,
   `original_data_bootstrap`) в блок, включаемый при заданном
   `TORCHLIGHT_GAME_DIR`. Поведенческие сравнения с ELF
   (`original_*_comparison`, `original_level_entry_dispatch`) остаются под
   `TORCHLIGHT_ORIGINAL`.
3. Раздели графические цели: `torchlight_gles2` (renderer) должен собираться при
   наличии EGL+GLES2 без Wayland/xdg-shell; Wayland и `xdg-shell` нужны только
   для `torchlight_desktop`. Тесты `gles_render_smoke`, `ogre_mesh_render`,
   `scene_geometry_render` не должны зависеть от Wayland и должны запускаться
   с `EGL_PLATFORM=surfaceless`. Рендер-тесты, которым нужен pak, остаются
   зависимыми и от `TORCHLIGHT_GAME_DIR`.
4. Расставь CTest-метки `core`, `assets`, `reference`, `render`, `desktop`
   (`set_tests_properties(... PROPERTIES LABELS ...)`) и задокументируй группы.
5. Перепиши `tools/check.sh`: режимы `--portable`/`--core`, `--assets DIR`,
   `--reference ELF`, `--render`, `--desktop`, полный режим с обоими входами.
   Скрипт обязан печатать итоговую таблицу «группа → выполнено/пропущено/
   провалено» и возвращать ненулевой код, если запрошенная группа не может
   выполниться. Не допускай сценария, при котором отсутствие pak или ELF даёт
   зелёный итог.
6. Сохрани текущие 28/28 portable и общее число зарегистрированных тестов.
   Перенос регистрации в группы не должен уменьшать покрытие полного режима.

## Приоритет 2: один игровой цикл для окна и сценариев

`src/linux_desktop_main.cpp` (около 1920 строк) сейчас содержит единственную
реализацию запуска кампании, переходов и порядка обновления. Извлеки общий
компонент, не переписывая проект целиком.

1. Вынеси игровой цикл и владение подсистемами (frontend, `PlayerSession`,
   загрузка этажа, world/logic/AI, ввод, камера, renderer) в переносимый
   компонент. Оконный `main` должен остаться тонким адаптером: окно, системные
   события, EGL/GLES-контекст, реальное время.
2. Введи инъекцию ввода, времени и RNG. Автоматический сценарий использует тот
   же компонент с очередью команд и управляемым временем. Ожидания — по
   событиям с таймаутом, а не `sleep`.
3. Сценарий уровня меню обязан идти через настоящий обработчик команды
   (`New Game`, `Load`, `Continue`, `Save`, выход), а не подменяться прямым
   созданием `PlayerSession`. Прямая сборка состояния допустима только там, где
   тест явно проверяет ядро, и это должно быть видно в отчёте теста.
4. Фиксированный шаг теста помечай `prototype` и не выдавай за восстановленный
   scheduler оригинала. В сравнительных сценариях с RNG фиксируй порядок
   значимых обращений к случайности, а не только seed.
5. Добавь сквозной сценарий в отдельных процессах: меню → New Game → Town →
   ходьба → смена предмета/экипировки → save → завершение → новый процесс →
   Continue → те же семантика состояния и допустимая позиция. Второй сценарий:
   вход в данж → возврат → повторная загрузка.

## Приоритет 3: настоящие ресурсы как проверочные сцены

1. Построй машинно читаемый каталог зависимостей ресурсов: `UNIT` → `BASEFILE`
   → модель → skeleton → animation manifest → атакующие клипы → материалы →
   текстуры → эффекты; аналогично комнаты/layout/логика, предметы, интерфейс.
   Для каждой зависимости различай: найдена и поддержана, отсутствует,
   повреждена, существует но не поддержана. Тихий fallback запрещён — он должен
   быть видимым состоянием.
2. Первый обязательный набор: Town, один тип данжа, все три класса, несколько
   существенно разных комплектов экипировки. Цепочки:
   - персонаж: загрузка → skeleton → выбранный клип → поза → attachment оружия
     → `HIT` → изменение состояния цели;
   - комната: раскрытие layout → преобразования → collision → перемещение →
     trigger → переход → правильная точка прибытия;
   - предмет: ресурс → рассчитанный экземпляр → подбор → смена слота →
     сохранение → загрузка без изменения характеристик.
3. Сохрани искусственные фикстуры для точных границ (например, вертикальная
   тонкая стенка между центрами клеток из `NEXT_CHECKS.md`). Реальные ресурсы
   проверяют совместимость с игрой, фикстуры — границы алгоритма.

## Приоритет 4: полноценный headless-рендер и численные дампы

1. Расширь `scene_geometry_render_test` и `gles_ui_headless` до общей сцены с
   рендером в память, а не только проверкой «достаточно цветных пикселей».
   Первый полноценный кадр — городская сцена с фиксированной камерой.
2. Введи три уровня машинных результатов: до отрисовки (матрицы камеры, мира,
   костей, положение оружия, назначенные материалы, свет), во время подготовки
   (текстуры, blend/depth/cull, порядок проходов), после (RGBA8, при
   необходимости depth и маска объекта). Формат — стабильный текстовый/бинарный
   дамп, пригодный для точного diff.
3. Реализуй сравнение с эталоном и отчёт о первом расхождении. Источники
   эталона: расчёт оригинальной библиотеки/формулы (предпочтительно),
   закреплённая трасса оригинала, и только затем собственный кадр как
   regression после независимого подтверждения.
4. Не вводи порог «похоже на 99 %» на весь экран. Для важных объектов —
   отдельные проверки видимости/положения; для чисел — точное совпадение или
   обоснованный допуск с измеренной повторяемостью. Допуск нельзя поднимать
   ради зелёного теста.

## Приоритет 5: ограниченные эталонные трассы оригинала

1. Расширяй существующий способ изолированного исполнения (слайсы ASM с SHA и
   `*_probe`), а не начинай заново. Допустим GDB Python для коротких сценариев
   состояний, но привязка к SHA-256 ELF обязательна.
2. Первые сценарии: одна атака до `HIT`, один переход между этажами, одно
   переключение UI ↔ мир. Снимай выбранное описание атаки, клип, скорость,
   время события, HP, cooldown и порядок значимых вызовов. Указатели не
   записывай как устойчивые ID.
3. Трассы сохраняй как проверочные данные. Тест порта сравнивается с трассой
   без повторного запуска оригинала. Новый захват — только при изменении
   сценария или версии ELF.
4. `.otc` не сравнивай побайтово с оригинальными сохранениями: сравнивай
   семантику состояния (класс, имя, этаж, HP/mana/gold, экземпляры и слоты).

## Приоритет 6: автоматический оконный прогон

1. Подготовь изолированный headless-прогон `torchlight_desktop`
   (headless-бэкенд Weston или минимальный тестовый compositor) и закреплённую
   доставку синтетического ввода. Не управляй рабочим столом пользователя и не
   трогай его сессию.
2. Сценарий: меню → создание героя → Town → resize → пауза → возврат →
   сохранение → закрытие → новый процесс → Continue. Дополнительно: ошибочный
   файл сохранения и ошибка записи.
3. Проверяй ожидаемые состояния приложения и контрольные кадры, а не только
   отсутствие падения. Программный renderer не доказывает производительность на
   реальной видеокарте — это отдельная граница.

## Правила исследования и реализации

1. Сначала ресурсы, символы, RTTI, функции и адреса оригинала, затем код.
2. Каждое существенное утверждение помечай `original-code`,
   `resource-derived`, `library-derived`, `inferred` или `prototype`.
3. Сначала минимальный дамп/чистая функция/differential test, затем runtime.
4. Сравнивай числа, состояния и последовательности событий. Внешнее сходство и
   загрузочный smoke не доказывают поведение.
5. Не создавай огромную ABI-имитацию ради тесно связанной функции: выделяй
   чистые части, остаток проверяй короткой трассировкой.
6. Оригинальные ELF и ресурсы только read-only. Не включай их в результат и не
   создавай полный дамп программы; добавляй только точечные экспорты.
7. Сохраняй `-Wall -Wextra -Wpedantic -Werror`; не отключай предупреждения и не
   ослабляй прежние проверки. Не удаляй и не переименовывай существующие тесты
   без сохранения их покрытия в полном режиме.

## Проверки и результат

- Сохрани 28/28 portable и отдельный ASan/UBSan набор.
- Для каждого нового механизма добавь проверку, которая падает при его
  отключении, и явный тест «обязательная группа недоступна → NOT RUN».
- Чётко отделяй авторские fixtures от original- и asset-проверок.

Верни **один авторитетный полный ZIP** проекта, cumulative patch к `large-6` и
подробный русский отчёт. Не возвращай несколько конкурирующих `patched/fix`
архивов. В ZIP не должно быть ELF, `pak.zip`, `build/`, собранных бинарников
или полного дампа. Если всё не помещается в один проход, сделай максимально
большой законченный участок и продолжи по приоритетам, а не растягивай один
scalar-fix.
