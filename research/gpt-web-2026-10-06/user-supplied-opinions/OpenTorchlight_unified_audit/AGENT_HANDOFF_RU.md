# Задание на внедрение по единому аудиту

## Цель и границы

Сначала прочитать AGENTS.md текущего проекта и REPORT_RU.md этого пакета. Работать только в действующем decomp-треке, сохраняя оригинальные TU, C++98, классы/layout, закреплённые библиотеки и флаги GCC 4.4.7. Архивные сведения не считать состоянием всех текущих веток. Никаких новых gameplay-правил, заглушек, собственного runtime, p-code-эмулятора, ручного четырёхстадийного реестра или скрытого обращения к LLM.

Это инженерное задание, а не сообщение, что перечисленные доработки уже сделаны. Четыре patch-файла являются узкими опциональными изменениями, остальные пункты требуют реализации в текущем проекте.

## Сначала проверить исходное состояние

Зафиксировать commit/worktree, original ELF hash, реальный compiler, конфигурацию, актуальные тесты и метрики. Сверить действующий код с reviewed fingerprints из results/reference_source_fingerprints.json. Изменённые участки анализировать заново; непрохождение архивного repro может означать уже выполненное исправление. Не вносить старые патчи повторно. Сохранить исходные функции/данные и использовать временные рабочие копии.

## Надёжная приёмка и публикация

Исправить zero-selected selftest, наследование фильтра полной проверки и игнорирование кода процесса. Обновить учёт реально выбранных/выполненных тестов и association к проверяемым оригинальным адресам. Не засчитывать объявление TL_ORIGINAL само по себе как факт исполнения.

При mutation run сохранять fingerprint того baseline, который испытывался. Fingerprint должен связывать source/object, resolved includes, compiler/options, tests/capture, mutator и original ELF. Record обязан проверить текущую идентичность, а не записать свежий digest рядом со старой статистикой. Старый формат без baseline оставить историческим до повторной проверки.

Перенести trial source и header promotion в staging. Не допускать, чтобы непроверенный кандидат оказался в деcomp/src и был подобран другим hybrid build. Финальная публикация должна включать исходник, заголовки и соответствующий результат проверки как одну согласованную операцию. После promotion пересобрать реальный TU без временных includes/послаблений; сравнить фактический объект и заново подтвердить тесты, если код изменился. DIFF→DIFF не означает неизменность реализации.

Исправить literal truncation и учёт существенных EH/data dependencies в нормализаторе. До полной поддержки таких случаев не повышать неполное совпадение до безусловного доказательства. Capture должен сохранять необходимую идентичность объектов и выдавать явную ошибку при переполнении, а не сравнивать усечённый prefix.

## Входы, типы и кэш

Повторить критические регрессии converter: direct/virtual, return x!=false, литералы со словом byte, cv, overload, namespace collision. Исправлять реальную цепочку convert, а не отдельный helper, который тест проходит изолированно.

Исправить fresh для timeout/missing body, dependent prototype invalidation, актуальность types export и shared io между workers. Развести job outputs/logs; отдельно установить корректную политику доступа к Ghidra project. Перечитать правила Ghidra cache/flush при обновлении типов.

Сохранить полные type names, размеры, квалификаторы, все нужные vtable groups и сигнатуры слотов. ABI агрегатов проверять точным compiler, не только размером структуры. Сигнатуры библиотечных imports брать из закреплённых источников; модифицированные версии не подменять соседними релизами.

Исправить cache invalidation при появлении нового более приоритетного заголовка. Include resolution, порядок путей и фактические preprocess inputs должны входить в идентичность результата. Norm cache не должен зависеть лишь от mtime. Оптимизация сравнения через section index допустима после regression checks, но не решает смысловые ошибки normalizer.

## Общий детерминированный кандидатный процесс

Вынести из существующих инструментов общий путь получения, компиляции, сравнения, тестирования и публикации кандидата. Существующие properties/descriptors/name_tables/ghidra_cpp должны быть providers, а не отдельными несовместимыми потоками записи. В безмодельном режиме Model.ask и внешние model/network fallbacks должны завершаться явной ошибкой: ни один не должен вызываться скрыто.

Очередь строить по актуальной разности ожидаемых оригинальных функций и свежих принятых реализаций внутри TU. Не исключать весь TU из-за существования .cpp или большого размера. Владение, полноценный контекст компиляции и атомарная публикация остаются на исходном TU. Общие headers должны синхронизироваться и инвалидировать зависимые задания.

Повторный провал без изменения входов кэшировать как unresolved, а не бесконечно перегенерировать. В результате должна быть точная причина: отсутствующая сигнатура, конфликт layout, нераспознанная операция, неизвестный эффект вызова, неготовый тестовый state. Нельзя заполнять это придуманных поведением.

## Первый измеряемый результат генерации

Выбрать по текущему progress незавершённую крупную семью. Архивный кандидат — Merchant/Stash setPetSlotIcon, но его текущая завершённость неизвестна. Цель: один подтверждённый donor, восстановление точной delta и автоматическое получение второй реализации с финальной приёмкой. Если семья уже готова, взять аналогичную, а не считать повтор её восстановления новым прогрессом.

После этого подключать по наблюдаемым причинам отказов: CEGUI подписки с полным владением, GetDataValue с сохранением defaults/порядка, операции TArrayList, byte-provenance копирования/очистки, математические операции из точного OGRE. Прототипы из пакета — материал для адаптации; их успешные synthetic tests не заменяют исходный ELF и контекст класса.

Структурированные данные получать из Ghidra HighFunction, сохраняя адреса, типы, ветви, исключения и memory dependencies. Не строить сначала общий декомпилятор или универсальный e-graph. Углублять только представления, которые нужны выбранным семействам.

## Проверки готовности

Негативные тесты: ноль выбранных тестов; авария после успешной строки stats; старый mutation report с новым code; header shadowing; DIFF→DIFF после promotion; interruption до commit; конфликт двух io jobs; исчезнувший raw body; долгий string literal; различный catch type; разные external pointers; capture overflow; неоднозначная перегрузка; изменение default; container count/capacity и переполнение; отказ выделения/чтения.

Каждому негативному тесту нужен положительный контроль. Исправление не должно просто запрещать всё. Для генерации учитывать compiler context и точную модель наблюдения. При UNKNOWN не публиковать source.

Метрики: новые уникальные accepted original bytes/functions; доля кандидатов, дошедшая до финальной приёмки без ручной записи; количество ручных исправлений; полное время по стадиям; повторная работа после изменений. Копии, пересечения семейств, thunks и старые уже принятые методы не считать новым выигрышем.

## Остаток самостоятельной сборки

Строить машинный отчёт из реальных link/import/redirect данных: какие игровые функции, globals, tables, vtables, RTTI, constructors/destructors и runtime objects ещё поставляет оригинал. Отдельно проверять data/init closure. Не возобновлять старый runtime для получения формально линкованного executable. Успех гибрида не равен автономной игре.

## Отчёт после реализации

Указать конкретные изменённые файлы, выполненные команды, тесты/ограничения, новые принятые реализации и end-to-end измерение. Разделить исправления безопасности, ускорение отдельных утилит и сокращение ручного восстановления. Не обещать множитель всего проекта на основании synthetic benchmark.
