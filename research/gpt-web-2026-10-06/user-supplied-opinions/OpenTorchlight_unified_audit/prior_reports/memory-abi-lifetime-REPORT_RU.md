# Проход 8: дополнительные этапы автоматического восстановления без LLM

## Главный результат

Разработаны и выполнены отдельные прототипы: калибровка физического возврата агрегатных типов компилятором; статическое восстановление блочных операций памяти; изолированная нативная проверка архивных листингов; распознавание упорядоченных математических выражений; сопоставление локальных статических объектов с guard-переменными; тесты отложенного заполнения строк и отказов выделения ресурсов.

Все 2 285 исходных файлов архива сохранены. Оригинальный ELF, GCC 4.4.7 и сама игра не запускались. Новых функций, принятых штатным конвейером, нет. Общая скорость декомпиляции не измерена.

Этот проход не предлагает заменить C++ эмулятором или вынести игру в другой runtime. Нативные листинги служат только изолированным тестовым эталоном. Автоматический генератор выдаёт обычные операции C++.

## 1. Физическое размещение агрегатов, а не только имена типов

В `research/decompiled-core/level.c:7077–7135` известная сигнатура `CLevel::passableBetween(Ogre::Vector3, Ogre::Vector3 const&, bool)` в черновике распалась на `undefined8`, отдельный `float` и указатели. Другие примеры с `in_XMM1_Da` есть в `path_controller.c`. Наличие таких фрагментов — свидетельство кандидата для анализа, не доказательство ошибки каждого текущего черновика.

`tools/decomp/types_export.py:171–203` уже определяет скрытый возврат класса. `tools/decomp/ghidra/DecompDrafts.java:207–273` применяет прототипы: неподдержанные объектные параметры оставляет Ghidra; в специальном пути скрытого возврата распределяет скаляры, но отказывается от некоторых больших и стековых аргументов. Поэтому предложение не состоит в повторном добавлении sret.

Дополнительный этап: компилировать небольшие пробы с точными классами, сигнатурами и флагами, извлекать расположение частей параметров и результата, проверять его на границах оригинальных вызовов и передавать подтверждённые сведения в декомпилятор.

Проверены шесть возвратов (`results/abi-probe.json`):

| Тип | Размер | Наблюдение |
|---|---:|---|
| Ogre::Vector3 | 12 | первые два float в младших 64 битах XMM0; третий в младших 32 битах XMM1 |
| Ogre::Quaternion | 16 | две части по 64 бита в XMM0 и XMM1 |
| Mixed: uint64 + double | 16 | RAX и младшие 64 бита XMM0 |
| Big: три double | 24 | скрытое место результата через RDI; исходный указатель в RSI; RAX возвращает адрес результата |
| Нетривиальный Small | 8 | скрытое место результата, несмотря на размер 8 |
| std::wstring со старым ABI | 8 | скрытое место результата |

Использованы реальные заголовки OGRE из архива, но современный GCC. Автоматического полного ABI-классификатора и импорта этих проб в Ghidra пока нет. Аргументная проба `take_v3` сохранена в ассемблере для исследования; шесть успешных исполняемых проверок относятся к возвратам.

Историческая выборка: 196 функций с регистровыми фрагментами, суммарный размер их тел 415 656 байт. Это не доля кода, которую гарантированно устраняет этап. Категории пересекаются; завершённость на ПК пользователя неизвестна.

Первичные источники: Itanium ABI, разделы 3.1 и 3.1.3; Ghidra Function.setReturn / setCustomVariableStorage и VariableStorage.

- https://itanium-cxx-abi.github.io/cxx-abi/abi.html
- https://ghidra.re/ghidra_docs/api/ghidra/program/model/listing/Function.html
- https://ghidra.re/ghidra_docs/api/ghidra/program/model/listing/VariableStorage.html

## 2. Статическое восстановление операций памяти

Вход прототипа — `research/disassembly/91a980.asm`, `CKeyManager::capture()`, адрес 0x91a980, размер по архивным символам 0x119. Листинг содержит 54 инструкции: разрозненные загрузки и записи на 1, 2, 4 байта, LEA, REP MOVSQ и REP STOS.

`tools/memory_transfers.py` не ищет заранее записанные смещения этой функции. Он статически отслеживает происхождение каждого байта и частичные изменения регистров в узком поддержанном подмножестве инструкций. Затем объединяет смежные записи, проверяет непересечение копируемых диапазонов и отсутствие устаревшего источника после промежуточной записи.

Результат `results/native/generated_capture.cpp`:

```cpp
std::memcpy(object + 0x11,  object + 0x711, 512);
std::memcpy(object + 0x411, object + 0xb11, 512);
std::memcpy(object + 0x211, object + 0x911, 512);
std::memset(object + 0x711, 0, 512);
std::memset(object + 0xb11, 0, 512);
```

Из 2 560 побайтовых записей получено пять операций. Символьные карты конечного происхождения байтов модели инструкций и сгенерированных операций совпадают. Это условное равенство внутри написанной модели, а не автоматически проверенное доказательство всей x86-семантики.

Предусловия: доступная обычная память объекта, DF=0 на входе ABI, отсутствие гонок/volatile-наблюдений и ошибок обращения к памяти. Неизвестная инструкция, неизвестный адрес, указатель в записываемых данных, перекрытие и устаревший источник блокируют генерацию. Не делается вывод, что любой набор записей конструктора можно заменить memset: в нём могут быть виртуальные таблицы, нетривиальные объекты и побочные эффекты.

Важная проверка новизны: соответствующая реализация уже есть в `decomp/src/keymanager.cpp:5–15`. Инструмент её не читает; он автоматически повторно получает тот же набор операций по листингу. Это проверочный пример генератора, НЕ новая завершённая функция. Исходные имена полей не восстановлены; сохранены технические смещения.

Этап полезен для развёрнутых копирований, нулевой инициализации простых буферов и константных участков; для структур классов он даёт свидетельства о границах диапазонов, но не право самостоятельно менять layout.

## 3. Изолированные нативные эталоны

`tools/native_capsule.py` пересобирает пять выбранных полных листингов. Разрешены только исследованные операции без внешних вызовов, RIP-зависимостей, внешних/косвенных переходов. Внутренние переходы получают локальные метки. `.org` сохраняет позиции инструкций; более длинная кодировка вызывает ошибку сборки. Это не защитная песочница для произвольных входов.

Источники:
- `research/disassembly/91a980.asm`: CKeyManager::capture, 281 байт;
- `research/disassembly/91a680.asm`: CKeyManager::keyHeld, 27 байт;
- `research/disassembly/CRandomizer.txt`: getOdds, 45 байт; setChoiceOdds, 119; removeChoice, 162.

Размеры пересобранных функций совпали с указанными размерами. Хеши исходных текстов и строки инструкций записаны в `results/native/native-capsules.json`; повторный дизассемблер — `results/native-disassembled.txt`.

Эталон — пересобранный текст архивных инструкций. Оригинальные байты ELF независимо не проверялись. Это существенно слабее проверки непосредственно загруженного оригинала; никакой новый штатный статус MATCH не присваивается.

На синтетических, полностью выделенных состояниях выполнены сравнения (`results/native-probe.json`):

| Метод | Случаев | Расхождения |
|---|---:|---:|
| capture, автоматически сгенерированный C++ | 4 096 | 0 |
| keyHeld, кандидат явного сравнения с единицей | 8 192 | 0 |
| getOdds | 20 000 | 0 |
| setChoiceOdds | 20 000 | 0 |
| removeChoice | 20 000 | 0 |

Всего 72 288 случаев. Для capture сравнивались все 4 096 байт входного буфера после вызова, а не только ожидаемые поля. В CRandomizer сравнивались состояние и все три подложки массивов; различие физических адресов нормализовано. Половина случаев соблюдает count<=capacity для каждого списка; другая половина намеренно включает более широкие состояния, но подложка всегда выделена на восемь элементов. Достижимость этих расширенных состояний в игре не утверждается. Для преобразования float→int используются только представимые конечные значения.

Три варианта с внесённой ошибкой отличились: лишняя очистка текущего удержания — 4 096; замена `==1` на ненулевое значение — 4 096; установка dirty при отсутствии выбора — 7 930.

Только capture сгенерирован анализатором. Остальные короткие кандидаты написаны по листингу для проверки механизма эталонов. Методы Randomizer уже существуют в `decomp/src/randomizer.cpp`, что также не выдаётся за новое восстановление.

Для развития этапа на ПК с ELF нужно извлекать оригинальные байты и замыкание реальных зависимостей: данные, релокации, известные вызываемые методы, исключения/TLS при наличии. Незамкнутые функции оставлять на существующей hybrid-проверке, а не подменять неизвестные вызовы заглушками. Нативный код остаётся только в тестовой части.

Первичный пример готовой инфраструктуры: DDisasm восстанавливает пересобираемый ассемблер через GTIRB. Он не установлен и не запускался здесь; ссылка подтверждает существование направления, не пригодность без проверки для игры.
https://www.grammatech.com/ddisasm/

## 4. Упорядоченная математика OGRE вместо произвольной алгебры

`OgreVector3.h:353` содержит squaredLength; `:428–440` — normalise с порогом `1e-08`. `tools/math_shapes.py` принимает только упорядоченную сумму трёх квадратов известных float-переменных. Перестановки, неизвестные типы, вызовы и другая структура выражения не принимаются.

В архивной лексической выборке 43 места в 25 функциях. Пока не установлены происхождение всех компонентов, alias/volatile-свойства и точные исходные инструкции, поэтому это кандидаты, не 43 безопасно заменённых участка.

Выполнено 12 000 троек битовых float-входов с реальными заголовками закреплённого OGRE: в том числе все 2 744 сочетания набора из 14 специальных шаблонов. Сравнивались биты результата/компонентов, флаги FP и errno в текущем окружении. У squaredLength и normalise расхождений нет. Замена порога на строго больше нуля дала 484 расхождения.

Проверка перестановки сложений: `(1e20f + -1e20f) + 1.0f` дала 1; `1e20f + (-1e20f + 1.0f)` — 0. Следовательно, источник из точной версии библиотеки полезнее произвольного «математически равного» упрощения.

Это не доказательство для всех float и не сравнение с оригинальным кодом игры. Использованы GCC 14.2, `-ffp-contract=off`, отсутствие fast-math; режимы округления целиком не перебирались.

Следующий пилот: связывать типизированные компоненты и выражения в графе, предлагать точную операцию закреплённой библиотеки и проверять весь окружающий метод. Не применять допуск сравнения там, где пользователь требует исходного поведения.

Первичный источник о влиянии настроек оптимизации на floating-point: GCC 4.4.7 Optimize Options.
https://gcc.gnu.org/onlinedocs/gcc-4.4.7/gcc/Optimize-Options.html

## 5. Восстановление ленивых локальных объектов

`research/decompiled-core/inventory_menu.c:3305–3330` показывает guard-инициализацию `CInventoryMenu::update(float)::g_GP`, а затем отдельную проверку пустоты и загрузку перевода. Guard и строка имеют разные адреса, хотя декомпилятор печатает похожее имя.

`tools/static_guards.py` сопоставляет полные имена из `original-symbols.txt`. Всего в полной таблице символов 281 guard, 277 печатных идентичностей, 272 однозначные пары с объектами. Это включает не только пользовательский игровой код. Пять идентичностей блокируются: четыре имеют дубликаты, одна не имеет найденного объекта.

Для g_GP таблица различает guard по адресу 21787456 и строковый объект 21787464 (десятичная запись). Исходные строки символов — 27701 и 27702.

Предлагаемый высокоуровневый кандидат:
```cpp
static std::wstring value;
if (value.empty())
    value = obtainTranslation();
```
Это только иллюстрация формы. Аргументы obtainTranslation в этом фрагменте не восстановлены, поэтому готовое определение метода не генерируется. Существенно, что инициализация пустого объекта и заполнение перевода разделены. Вариант `static std::wstring value = obtainTranslation();` может перестать повторять попытку после пустого результата.

Синтетическая модель проверила 256 последовательностей по четыре обращения. Ответы провайдера: пустая строка, A, B или исключение. У сохранённого ленивого заполнения расхождений нет; вариант заполнения только при первой инициализации отличается в 84 последовательностях. Это модель последовательного исполнения, не оригинальные переводы/конкурентный доступ.

В историческом псевдокоде guard-пути есть в 33 функциях с суммарным размером тел 272 267 байт. Это не объём полностью устранимого кода.

ABI содержит правила guard acquire/release/abort, регистрации уничтожения и повторной попытки после неуспешной инициализации. В рабочем анализе нужны реальные связи guard/object/initializer/dtor и путь abort, а не удаление всех служебных вызовов регулярным выражением.
https://itanium-cxx-abi.github.io/cxx-abi/abi.html

## 6. Уточнение множества возможных динамических типов

Дополнительное направление, пока без реализованного межпроцедурного решателя: хранить не только статический тип указателя, но и проверенные варианты фактического объекта в конкретной точке.

В выборке найдено 150 вызовов __dynamic_cast в 83 функциях; в 92 текстовых случаях получены кандидаты source/destination typeinfo. Разрешение неполных имён и подтверждение ABI пока не выполнены. Примеры: `animation_player.c:1903` — CBaseUnit→CCharacter; `character.c:18823` — CBaseUnit→CEquipment.

Новый этап должен связывать выделение памяти, конструктор, установку vptr, сохранение в поле, передачи параметров и успешные ветви dynamic_cast. На схождении путей сохраняется объединение вариантов; после неизвестного изменения соответствующей памяти информация ослабляется. Успешное приведение к базовому классу не означает точный конечный тип: производные сохраняются. Трасса одного запуска также не доказывает единственность типа.

Результат полезен для уменьшения множества возможных целей виртуального вызова и зависимостей анализа. Он не даёт права без доказательства заменить виртуальный вызов прямым в итоговом C++.

SVF предоставляет field-/flow-/context-sensitive pointer analysis и итеративный value-flow analysis. Вход — LLVM IR; это не готовый подключаемый анализатор ELF/Ghidra для Torchlight.
https://svf-tools.github.io/SVF/

## 7. Генерировать испытания отказов, а не надеяться на случайность

Предлагаемый дополнительный этап проверки: из обычного успешного пути последовательно вызывать контролируемый отказ в выбранной операции выделения памяти или внешнего ввода. Сравнивать не только return, но и тип исключения, завершённые побочные эффекты, уничтожение объектов и остаточные ресурсы.

Синтетический пример создаёт четыре ресурса. Проверены успех и отказ при каждом из четырёх выделений — пять сценариев. Кандидат на RAII совпадает с явной очисткой по результату, полному журналу и числу живых ресурсов. Вариант с утечкой первого ресурса при более позднем отказе обнаружен в трёх сценариях. Проверка только возвращаемого значения не нашла ни одного различия.

Это не fault-injection в Torchlight. Для оригинала необходимы одинаковая точка отказа в обеих версиях, одинаковое исходное состояние, наблюдение реальных зависимостей. Ошибки API следует подавать по соответствующей семантике: не каждый отказ обязан бросать исключение.

Историческая выборка содержит 190 функций с выбранными признаками выделения, но их 806 890 байт — суммарные тела, а не оценка устранимого кода или количество необходимых сценариев.

## Рекомендуемый ограниченный порядок

1. Использовать автоматически восстановленный capture как регрессионный тест этапа byte-provenance, затем проверять другие простые участки памяти.
2. На машине с ELF собрать оригинальные нативные тестовые эталоны для небольшой группы функций; не заменять ими штатный финальный hybrid gate.
3. Проверить физический ABI Vector3/Quaternion/нетривиальных объектов именно GCC 4.4.7; затем улучшить зависимые черновики.
4. Запустить ограниченный набор точных OGRE-операций и local-static восстановления.
5. Добавить контролируемые ошибки к существующим дифференциальным тестам.
6. Межпроцедурное уточнение динамических типов развивать отдельно, сначала на нескольких связанных классах.

Критерий полезности — дополнительный принятый C++ и уменьшение ручного остатка на фиксированной выборке, а не число найденных кандидатов или красивых строк.
