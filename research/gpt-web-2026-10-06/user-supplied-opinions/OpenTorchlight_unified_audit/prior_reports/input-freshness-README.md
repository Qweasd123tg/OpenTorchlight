# OpenTorchlight: ускорение восстановления без ЛЛМ

Проверенный вход: `OpenTorchlight-main(4)(1).zip`. Анализ выполнен 6 октября 2026 года.

## Граница проверки

Изучен действующий трек `decomp`, а не замороженные runtime/code-first/p-code направления. Исходники игры не изменялись. В архиве нет оригинального ELF и подготовленного GCC 4.4.7; полная сборка, Ghidra, сравнение с оригиналом и игровые самотесты здесь не запускались. Числа старых прогонов ниже явно отделены от новых проверок.

Цель по `AGENTS.md` и `decomp/README.md`: читаемый C++ с исходной структурой классов и единиц трансляции; поведение проверяется по оригиналу. Код эмулятора или сохранение оригинальных машинных тел не является предлагаемым конечным результатом.

## Что показывают сохранённые измерения

`decomp/README.md`, раздел «Сгенерированные заголовки и пробная сборка черновиков», описывает прогон от 3 октября: 349 MATCH дали всего около 8 КБ машинного кода. Эти числа не пересчитывались на актуальных черновиках.

Файл `research/decomp-automation-audit-2026-10-04/measured.json` перечитан отдельно: 666 крупных функций, 2 797 634 байта. Маркеры строк найдены в 506 функциях, TArrayList — в 134, деревьев — в 70, vector — в 37, неизвестного ABI — в 46. Группы пересекаются; маркер не означает, что вся функция автоматически восстанавливается. Текущие правила уже могли устранить часть отмеченных конструкций. Машиночитаемый пересчёт: `saved_snapshot_recount.json`.

Главный вывод: оптимизация количества принятых крошечных функций может почти не затронуть основную работу. Эксперименты нужно проводить на крупных функциях и измерять реально снятую работу, а не сокращение строк.

## Два конкретных пробела инвалидации

### 1. Изменение прототипа вызываемой функции из другого TU

`tools/decomp/ghidra_draft.py::draft_state` вычисляет `own` как адреса функций текущего TU и сверяет только их `prototype_digest`. Прототипы вызываемых функций из других TU в этот список не входят. Раскладки классов проверяются отдельно, но не компенсируют изменение только сигнатуры при неизменных полях.

Синтетическая проверка без ELF и GCC (`probe_draft_invalidation.py`) дала:

```
unchanged               -> fresh
callee_return_changed   -> fresh
own_return_changed      -> stale
```

Это воспроизведение ограничения ключа кэша, а не доказательство конкретного неверного черновика игры. Запуск:

```
python3 probe_draft_invalidation.py /path/to/OpenTorchlight
```

Рекомендуемое изменение: fingerprint всех используемых прототипов, включая внешние функции и разрешённые виртуальные цели. При недостаточной информации допустима консервативная более широкая инвалидация. Дополнительно сохранять версии vtable/типов вызовов и инструментария.

### 2. Проверка stale до обновления types.json

В `ghidra_draft.py::main` путь `drafts --stale` сначала вызывает `stale()`. `_types()` экспортирует типы лишь при отсутствии `types.json`. Безусловный экспорт находится позже, в `drafts(tus)`. Поэтому после изменения заголовка при существующем старом `types.json` этот путь сам по себе может не заметить новые типы и закончиться сообщением `no stale drafts`.

Это установлено чтением кода; end-to-end прогон Ghidra не выполнялся. Рекомендуемое изменение: перед выбором stale гарантировать актуальность экспорта заголовков по зависимостям.

## Ещё одна граница импорта прототипов

`elfdb.py` при построении `functions` отбирает определённые STT_FUNC внутри `.text`. `types_export.py::prototypes` строит адресное сопоставление только из этого списка. Этот конкретный путь не является полноценным импортом прототипов неопределённых внешних символов OGRE/CEGUI через PLT.

Это не утверждение, что у Ghidra отсутствуют все библиотечные типы: часть может прийти из других анализаторов. Практический эксперимент — сравнить покрытие известных импортированных символов точными прототипами из закреплённых заголовков, добавить отсутствующие в external/thunk функции Ghidra. Сведения о модифицированных Runic участках OGRE проверять отдельно.

## Предлагаемые направления

### A. Компилятор как генератор словаря шаблонов

Создать небольшой набор C++98-проб известных конструкций: TArrayList::add/removeAt/clear/find; строковые операции; конкретные специализации map/vector; new/constructor/destructor; известные подписки событий. Компилировать закреплённым GCC с исходными флагами, извлекать графы операций и связи значений. Распознавать конструкции не только как целые функции, но как фрагменты крупных функций.

Параметризовать только доказанно изменяемые части: типы, смещения, константы и цели вызовов. Совпадение формы — кандидат, не эквивалентность. Условия применения должны учитывать ширины, signedness, алиасинг, порядок эффектов, исключения и время жизни объектов. Отдельные обёртки недостаточны для полного покрытия: нужны контекстные пробы, а компилятор может переплетать соседние операции.

### B. Структурные преобразования вместо растущего набора regex

Сохранить полезные правила `ghidra_cpp.py`, но новые крупные правила реализовать над типизированным представлением графа/синтаксического дерева. Ghidra HighFunction даёт доступ к базовым блокам, p-code операциям, прототипам и переменным. Использование этого представления для анализа не требует генерации эмулятора: выходом должен оставаться обычный C++.

Первое семейство — полные операции TArrayList и обходы с повторным чтением размера после callback. `operator[]` в восстановленном заголовке проверяет capacity и возвращает элемент 0 при выходе за неё; `removeAt` переставляет последний элемент. Не заменять их обычным vector или сохраняющим порядок erase.

### C. Ограниченный перебор кандидатов

Для уже определённого смысла операции перечислять небольшое множество форм C++: if/тернарная форма, ранний return, допустимые локальные переменные, корректные перегрузки и формы конструирования. Сначала отсев по типам и эффектам, затем компиляция/сравнение, далее сильные тесты. Числовая близость DIFF не является приёмкой.

Не запускать неограниченный поиск по всей крупной функции. Не разрешать финальным вариантам UB, произвольные asm-привязки и изменения порядка эффектов. `decomp-permuter` полезен как пример идеи, но его документированные backend — MIPS/PowerPC/ARM32, а не готовая поддержка этого x86-64 C++ проекта.

### D. Генераторы декларативных участков крупных функций

Расширить доказавшийся подход descriptors на участки регистрации свойств, построения меню и чтения/записи схем данных. Генератор должен извлекать реальную последовательность операций, условия, строковые ключи, значения по умолчанию и назначения полей, затем выдавать обычный C++ в прежних TU.

Динамическая трасса одного исполнения даёт только наблюдавшийся путь, поэтому должна дополняться статическим анализом CFG. Циклы, callbacks и динамические ветви нельзя молча превращать в фиксированную таблицу.

### E. Генерация допустимых состояний для тестов

Развивать существующий fork-harness, а не делать его заново. Начинать с корректно созданных объектов и коротких последовательностей API-операций. Мутировать данные и последовательности с сохранением инвариантов. Для выживших мутантов генерировать отдельные граничные случаи; локальный symbolic execution может помогать искать такие входы, но не заменяет полную игру и её окружение.

Сравнивать не только return, но и состояние объектов/контейнеров, протокол вызовов, RNG и значимые изменения глобальных данных. Обоюдный crash не является успешным сравнением. Тестовая оценка не равна формальному доказательству.

## Минимальный проверяемый эксперимент

После обновления типов выбрать отдельные функции, не использовавшиеся при разработке правил: крупные операции TArrayList, несколько map/vector функций и один декларативный участок UI. Зафиксировать baseline текущих преобразований. Добавить одно структурное правило, не меняя другие части процесса. Сравнить число новых MATCH, силу дифференциальных тестов, ложные срабатывания, вычислительную стоимость и оставшиеся нерешённые фрагменты. Не объявлять автоматически принятыми функции только по успешной компиляции.

Кандидаты держать в `build-decomp/candidates/`, а не автоматически писать в `decomp/src`: гибрид использует находящиеся в `decomp/src` определения. Приёмка должна предшествовать автоматической публикации кандидата.

## Новые тесты этого анализа

Запуск `python3 -m unittest discover -s tools/decomp -p 'test_*.py' -v` обнаружил 26 тестов: 24 прошли, два завершились ошибкой отсутствующего GCC toolchain. Это проверки утилит, не всей игры. Два заблокированных теста относятся к `test_autotest_returns.py`. Они не объявлены пройденными и не интерпретируются как ошибки игрового кода.

## Оценка ускорения

Кратность на всём проекте не измерена. Для планирования можно использовать формулу `S = 1 / ((1-f) + f/r)`, где f — доля текущих трудозатрат, а r — ускорение автоматизируемого участка. Ни доля функций, ни доля байтов не равны f. Для условных f=0.7, r=10 результат около 2.7x; для f=0.9, r=10 — около 5.3x. Это арифметические сценарии, не прогноз проекта.

Наиболее перспективная ставка: восстанавливать повторяющиеся фрагменты внутри крупных функций и автоматически проверять результат. Автоматизация мелких функций, изменение счётчиков или переход к эмуляторным телам не решают ту же задачу.
