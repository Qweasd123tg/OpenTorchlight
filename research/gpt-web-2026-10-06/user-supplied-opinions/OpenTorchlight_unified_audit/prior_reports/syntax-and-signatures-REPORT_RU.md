# OpenTorchlight: четвёртый проход по автоматизации без LLM

Дата: 6 октября 2026 года.

## Область проверки

Источник — предоставленный архив `OpenTorchlight-main(4)(1).zip`. Исследован действующий трек `decomp`, прежде всего `tools/decomp/`. Замороженные направления ремейка, эмуляции p-code и прежних текстовых контрактов не развивались. Исходные игровые `.cpp` и заголовки не изменялись.

Проверялись настоящие Python-функции инструментов из архива и небольшие синтетические C++98-программы. Компилятор экспериментов: `g++ (Debian 14.2.0-19) 14.2.0`, Linux x86-64. Оригинальный ELF, GCC 4.4.7 и рабочая база Ghidra в этот эксперимент не входили. Игра не запускалась. Новых принятых игровых функций и измеренного ускорения полного конвейера этот отчёт не заявляет.

Главный результат: часть неопределённости и ошибок возникает не в машинном коде оригинала, а при преобразовании уже имеющейся информации. Выявлены конкретные изменяющие поведение правила, потеря идентичности методов и ограничения массовой очереди. Подготовлены воспроизводимые проверки, отдельный ограниченный патч сохранения cv-квалификаторов, прототип определения виртуальных слотов по объявлениям и прототип минимизации ошибки компиляции.

## 1. Преобразователь способен менять смысл программы

Источник: `tools/decomp/ghidra_cpp.py`. Машинные результаты: `results/probe-results.json`, разделы `direct_call`, `boolean_value`, `literal`.

### 1.1. Прямой вызов превращается в виртуальный

`call_rewrite`, строки 116–150: запись `C::m(obj, args)` переписывается как `obj->m(args)`; для `this` остаётся просто `m(args)`. Указание конкретного класса теряется. Признак исходного прямого/косвенного вызова в этом правиле не учитывается.

Проверка передаёт в настоящий `convert()` следующий черновик:

```cpp
int __thiscall CWrapper::probe(CWrapper *this, CBase *param_1)
{
    return CBase::step(param_1);
}
```

Результат инструмента:

```cpp
int CWrapper::probe(CBase* param_1)
{
    return param_1->step();
}
```

В контрольном сценарии исходный вызов известен как прямой вызов `CBase::step`; его соответствующее C++-выражение — `param_1->CBase::step()`. Метод виртуальный; базовая реализация возвращает 11, производная — 22. На объекте производного класса контроль возвращает 11, автоматически преобразованный вариант — 22. Обе программы успешно компилируются.

Это демонстрация существования ошибочного случая преобразования, а не утверждение об ошибке в конкретной уже принятой игровой функции. Правильное решение должно учитывать фактический вид вызова из ASM/p-code. Нельзя квалифицировать все вызовы подряд: настоящий виртуальный вызов должен остаться виртуальным. Конструкторы, деструкторы и поправки к `this` требуют отдельных правил.

Семантическая основа: явно квалифицированный вызов обращается к выбранной функции; неквалифицированный виртуальный вызов — к конечному переопределению динамического типа. См. первоисточник [1].

### 1.2. Сохранение истинности не означает сохранение значения

`tidy_expressions`, строка 447, без анализа контекста заменяет `x != false` на `x`.

```cpp
int normalize(int x) { return x != false; }
```

после настоящего преобразователя становится:

```cpp
int normalize(int x) { return x; }
```

Входы: `-3, 0, 2`. До преобразования получено `1 0 1`; после — `-3 0 2`.

Встроенное `!=` возвращает `bool`, который при преобразовании в `int` даёт 0 или 1 [2, 3]. Замена может сохранять выбор ветви для встроенных целочисленных условий, но не возвращаемое значение, арифметику или выбор перегрузки. Нужны ограничения по типам и контексту; при отсутствии доказательства безопаснее сохранить исходное выражение.

### 1.3. Подмена имени типа меняет текст строкового литерала

`convert`, строки 487–494, применяет удаление комментариев и таблицу `TYPES` к всему тексту. Строки не выделены в отдельные токены.

Настоящий `convert()` меняет:

```cpp
return "bad UTF-8 continuation byte";
```

на:

```cpp
return "bad UTF-8 continuation unsigned char";
```

Скомпилированные программы печатают соответственно исходный и изменённый текст. Эта исходная строка не придумана: она встречается в архивном выводе декомпилятора в трёх местах:

| Файл | Строка |
|---|---:|
| `research/decompiled-core/generic_model.c` | 10600 |
| `research/decompiled-core/path_controller.c` | 3150 |
| `research/decompiled-core/trigger_unit.c` | 4218 |

Это три найденных появления в исследовательских черновиках, не три повреждённые принятые реализации. Полный список — `archived_literal_hits` в JSON.

Существующая проверка `test_literals_are_kept_byte_for_byte` относится к отдельному `inline_temp_strings`, а не ко всему `convert()`. Поэтому её наличие не покрывает эту ошибку.

### Предлагаемая общая доработка

Сначала отделять код, комментарии, строковые и символьные литералы. Подмены типов и операторов применять только к подходящим токенам. Контекстно-зависимые упрощения выполнять на типизированном представлении; после получения синтаксически корректного C++ можно использовать AST-инструменты, например LibTooling/ASTMatchers [5]. Сырой вывод Ghidra не следует считать сразу допустимым входом Clang.

Нельзя просто спрятать все литералы на протяжении всех стадий: восстановление временных строк само использует литералы. Нужны явные границы действия каждого правила и сквозные регрессионные тесты `convert()`.

Для новых правил полезны автоматически генерируемые проверки на отрицательных числах, нулях, различающихся динамических типах, перегрузках и текстах с ключевыми словами. Это тестирование генератора на компактных контрпримерах, а не очередной слой эмуляции игры.

## 2. Идентичность метода уже известна, но теряется между инструментами

### 2.1. cv-квалификаторы записаны словами, а читаются как буква mangling

`elfdb.parse_demangled`, строки 67–114, и заполнение записи около строк 338–344 сохраняют `f['cv']` как текст, например `const`.

`headers.Gen.method_decl`, строка 276, проверяет наличие буквы `K`, поэтому известный `const` не печатается. `virtual_signature`, строка 291, использует ту же проверку и не различает соответствующие сигнатуры.

`ghidra_cpp.convert`, строка 514, при восстановлении заголовка из символа вообще не дописывает `f['cv']`.

Проверка настоящих функций: `CProbe::get() const` корректно распознаётся в elfdb, но генератор печатает `int get();`, а преобразователь — `int CProbe::get()`. Последнее не компилируется против правильного объявления `int get() const;`. Добавление одного `const` исправляет проверку.

В архивном списке сильных символов T/t классов с префиксом `C[A-Z]` найдены 32 различных адреса с cv-квалификаторами. Это не оценка невыполненной работы. Примеры — `CCharacter::animationExists(std::string const&) const` и методы `CDynamicLine`, `CGenericModel`.

### 2.2. Наличие имени принимается за наличие всех перегрузок

`headers.Gen.trial_include`, строки 581–589, проверяет `name in seen` и наличие такого имени в тексте класса; список параметров и cv не используются.

При известном исходном наборе `read(int)` и `read(double)`, но существующем заголовке только с `read(int)`, фактическое дополнение добавляет 0 объявлений. `read(double)` остаётся отсутствующим.

Синтетический вызов `read(1.5)` компилируется в обоих случаях. В неполном заголовке вызывается `read(int)` и возвращается 11; в полном — `read(double)` и возвращается 22. Следовательно, это может быть не просто ошибка компиляции, а незаметный выбор другой функции.

В той же ограниченной выборке символов найдены 123 полных имени функций с несколькими вариантами параметров/cv; конструкторы включены. Это характеристика наличия перегрузок, не число неисправных или незавершённых функций.

### 2.3. Объявление в чужой области видимости подавляет нужную функцию

`namespaces_header`, строки 606–617, ищет короткое имя метода в совокупном тексте всех рукописных заголовков.

Проверка: наличие `CNoise::parse(int)` подавляет генерацию отдельной известной `TOOLS::parse(int)`. В полученном файле нет ни нужного объявления, ни соответствующего namespace.

### Предлагаемое решение

Использовать единый ключ объявлений: полная область видимости, имя, канонические типы параметров, cv-квалификаторы и категория метода. Для связи с бинарником использовать соответствующий полный символ/адрес и отдельно обрабатывать варианты ctor/dtor. `static` и тип возврата не следует выдумывать из обычного mangled-имени: они требуют собственных подтверждённых сведений.

Нужно различать «объявлен один метод с таким именем» и «восстановлен весь требуемый набор перегрузок». При незавершённом наборе следует явно ограничивать автоматические переписывания вызовов, а не считать успешную компиляцию подтверждением правильной цели.

### Подготовленный ограниченный патч

`preserve-cv-qualifiers.patch` меняет только сохранение текстовых cv-квалификаторов в двух файлах и их использование в ключе виртуальной сигнатуры. Он НЕ исправляет преобразования вызовов/литералов, перегрузки, namespace-поиск, виртуальные слоты или очередь.

`verify_cv_patch.py` применил реальный patch во временной копии инструментов. Проверены четыре случая: без квалификатора, `const`, `volatile`, `const volatile`; объявления и определения компилируются, ключи сигнатур различны. Существующие 21 тест из модулей `test_ghidra_cpp`, `test_llm_loop_headers`, `test_mutate_overloads` проходят и на оригинале, и после патча. Это модульные тесты инструментов, не 21 проверка игры.

Результаты: `results/cv-patch-verification.json`. Применение на актуальном рабочем репозитории и целевом GCC остаётся отдельной проверкой: архив мог отстать от текущих правок.

## 3. Проверять виртуальные слоты можно по одним объявлениям

### Обнаруженное ограничение текущего сравнения

`headers.dumped_vtable` и `headers.original_vtable` сокращают записи до `Scope::method`. Аргументы перегрузок теряются. Порядок `COver::f(int), COver::f(long)` и обратный порядок превращаются в одинаковый список `COver::f, COver::f`.

Важная оговорка воспроизведения: GCC 14 печатает перед именами `(int (*)(...))`. Парсер архива воспринимает такие строки как служебные и на сыром современном дампе возвращает пустую группу, то есть отвергает обе проверки. Для изоляции потери идентичности в эксперименте удалён только этот префикс из строк имён функций. Заголовочные записи, имена и порядок не менялись. На таком форматно-совместимом представлении перестановка не обнаруживается. Реальные relocation targets объектных файлов подтверждают разный порядок `_ZN5COver1fEi` и `_ZN5COver1fEl`.

Поэтому отчёт не утверждает, что полностью необработанный GCC14-дамп был ложно принят, и не выдаёт эту проверку за запуск GCC4.4.7.

### Новый работающий прототип

`probe_member_slots.py` использует точные типы указателей на перегруженные методы:

```cpp
struct COver {
    virtual int f(int);
    virtual int f(long);
};
int (COver::*pi)(int) = &COver::f;
int (COver::*pl)(long) = &COver::f;
```

В эксперименте нет определений `f()` и нет экземпляра `COver`. Программа всё равно собирается и выводит представление указателей на методы. В стандартном варианте Itanium C++ ABI указатель на виртуальный метод кодирует `1 + смещение слота в байтах`; отдельно хранится поправка `this` [4]. Для проверенной x86-64 конфигурации размер слота — 8 байт.

| Объявления | `f(int)` | `f(long)` |
|---|---:|---:|
| Исходный порядок | encoded 1, slot 0 | encoded 9, slot 1 |
| Переставленные объявления | encoded 9, slot 1 | encoded 1, slot 0 |

`this_adjustment` во всех четырёх случаях равен 0. Запуск проверяет размер представления и ожидаемый признак виртуального указателя. Результат — `results/member-slot-results.json`.

Практическое применение: автоматически генерировать такие пробы из подтверждённых сигнатур заголовка и сопоставлять полученные слоты с известными слотами оригинального ELF. Это позволяет проверять заголовок до написания реализаций методов и без запуска игры.

Граница прототипа: он не восстанавливает неизвестную сигнатуру и не проверяет все особенности множественного/виртуального наследования, деструкторов и ковариантного возврата. Это ABI-зависимый способ, а не переносимый C++-трюк для любой платформы. На исходном GCC 4.4.7 ещё требуется проверка. Форматные различия `.class` он обходит, но сам не является готовой заменой всего текущего валидатора.

## 4. Массовые режимы не означают всю оставшуюся работу

`parallel.candidates`, строки 77–103, исключает исходную единицу трансляции, если файл `decomp/src/<name>` уже существует. Не проверяется, сколько нужных функций в нём реально определено и принято. Также исключаются TU с суммой размеров соответствующих функций больше `LARGE_TU=60000` байт. Правила owners/claims и reserved также действуют и должны сохраняться.

`draft_trial.py --all`, строки 154–157, рассматривает только TU, имени которых ещё нет среди существующих `.cpp`. Явное указание имени TU поддерживается; речь об ограничении стандартного массового режима, а не о невозможности ручной работы над файлом.

Проверка настоящего `candidates()` на изолированной синтетической базе:

| Файл | Условия | В очереди |
|---|---|---|
| `Partial.cpp` | Файл существует, нет оснований считать весь TU принятым | Нет |
| `Large.cpp` | Исходника нет, размер 60001 | Нет |
| `Small.cpp` | Исходника нет, размер 100 | Да |

### Масштаб по исторической выборке — с ограничениями

`research/decomp-automation-audit-2026-10-04/measured.json` содержит 666 функций размером от 1024 байт, суммарно 2 797 634 байта, в 193 TU.

181 из этих записей, суммарно 456 850 байт, находится в TU, для которых в присланном дереве уже есть `.cpp`. Это не говорит, какие конкретно функции в них восстановлены.

По одной этой выборке — даже без более мелких функций — восемь TU уже превышают порог 60000: `gameclient.cpp`, `character.cpp`, `Equipment.cpp`, `level.cpp`, `gameui.cpp`, `enchantmenu.cpp`, `inventorymenu.cpp`, `petmenu.cpp`.

Объединение двух описанных фильтров затрагивает расположение 348 записей выборки, или 1 404 454 байта. Это НЕ 348 свободных задач, НЕ доказанный текущий остаток и НЕ будущий прирост. Выборка историческая, а актуальные результаты других работников и свежая приёмка не получены. Данные показывают ограниченность охвата очереди, а не статус готовности этих функций.

### Предлагаемая доработка

Вычислять реальный остаток как разность ожидаемых символов исходного TU и свежих подтверждённых определений/результатов приёмки, а не по существованию имени файла. После обновления правил генератора повторять именно затронутые отсутствующие или не прошедшие проверку определения.

Единицу компиляции и интеграции сохранить прежней: исходный TU или класс. Функциональную разность использовать как автоматическое внутреннее планирование, а не создавать новый ручной реестр стадий. Большие TU можно обрабатывать ограниченными порциями в отдельной рабочей копии полного файла с сохранением компиляторного контекста. Не допускать одновременной записи несколькими работниками в один TU, не обходить чужие claims/owners и не публиковать заглушки в `decomp/src`.

## 5. Ошибки генератора можно автоматически сводить к минимальным причинам

Вместо ручного просмотра каждой длинной диагностики предлагается цикл:

```text
Неудачный черновик
→ воспроизводимый предикат конкретной ошибки
→ автоматическое сокращение входа с сохранением этой ошибки
→ группировка одинаковых причин
→ исправление общего правила
→ повтор затронутых проб + постоянный регрессионный тест
```

Выполненный прототип `probe_reduce_failure.py` — собственный простой line-deletion reducer, не запуск C-Reduce. Вход содержал 82 строки: 80 независимых объявлений и показанную ошибку `const`.

Предикат требует именно ошибку `no declaration matches ... CProbe::get()`; любой иной синтаксический сбой не засчитывается. Получено 2 строки за 34 вызова компилятора для проверок предиката, включая контрольные проверки:

```cpp
struct CProbe { int x; int get() const; };
int CProbe::get() { return x; }
```

Удаление любой из оставшихся строк уже не сохраняет нужную ошибку. Исправление `const` компилируется. Это минимальность относительно удаления одной строки, а не доказательство глобально наименьшей C++-программы. Результат: `results/reducer-results.json`.

Для полноценного сокращения C/C++ существует C-Reduce [6], который сохраняет заданное пользователем свойство входа. В этом проходе он не устанавливался и не запускался.

При минимизации расхождения поведения предикат должен требовать успешную сборку обеих сторон и прежнее различие на зафиксированном входе. Нельзя сохранять только ненулевой exit code, допускать замену ошибки случайным падением или забывать межпроцедурный контекст, который определяет исходное расхождение. Одного совпавшего текста диагностики недостаточно для окончательного признания одной причины: группировка является подсказкой для проверки общего правила.

## 6. Порядок внедрения и критерий выигрыша

Первая практическая задача — сохранить известную идентичность методов и убрать показанные изменяющие смысл переписывания. Узкий патч cv готов для отдельного просмотра; остальные изменения требуют реализации и сквозных тестов.

Вторая — проверять заголовки до массового перевода: полнота перегрузок, квалификаторы, области видимости, точные виртуальные слоты. Прототип ABI-проб уже обнаруживает перестановку без тел методов.

Третья — расширить массовую очередь на действительный остаток частично написанных и больших TU, не меняя правила владения и исходную структуру сборки.

Четвёртая — сохранять минимальные воспроизводимые ошибки генератора, чтобы одна новая ошибка не исправлялась многократно по местам применения.

Проверять эффект на фиксированной выборке реальных TU до и после изменения: количество исправленных деклараций, количество правильно выбранных целей вызовов, число проходящих проверку новых определений, процессорное время и количество необходимых ручных вмешательств. Компиляция и сокращение черновика сами по себе не означают правильную реконструкцию.

## 7. Состав пакета и воспроизведение

Требуются Python 3.10+, `g++`, `readelf`, `patch`; x86-64 Linux для ABI-пробы. Инструменты оригинального репозитория должны оставаться в версии исследованного архива для точного повторения. Проверки пишут диагностические файлы в отдельный каталог; патч применяется только во временной копии.

```bash
python3 probe_pass4.py /path/to/OpenTorchlight-main --output ./results
python3 verify_cv_patch.py /path/to/OpenTorchlight-main --output ./results
python3 probe_member_slots.py --output ./results
python3 probe_reduce_failure.py --output ./results
```

Во второй команде создаётся `preserve-cv-qualifiers.patch` рядом с каталогом `results`; команда не применяет его к переданному репозиторию. Некоторые модульные тесты Python могут создать служебный `__pycache__`; содержимое игровых и инструментальных исходников не меняется.

В ZIP включены отчёт, сценарии, патч, JSON-результаты, синтетические C++-исходники и текстовые результаты разбора объектов. Скомпилированные исполняемые/объектные файлы и исходники самой игры не включены.

`results/source-integrity.json` содержит SHA-256 входного архива и результат побайтного сравнения распакованных файлов с исходным ZIP. Это подтверждает отсутствие изменений входных файлов, но не проверяет свежесть архива относительно рабочего компьютера пользователя.
