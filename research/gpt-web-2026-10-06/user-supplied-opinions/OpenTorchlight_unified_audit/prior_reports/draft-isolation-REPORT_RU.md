# OpenTorchlight: девятый проход — конкретные потери работы

Дата: 6 октября 2026 года.

## Результат и границы

Этот проход не добавляет новый универсальный декомпилятор. Найдены два конкретных дефекта обвязки экспорта Ghidra, подготовлен опциональный патч и измерена одна ограниченная оптимизация компиляции на настоящих исходниках проекта.

Подтверждено:

* Неудачный экспорт без тела может считаться актуальным по существующей проверке отпечатков.
* Два запуска из разных рабочих копий могут перезаписать общие входы экспорта. Это воспроизведено настоящей Python-обвязкой с управляемым заменителем файлового обмена Ghidra.
* Предкомпиляция общего начального заголовка ускорила две реальные единицы компиляции на системном GCC; полные объектные файлы побайтно совпали.

Не подтверждено: выполнение исправленного Java-скрипта в установленной Ghidra, успешная повторная декомпиляция крупнейшей функции, работоспособность PCH на исходном GCC 4.4.7, ускорение всего конвейера, принятие новых игровых функций. Количество новых принятых игровых функций в этом проходе: ноль.

Исследовался загруженный срез, а не текущие рабочие копии пользователя. Старые экспорты могут не отражать уже сделанные на его компьютере исправления. Из 2 285 исходных файлов ZIP ни один не изменён; Python создал дополнительные служебные `__pycache__`, не являющиеся файлами исходного архива и не включённые в результат.

## 1. В крупнейшей функции сохранено сообщение об истечении времени

В `research/decomp-automation-audit-2026-10-04/measured.json` самая крупная запись из сохранённой выборки 666 функций:

```text
CGameUI::updateIngameUI(float, CGameClient*, Ogre::RenderWindow*)
Адрес: 0xab8100
Исходный TU: gameui.cpp
Размер машинного тела: 80 437 байт
raw_lines: 2
accepted: false
```

В `research/decompiled-core/game_ui.c`, строки 16737–16740, вместо тела находится:

```c
/* address=00ab8100
   symbol=CGameUI::updateIngameUI */
/* DECOMPILATION FAILED: Exception while decompiling 00ab8100: process: timeout
 */
```

Две строки и нулевые признаки контейнеров в старой метрике означают отсутствие черновика, а не простую функцию без контейнерных операций.

По классовым C-экспортам в `research` найдены 22 записи об ошибках: одна с тайм-аутом и 21 с `Overriding symbol with different type size`. Это не список 22 функций, для которых нигде нет успешного результата: в архиве и на рабочем компьютере могут быть другие, более поздние экспорты. Больший тайм-аут также не является исправлением конфликта размера типов.

### Почему текущий повторный запуск не обязан это устранить

В `tools/decomp/ghidra/DecompDrafts.java`, строка 365, установлен `callback.setTimeout(120)`. При неуспехе в строке 359 сохраняется `// failed: ...` вместо C-кода.

В `tools/decomp/ghidra_draft.py` проверка `draft_state()` сравнивает отпечатки ELF, инструментов, типов и прототипов, но не проверяет наличие пригодного тела. `drafts()` может записать отпечаток и для файла, состоящего из комментария об ошибке.

Воспроизведение создало минимальную корректную структуру БД, метаданных и raw-файла с `// failed: process: timeout`. Настоящий исходный `draft_state()` вернул `fresh`. После патча тот же случай возвращает `stale`. Исчезнувший raw-файл тоже перестаёт считаться актуальным.

Ни оригинальная Ghidra, ни ELF для проверки этого Python-условия не использовались. Реальный успешный экспорт `updateIngameUI` в этой среде не получен.

### Добавляемый этап

Перед передачей черновика преобразователям — проверка завершённости экспорта. После неудачи — явный повтор только проблемных результатов, а не молчаливое закрепление ошибки в кэше.

Патч добавляет `--retry-failed` и `--timeout`. При неизменных исходных зависимостях можно повторить только недостающие/неудачные функции. При изменении ELF, инструментов, типов или прототипов повторяется весь запрошенный TU: старые успешные тела нельзя пометить новым отпечатком без обновления.

Ghidra штатно различает успешное завершение, тайм-аут, отмену и отказ запуска через `DecompileResults`; `DecompilerCallback.setTimeout(int)` задаёт секунды для отдельной декомпиляции [1, 2]. В предлагаемом минимальном патче контроль готовности на стороне Python распознаёт текущий формат сообщений экспортёра и наличие тела. Это не синтаксический валидатор C++ и не доказательство правильности декомпиляции.

## 2. Независимые рабочие копии делят один каталог входов

В `ghidra_draft.py`, строка 37, значение по умолчанию:

```python
WORK = Path(os.environ.get("OTL_GHIDRA_WORK", "/var/tmp/opentorchlight-ghidra"))
```

Далее каждый `drafts()` делает, строки 164–165:

```python
io = base / "io"
shutil.rmtree(io, ignore_errors=True)
```

После удаления туда записываются `types.json`, `targets.txt`, Java-скрипт и результаты. Для журналов также используется общее имя `drafts`.

`parallel.py` создаёт отдельные git worktree и отдельный каталог гибридного runtime, но сам по себе не назначает независимый `OTL_GHIDRA_WORK`. Поэтому наличие разных git worktree не разделяет перечисленные входы Ghidra.

### Детерминированное воспроизведение

Две настоящие Python-обвязки загружены из исходного скрипта с двумя временными корнями проекта. База ELF и экспорт заголовков заменены минимальными тестовыми значениями. На границе запуска Ghidra установлен заменитель, который читает переданные пути к входам и пишет результат по их контракту.

Первый поток подготовил задание A для `0x100` и остановился перед чтением списка. Второй подготовил B для `0x200`, удалив общий `io`. Затем оба продолжили работу.

| Наблюдение | Исходная обвязка | С патчем |
|---|---|---|
| Что прочитало A | `0x200`, чужая цель | `0x100`, своя цель |
| Что прочитало B | `0x200` | `0x200` |
| Появилось тело A | Нет | Да |
| Появилось тело B | Да | Да |
| Имена журналов | Общие | Разные |

Исходные Python-команды в этом воспроизведении не выбросили ошибку, хотя A не получила своего результата. Это не запуск двух реальных процессов Ghidra: их проектные блокировки здесь не проверены. Подтверждён конфликт файлового контракта обвязки, а не вся картина конкурентного исполнения на машине пользователя.

### Исправление

Каждый запуск получает собственный каталог через `tempfile.mkdtemp`:

```text
work/io/drafts-<уникальный-id>/
    scripts/
    types.json
    targets.txt
    out/
    status.json
```

Журналы получают тот же уникальный идентификатор. Другие входы больше не удаляются. Каталог остаётся для диагностики.

Кроме того, если ожидаемый новый output не появился, обвязка больше не оставляет на его месте прежнее успешное тело. Записывается явный неуспех, операция возвращает ненулевой код, а черновик остаётся неактуальным.

Ограничения патча: он не обеспечивает синхронизацию публикации одного TU двумя работниками в одной рабочей копии, не изолирует общий проект/кэш Ghidra, не меняет её проектные блокировки и не делает весь процесс многопоточно безопасным. Исправлен конкретный конфликт входов и журналов; он не является разрешением одновременно писать один исходный TU.

## 3. Предкомпиляция общего начала файла: ограниченный, измеренный резерв

В `decomp/src` 201 C++-файл; у 200 первый include — `EmptyStrings.h`. Исключение: `ShellUtils.cpp`.

Существующий `toolchain.py` уже кэширует результат компиляции с учётом содержимого и зависимостей. Предкомпилированный заголовок решает другой случай: после изменения тела C++-функции готовый объект нельзя переиспользовать, но одинаковое начало с заголовками необязательно разбирать заново. GCC 4.4.7 документирует PCH, включая включение через `-include`, ограничения по компилятору, флагам и макросам [3].

В `EmptyStrings.h` есть TU-local строковые объекты. Комментарий в проекте прямо отмечает значимость порядка их инициализации. Поэтому тест не объединял все заголовки проекта произвольно и не переставлял инициализаторы: временный PCH-префикс состоял только из первого существующего include.

### Методика

Использованы неизменённые `BinaryStyle.cpp` и `utilities.cpp`, системный GCC 14.2, C++98, `-O2 -fno-strict-aliasing -DNDEBUG`, старый ABI libstdc++ и доступные заголовки архива. Для каждого режима — один прогрев и девять измеряемых компиляций. Порядок обычной и PCH-компиляции чередовался. `-H` подтвердил фактическое использование `.gch`.

Кэш готовых объектных файлов не участвовал: измерялось выполнение компилятора. Сравнивались SHA-256 полных `.o`, а не только нормализованный код.

| Файл | Без PCH, медиана | С PCH, медиана | Отношение | Объектные файлы |
|---|---:|---:|---:|---|
| BinaryStyle.cpp | 60,64 мс | 27,29 мс | 2,22× | Побайтно одинаковы |
| utilities.cpp | 247,43 мс | 218,65 мс | 1,13× | Побайтно одинаковы |

Создание PCH заняло 116,40 мс. В каждом измеренном повторе выигрыш составляет около 29–33 мс, а не секунды. Поэтому множитель 2,22 не следует переносить ни на большой файл, ни на весь конвейер. Для редких компиляций предварительная подготовка может не окупиться.

Полная компиляция проекта не проверялась. Полные OGRE-заголовки и исходный GCC 4.4.7 отсутствуют в этой среде. Нельзя считать подобранный `-D_GLIBCXX_USE_CXX11_ABI=0` заменой точного исходного компилятора.

Производственный патч PCH намеренно не включён. Приоритет — сначала повторить измерение точным GCC на реальных часто меняющихся больших TU и проверить все зависимости, варианты макросов и совпадение объектов. Здесь предоставлен измеритель, а не рекомендация сразу переделать сборку.

## 4. Что находится в патче

`patches/draft-retry-isolation.patch` меняет только:

```text
tools/decomp/ghidra_draft.py
tools/decomp/ghidra/DecompDrafts.java
```

Он добавляет независимый каталог задания и журнал, явный результат экспорта, проверку отсутствующего/ошибочного raw-тела, ограниченный повтор неудач, параметр времени на функцию и сохранение зависимостей типов при частичном обновлении. Измерительный режим с отключёнными прототипами консервативно вызывает полное обновление, а не выборочный повтор.

При первом запуске после изменения скриптов их отпечаток изменится: запрошенный TU будет обновлён полностью. Выборочный повтор применяется, когда входы действительно совпадают. Нормализация результатов, приёмка MATCH, игровая логика и `decomp/src` не меняются.

Не вошли ранее обсуждённые расширения отслеживания прототипов внешних вызываемых функций и безусловное обновление экспорта типов до выбора `--stale`. Это отдельные известные ограничения исходного механизма; данный патч не объявляет полноту всей системы инвалидации.

## 5. Воспроизведение и применение

Проверки без изменения рабочего проекта:

```bash
python3 run_checks.py /путь/к/OpenTorchlight-main --out /tmp/ot-pass9-check
```

Также выполнить измерение PCH системным `g++`:

```bash
python3 run_checks.py /путь/к/OpenTorchlight-main --out /tmp/ot-pass9-check --benchmark
```

Обвязка копирует два файла во временный каталог, проверяет и применяет именно приложенный патч там, затем запускает тесты. Если исходный проект уже изменён и патч не применим, проверка останавливается. Она не выполняет Ghidra, игру и исходный GCC автоматически. Для импортов Python нужны штатные зависимости утилит проекта; компиляционные измерения требуют `g++` и заголовков из архива.

Опциональное применение после просмотра diff, из корня проекта:

```bash
git apply --check /путь/к/OpenTorchlight_pass9/patches/draft-retry-isolation.patch
git apply /путь/к/OpenTorchlight_pass9/patches/draft-retry-isolation.patch
python3 tools/decomp/ghidra_draft.py drafts gameui.cpp --retry-failed --timeout 600
```

Последняя команда должна исполняться в окружении проекта с оригинальным ELF, установленной Ghidra и её уже подготовленной базой. Здесь она не исполнялась. 600 секунд — конфигурируемый предел для отдельной функции, не прогноз её завершения и не доказательство, что этого времени достаточно. Ограничение времени не исправляет несовместимые типы.

## 6. Пройденные проверки

16 тестов нового поведения: классификация нескольких видов raw-выхода, актуальность, отсутствие файла, частичный повтор, полное обновление при смене входов, сохранение зависимостей типов, режим без прототипов, пропавший output, отказ backend, два конкурентных задания, независимость каталогов, пустая очередь и проверка аргументов.

Все 16 пройдены. Тесты вызывают настоящую Python-логику, но Ghidra на границе её запуска заменена управляемым обработчиком файлов.

Отдельно выполнены 24 существующих Python-теста `test_ghidra_cpp`, `test_objdiff_literals`, `test_llm_loop_headers`, `test_mutate_overloads`; все пройдены. Они не являются новыми тестами игрового поведения и не доказывают работу изменённого Java-скрипта.

Проверено `git apply --check`, применение патча к временной копии, совпадение результата с тестируемой версией и синтаксис Python. Java с Ghidra не компилировалась и не запускалась.

Результаты:

* `results/draft-regressions.json` — 16 тестов и исходные наблюдения до/после.
* `results/patch-application.json` — применение патча и ограничения проверки.
* `results/pch-benchmark.json` — все времена, флаги компилятора, хеши `.o`.
* `results/archive-evidence.json` — источники, номера строк, ошибки исторических экспортов и контроль исходного ZIP.
* `results/existing-unit-tests.txt` — 24 существующих теста.

## 7. Практический приоритет

Первое полезное действие — получить полный, однозначный вход для реального крупного метода: повторить неудачный экспорт `updateIngameUI` с явной диагностикой и не дать соседнему заданию заменить его входы. Это ещё не восстановленный C++, но конкретная предпосылка для всех последующих автоматических преобразований.

Следующий проверяемый результат — принятый крупный метод или его существенная часть, полученные без ручного написания тела. Количество тестов на искусственных примерах, распознанных шаблонов и потенциальных кандидатов не заменяет этот результат.

PCH — менее приоритетная оптимизация, которую стоит внедрять только после измерения доли компилятора в реальных затратах. Новый сложный анализатор без такого измерения может увеличить объём работы над инструментами быстрее, чем уменьшит остаток игры.
