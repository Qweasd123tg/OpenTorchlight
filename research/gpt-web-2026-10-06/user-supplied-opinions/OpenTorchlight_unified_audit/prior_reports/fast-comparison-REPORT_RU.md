# OpenTorchlight: третий проход по автоматизации без LLM

## Границы проверки

Проверен присланный `OpenTorchlight-main(4)(1).zip`, а не текущее состояние рабочего компьютера пользователя. Источники: действующие `tools/decomp`, `decomp/src`, `decomp/include`, `decomp/hybrid` и архивные результаты анализа в `research`. Указанные номера строк относятся к этому архиву.

Оригинального ELF, целевого GCC 4.4.7 и готовой базы Ghidra в окружении проверки нет. Игровые функции не запускались, новые функции игры не приняты, полный конвейер не измерен. Эксперименты выполнены системным GCC 14.2.0. Результаты по историческим символам не являются текущим отчётом о незавершённых функциях.

Исходники игры и инструменты в распакованном проекте не изменены. Опциональный патч применялся только к временной копии. Его задача — ускорение прежнего алгоритма нормализации, а не исправление всех ограничений проверки эквивалентности, описанных в предыдущих проходах.

## 1. Измеренное ускорение: перестать повторно разбирать секцию для каждой функции

**Подтверждено кодом и воспроизводимым тестом.**

В `tools/decomp/objdiff.py:349–376`, функция `object_functions`, вывод `objdump` сначала разделяется на текстовые секции. Затем внутри цикла по символам для каждой функции заново выполняется:

```python
parse_insns("\n".join(sections.get(section.name, [])))
```

То есть заново разбирается вся соответствующая секция, после чего ненужные инструкции отбрасываются по диапазону адресов. При F функциях и I инструкциях в одной секции эта часть работы имеет порядок F × I. Это не повторный запуск objdump: повторяется Python-разбор уже полученного текста.

Прототип разбирает каждую секцию один раз и строит массив адресов. Инструкции функции выбираются двумя `bisect_left`. При необычном неупорядоченном выводе сохраняется прежняя фильтрация, но без повторного текстового разбора. Сами `normalize`, обработка релокаций, границы функции и правила имён не меняются.

### Результаты

Синтетические `.o`, созданные GCC 14.2.0, все функции одной серии в одной секции. Три запуска каждого варианта, ниже медианы. Измерено всё выполнение `object_functions`, включая objdump, а не только один вызов regex.

| Число функций | Прежний вариант, с | Индексация, с | Отношение | Вызовы parse_insns |
|---:|---:|---:|---:|---:|
| 50 | 0,016839 | 0,002726 | 6,18 | 50 → 1 |
| 200 | 0,140814 | 0,005317 | 26,48 | 200 → 1 |
| 500 | 0,817539 | 0,009322 | 87,70 | 500 → 1 |

Полные словари результатов совпали во всех случаях. В серии из 500 функций суммарно разобранный текст сократился с 33 576 000 до 67 152 символов.

Дополнительно прототип проверен на 18 функциях смешанного C++-объекта: несколько секций, виртуальные деструкторы, thunks множественного наследования, строки, исключение, ссылки на данные, рекурсия, switch. Вывод совпал.

Для самого файла патча отдельно проверены применение к временной копии, объект с 500 функциями, объект с 17 функциями/алиасами/несколькими секциями и три существующих теста `test_objdiff_literals` на исходной и изменённой версиях. Все эти проверки прошли.

Файлы: `objdiff-section-index.patch`, `objdiff_fast_probe.py`, `verify_patch.py`, `results/parser-benchmark.json`, `results/patch-verification.json`.

**Ограничение вывода:** это ускорение одного этапа на синтетических объектах. Если он занимает малую долю общего времени, выигрыш всей системы будет намного меньше. Нельзя называть это ускорением декомпиляции игры в 88 раз. Патч не исправляет семантические ограничения существующего нормализатора, включая литералы и данные исключений из прошлого отчёта.

## 2. Неполный исходный .cpp может мешать MATCH при правильном тексте функции

**Подтверждён механизм на синтетическом коде; масштаб в игре пока неизвестен.**

Один и тот же код:

```cpp
extern "C" unsigned helper(unsigned) __attribute__((noinline));
extern "C" unsigned probe(unsigned* p, unsigned x) {
    unsigned a = *p;
    return a + helper(x) + *p;
}
```

В первом варианте доступно только объявление `helper`. Во втором в том же исходном файле присутствует её тело:

```cpp
extern "C" unsigned helper(unsigned x) { return x * 3u; }
```

Текст `probe` и параметры компиляции одинаковы. `helper` запрещено встраивать в обоих вариантах. Однако GCC 14.2 выпускает для `probe` 13 и 6 инструкций соответственно: видимость тела позволяет использовать дополнительные сведения о вызове, включая отсутствие записи в память. Значение по `p` не обязательно перечитывать после него. В конкретный результат также могут входить другие межпроцедурные оптимизации современного GCC; именно последовательность 13 → 6 не заявляется для GCC 4.4.7.

Это отличается от ранее найденной зависимости от прототипов. Тип может быть правильным, но компилятору всё ещё не хватает тел соседних методов, определений inline-функций или известных побочных эффектов. Целевой GCC 4.4.7 уже документирует межпроцедурное определение pure/const и анализ ссылок [1].

### Предлагаемая автоматизация

При DIFF отдельно диагностировать различия, объясняемые контекстом исходного .cpp: повторные чтения после вызова, доступность inline-тел, решения об устранении или переносе операций. Использовать подтверждённые соседние определения и диагностические дампы компилятора. В GCC 4.4.7 предусмотрены `-fdump-ipa-all`, `-fdump-ipa-cgraph`, `-fdump-ipa-inline` [2].

Не следует произвольно менять правильный caller, присваивать неизвестному вызову `pure`/`const`, менять исходные флаги игры или подставлять непроверенное тело для получения процента сходства. Неизвестное определение — основание отложить точное сопоставление либо проверять поведение другим обоснованным способом.

Файлы: `context_a.cpp`, `context_b.cpp`, `results/probe-results.json`.

## 3. Ограниченный проверяющий инструмент семантической эквивалентности

**Новый экспериментальный путь проверки, не изменение действующей политики приёмки.**

В некоторых случаях понятный C++ уже есть, но машинный код отличается. Можно не только перебирать форму исходника или вручную писать тест, но и поставить математическую задачу: существует ли вход, на котором результаты двух реализаций различаются?

Для небольших целочисленных фрагментов естественна модель фиксированной разрядности. Она учитывает арифметику по модулю 2^N и различия signed/unsigned; Z3 поддерживает соответствующую теорию битовых векторов [3].

### Что реально сделано

Скомпилирована одна функция умножения беззнакового 32-битного аргумента на семь с `-O2` и `-Os`. Из реально полученных инструкций извлечены две формы:

```text
lea (x * 8); sub x       → (8*x - x) mod 2^32
imul 7                  → (7*x) mod 2^32
```

Миниатюрный анализатор принимает только явно поддержанные инструкции этого примера, не исполняет произвольную программу и отклоняет остальные конструкции. Z3 4.13.3.0 получил запрос о существовании различающего входа:

- правильная пара: `unsat`;
- ошибочный вариант `8*x`: `sat`, найден пример `x = 0xffffffff`.

Это подтверждение равенства возвращаемого `unsigned` для всех 2^32 входов в указанной модели, а не эквивалентности любых двух функций и не доказательство корректности игрового кода. `-Os` использован лишь для получения отличающегося образца, менять флаги Torchlight не предлагается.

### Как развивать, не превращая проект в эмулятор

Первая область применения: короткие целочисленные методы или выделенные фрагменты без неизвестных вызовов, циклов и неподдержанной памяти. Затем — небольшие ветвления и известные эффекты. Требуются точные условия на входы, видимые выходы и модель инструкций.

Нужны три результата: доказано в заявленной области; найден контрпример; UNKNOWN. Неподдержанные инструкции, тайм-ауты, неизвестные эффекты, сомнительные указатели не должны превращаться в успешную проверку.

Для памяти важны записи, отношения указателей, допустимость доступа, глобальные данные, внешние вызовы и наблюдаемые ошибки. Для float нужны отдельные модели округления, NaN и окружения. Доказательство в предположениях обязано явно перечислять предположения. Проверка бинарного поведения также не заменяет анализ неопределённого поведения исходного C++ и требований к переносимости.

PATE демонстрирует композиционный подход к сравнению бинарного поведения, но его заявленные платформы — статически связанные PowerPC/AArch32 ELF, не целевая x86-64 Torchlight [4]. Alive2 проверяет LLVM-преобразования и прямо ограничивает межпроцедурные преобразования [5]. Ни один из них здесь не объявляется готовой кнопкой для проекта.

Файлы: `algebra.cpp`, `probe_pass3.py`, `results/candidate.smt2`, `results/wrong_candidate.smt2`, `results/probe-results.json`.

## 4. Автоматическое наблюдение за связями объектов вместо ручных проверок адресов

**Ограничения Capture воспроизведены на настоящем заголовке проекта. Общий наблюдатель пока предложение.**

`decomp/hybrid/AutoTest.h:132–136` сохраняет для указателя NULL, смещение в тестовой арене или `-1`. Поэтому два различных ненулевых указателя вне арены получают одинаковое представление. Указатели внутри арены уже различаются по смещению — утверждение о потере относится только к внешним.

`Capture::add`, строки 125–130, молча обрезает запись при достижении 256 КиБ. Различия за пределом буфера не попадают в сравнение.

Общий `record<Value<T>>`, строки 170–173, копирует `sizeof(T)` байтов. Для агрегата это может включать padding. В отдельном примере с заранее заполненными объектами `Value<Padded>` одинаковые поля и разный padding дают разные capture. Не утверждается, что именно этот случай уже вызвал ложный результат в игре или что оператор возврата всегда сохраняет padding.

Все три свойства воспроизведены `probe_runtime.cpp`, использующим настоящий `AutoTest.h`.

### Почему это связано с ускорением

Для методов, возвращающих элементы инвентаря, персонажей или объекты UI, недостаточно знать, что результат «не NULL». Приходится писать индивидуальные проверки. Более общий наблюдатель можно генерировать из известных типов и описаний тестовых состояний.

Наблюдать нужно значения полей и отношения: возвращён именно третий входной объект; два поля ссылаются на один объект; объект удалён; существовавшая связь сохранена. Идентификаторы существовавших объектов привязываются к входному состоянию, а не выдаются независимо по порядку обхода результата. Иначе два разных возвращённых объекта снова получат «номер один».

Для новых выделений нужен учёт происхождения/структуры и отношений между ними, для глобальных объектов и функций — отдельные стабильные идентификаторы. Неизвестная ссылка должна остаться неизвестной. Глубина, полнота наблюдения и обработка циклов должны быть явными.

При переполнении capture требуется ошибка/UNKNOWN либо полный потоковый механизм сравнения с учётом длины; не молчаливый успех. Padding можно исключать из семантического сравнения членов, но не из действительно наблюдаемых сырых буферов и файловых форматов. Один такой наблюдатель мог бы использоваться во многих тестах, но полного решения в этом проходе не реализовано.

## 5. Восстановление пар save/load как одного протокола

**Подтверждено наличие подходящих участков; генератор схем не реализован.**

В сохранённом `research/decompiled-core` найдены:

| Функция | Машинных байтов по архиву символов | Синтаксических мест вызова fread/fwrite |
|---|---:|---:|
| `CCharacterSaveState::save` | 3304 | 83 fwrite |
| `CCharacterSaveState::load` | 5688 | 88 fread |
| `CItemSaveState::save` | 2421 | 56 fwrite |
| `CItemSaveState::load` | 4928 | 72 fread |

Итого 16 341 байт и 299 мест вызовов. Это не 299 уникальных полей, не количество выполнений и не утверждение, что все эти функции остаются невосстановленными сейчас. Код содержит версии формата, циклы и ветви.

Идея: автоматически извлекать общий упорядоченный протокол «условие/версия → ширина данных → поле/значение → повторение → ошибка», сопоставляя запись и чтение. Генерировать обычные исходные C++-операции в прежних `.cpp`, не новый формат сохранений и не универсальный runtime.

Две стороны служат взаимными ограничениями, но не обязаны быть буквальными обратными функциями: загрузчик может поддерживать старые версии, задавать значения по умолчанию и выполнять миграции. Нельзя генерировать схему из плоского списка вызовов: `tools/decomp/calls.py` прямо сообщает, что не следует по ветвям.

Полезные автоматические проверки: точное совпадение байтов записи оригинала и кандидата; перекрёстные оригинал-save → кандидат-load и кандидат-save → оригинал-load; поля объекта, положение файла, результат и ошибки; обрывы файла на границах операций; переходы между версиями. Только собственный round-trip кандидата недостаточен: две согласованные ошибки могут взаимно скрыться.

Это конкретная ограниченная область применения, а не обещание автоматически восстановить всю игру.

## 6. Дополнительная повторная работа после существующего кэша

**Установлено чтением кода, ускорение не измерено.**

`toolchain.py:153–235` уже содержит кэш компиляции с зависимостями и флагами. Предлагать «просто добавить ccache» как новое открытие неправильно. Кэш оригинальной нормализации также уже существует в `objdiff.py`.

Но дальше остаются повторяемые стадии:

- `objdiff.compile_for_diff:536–541`: преобразование ассемблера и сборка объекта после получения `.s`;
- `check.py:91–94`: сравнение всех имеющихся `.cpp`;
- `hybrid.py:314–329`: обход всех игровых и тестовых единиц, преобразование `.s` и сборка `.o`;
- `hybrid.py:351–382`: служебные объекты, линковка и сборка loader;
- `objdiff.py:569`: `SequenceMatcher(..., autojunk=False).ratio()` для каждого DIFF, даже когда процент не нужен для решения о неравенстве.

В архиве 201 игровой `.cpp` в `decomp/src` и 38 рукописных тестовых `.cpp`; число зарегистрированных тестов может быть другим.

Предлагается кэшировать именно производные артефакты и результаты чистых преобразований. Ключ должен включать содержимое входного `.s`, таблицы перенаправлений, версии преобразователей, оригинальный ELF, нужные символы/данные и параметры нормализации. Для повторного использования результатов тестов нужны более строгие зависимости, включая общие данные, виртуальные вызовы и состояние; пропускать их по одному имени функции нельзя. Полная финальная проверка остаётся.

Дорогую оценку похожести можно сделать отдельным режимом диагностики/ранжирования, сохранив точное сравнение. Параллелизм в мутационных инструментах уже частично есть; без профиля не предлагается просто ещё увеличить число процессов.

## 7. Очередь и приоритеты: небольшое уточнение

`parallel.py:candidates:90–95` пропускает TU, если соответствующий файл исходника уже существует, а также TU больше 60 000 байт. Это допустимо для конкретной очереди новых небольших файлов, но такую очередь нельзя считать всем оставшимся объёмом работы. Нужна отдельная обработка частично восстановленных и крупных TU по текущим данным MATCH/DIFF/MISSING, с сохранением блокировок владения файлами. Не следует возвращать замороженные старые реестры вместо действующего конвейера.

Архивный direct-call graph можно использовать для приоритета общих анализаторов и наблюдателей. Среди сохранённой выборки 666 крупных функций `getPosition(bool)` имеет 119 прямых callers, `CBaseUnit::ISA` — 113, `CDynamicPropertyFile::GetInt` — 101. Это не новые незавершённые функции, не покрытие всех вызовов и не независимые группы; суммировать их как процент экономии нельзя. Таблица в `results/inventory.json` полезна лишь как исходный материал для выбора общих зависимостей после сверки с текущим статусом.

## 8. Проверенная, но не подтвердившаяся большая ставка

В архивном списке 17 023 уникальных адреса функций. Выявлены 218 явно помеченных compiler clones, из них 211 относятся к статической инициализации, остальные — к библиотечным конструкциям. Действующий учёт уже отделяет автоматически порождаемые инициализаторы. Также найдены 596 thunk-функций общим размером 5217 байт.

Поэтому вывод «убрать эти клоны и получить сотни новых крупных игровых функций автоматически» не подтверждается. Отдельные тождества и распознавание встроенных фрагментов остаются полезны, но здесь не найден новый большой резерв, который можно честно посчитать ещё раз.

## Порядок внедрения

Ближайшая изолированная работа — индексирование секций в objdiff с регрессией на реальных `.o` и профилем полного check. Затем кэш неизменившихся промежуточных результатов. Это уменьшает машинное время, не меняя критерии правильности.

Следующий резерв — уменьшить число бесполезных итераций: учитывать компиляторный контекст, давать UNKNOWN для неподдержанных случаев и расширять повторно используемое наблюдение за объектами.

Более исследовательская ветвь — ограниченная семантическая проверка и парный генератор save/load. Сначала отдельная фиксированная выборка, без автоматической публикации кандидатов в `decomp/src`. Измерять новые проверенные реализации и затраты, а не только процент сходства или число сгенерированных строк.

## Воспроизведение

Нужны Python 3, системные `g++`, `objdump`; для проверки патча также `patch`. Арифметический эксперимент дополнительно использует установленную общую библиотеку Z3 через ctypes; Python-пакет z3 не требуется. При отсутствии библиотеки только этот этап отмечается пропущенным. Синтетические примеры рассчитаны на x86-64/GNU objdump; неподдержанный вывод отвергается. Benchmark использует `-fno-ipa-icf` системного современного GCC, а не целевой GCC 4.4.7.

Из распакованной папки этого отчёта, указав реальный путь к архивной версии проекта:

```bash
python3 probe_pass3.py /path/to/OpenTorchlight --out ./reproduced
python3 objdiff_fast_probe.py /path/to/OpenTorchlight --out ./reproduced/parser-benchmark.json
python3 verify_patch.py /path/to/OpenTorchlight --out ./reproduced/patch-verification.json
```

Последняя команда применяет патч только во временном каталоге. Перед применением патча к рабочей версии необходимо проверить расхождения с архивом. Исходный SHA-256 файла и SHA-256 варианта с патчем приведены в `results/patch-metadata.json`.
