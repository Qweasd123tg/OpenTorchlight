# OpenTorchlight: второй проход по ускорению без LLM

Дата: 6 октября 2026 года. Вход: `OpenTorchlight-main(4)(1).zip`.

## Граница проверки

Изучен действующий `decomp`, его импорт типов, нормализация машинного кода и исторические данные SDK. Исходники игры не изменены. Запущены отдельные воспроизводимые проверки настоящих Python-функций из архива на синтетических объектах, собранных системным GCC 14.2.0 с C++98. Для проверки DWARF использован DWARF-2. Это НЕ запуск GCC 4.4.7, Ghidra, оригинального Torchlight или полного `objdiff.py compare_source` против игры. Оригинального ELF, Core.dll и подготовленного оригинального тулчейна в архиве нет. Измерений ускорения восстановления не получено.

Главное отличие от первого прохода: помимо распознавания шаблонов внутри больших функций, следует сначала сохранять уже известную C++-информацию, использовать межпроцедурные ограничения, таблицы исключений и вторую сборку движка. Перед автоматическим принятием большого числа кандидатов нужно устранить найденные неоднозначности нормализации.

## 1. Импорт типов теряет сведения, которые затем приходится восстанавливать

### Таблицы виртуальных методов

`tools/decomp/types_export.py:309–323` экспортирует только `groups[0]`. Значения слотов — короткие имена; не сохраняются адреса целей и сигнатуры в составе записей слотов. В `tools/decomp/ghidra/DecompDrafts.java:124–132` каждый слот создаётся как `void*`. В `collect`, строки 150–152, пропускаются все поля `_vptr`; `fill`, строки 171–176, возвращает только один указатель на таблицу по смещению 0.

Это не значит, что вся Ghidra не знает типов методов: отдельные прямые функции получают прототипы. Ограничение относится к конкретному пути импорта типов виртуальных вызовов и вторичных базовых подобъектов.

Синтетический вызов настоящей `types_export.vtables` с двумя группами дал одну экспортированную группу: второй метод отсутствует. Чтением актуальных заголовков найдено 23 объявления классов с несколькими явно указанными базами, включая CCharacter, CEquipment, CSkill, CDamageShape и CGameClient. Это число объявлений, а не число ошибочных игровых функций.

Предлагаемый ремонт: для каждой vtable group сохранить адресную точку, смещение базового подобъекта, цель/слот/сигнатуру, ABI-коррекцию this и сведения о thunk. В Ghidra создавать указатель на FunctionDefinitionDataType, а не void*. Для базового указателя сохранить виртуальность: неизвестный динамический тип нельзя подменять одним конкретным вызовом.

### Пространства имён

`types_export.type_name` возвращает DW_AT_name, без полной цепочки пространств имён. `header_classes` использует короткое имя как ключ.

В проверке с настоящим DWARF:

- First::Cell имеет размер 4;
- Second::Cell имеет размер 16;
- экспорт оставил один ключ `Cell` размером 16;
- оба различных указателя в Holder стали `Cell*`.

Это воспроизведение ограничения схемы, не доказательство конкретного конфликта в уже принятых игровых функциях. Нужны стабильный type_id, полное имя, отдельный граф типов и явные ссылки между типами вместо текстовых догадок по имени. Для typedef нужно сохранять и идентичность, и базовый тип.

### Размер long

`DecompDrafts.java:102` отображает `long int` в IntegerDataType, игнорируя размер 8. В DWARF синтетического Linux x86-64 объекта поле long имеет размер 8. Для `unsigned long*` путь `primitive(inner, 0)` также не передаёт размер типа, на который указывает указатель.

Java не запускалась внутри Ghidra: ошибка ветки установлена чтением кода, а исходный размер подтверждён компиляцией. Правильнее передавать размер, signedness и кодировку базового типа через type_id, а не определять их по строке и размеру поля-указателя.

## 2. Восстанавливать типы системой ограничений через несколько функций

`layout.py` уже собирает полезные сведения по обращениям к полям и вызовам. Это не отсутствующая функциональность. Дополнение: связать факты о значениях, аргументах, результатах, полях и виртуальных вызовах в общий анализ с учётом потока управления.

Пример задачи: поле, загруженное в одной функции, передаётся в подтверждённый метод CInventory; в другой функции записывается результат известного конструктора; в третьей используется через интерфейсную vtable. Вместе это гораздо сильнее, чем частота похожих инструкций в одной функции.

Предлагаемый цикл:

1. Взять проверенные заголовки, реальные сигнатуры, RTTI и базовые смещения как исходные ограничения.
2. Из High P-code извлечь связи присваиваний, загрузок/записей, вызовов и возвращаемых значений.
3. Вывести совместимые типы по группе взаимозависимых функций, не объединяя разные подобъекты и несовместимые ветви.
4. Применить однозначные результаты к копии базы Ghidra; конфликты оставить явно неразрешёнными.
5. Перегенерировать зависимые функции и повторить до стабилизации.

Из уже имеющихся Get_/Set_ и AddProperty можно получать дополнительные ограничения на тип и назначение поля. Новое здесь не ещё один генератор дескрипторов, а использование их информации при восстановлении остальных методов.

Существующие ненейросетевые реализации для пилота: GrammaTech Retypd с Ghidra-плагином; Trail of Bits BTIGhidra. Совместимость с конкретной установленной версией Ghidra и качество на этом C++-проекте не проверены. Это кандидаты для контролируемого эксперимента, не готовая гарантия правильности. Обнаруженные правила должны оставлять неизвестное неизвестным, а не навязывать ближайший тип.

## 3. Таблицы исключений — дополнительный источник структуры C++

Нужно различать механизмы раскрутки стека (.eh_frame) и языковые таблицы обработчиков (.gcc_except_table/LSDA). В сочетании с машинным кодом, деструкторами, конструкторами и графом управления они ограничивают возможные области try/catch и моменты уничтожения объектов.

В собственном историческом `research/ui-function-bindings.md` уже есть пример CGameUI::mapToFunctions: по LSDA проверен catch-all, а рекурсивный обход находится вне защищённой области работы со свойством. Это ранее зафиксированный разбор, не новый запуск оригинала.

В действующем `DecompDrafts.java` выводится прежде всего `getDecompiledFunction().getC()`. Структурированного экспорта LSDA/cleanup-графа этим скриптом нет. `ghidra_cpp.convert` удаляет комментарии, а `drop_refcount_blocks` удаляет текстовые блоки. Нельзя считать удалённые строки доказательством восстановления эквивалентного C++.

Предложение: добавить к экспорту структурированные сведения: диапазон потенциально бросающего вызова, landing pad, action chain, catch type, cleanup path. Совместить их с данными о времени жизни объектов. По ним генерировать обычные локальные объекты, области видимости и try/catch, чтобы обслуживающий код снова создал компилятор.

В Ghidra уже есть LSDATable, LSDACallSiteTable, LSDAActionTable и LSDATypeTable; парсер формата не обязательно писать с нуля. Но эти классы не являются автоматическим генератором RAII. Оптимизатор может объединять cleanup-код; одна и та же стековая ячейка может относиться к разным объектам в разные моменты. Такие случаи требуют отдельного анализа и проверки.

Пилот: 5–10 функций с уже разобранными исключениями/локальными строками, сначала mapToFunctions. Проверять обычные и исключительные выходы, число и порядок уничтожений, затем методы с несколькими локальными объектами. Сокращение псевдокода не считать успехом само по себе.

## 4. Автоматическое сопоставление Linux-игры и Core.dll из TorchED

Повторно прочитан `research/torched-sdk.json`:

- 302 C-класса движка Core.dll найдены в символах Linux-оригинала;
- 193 реальных экспорта Core.dll;
- 196 P/Invoke-записей на 194 уникальных имени;
- 423 прямых IL-вызова Core.dll.

Это сохранённые измерения из архива; ни SDK, ни бинарник не извлекались заново. `torched-sdk.md` также фиксирует отсутствие C++-исходников и PDB в проверенном установщике. Не предлагается повторно искать там готовые исходники.

Прямой интеграции этих метаданных в действующих `tools/decomp`/`decomp` по поиску ссылок на Core.dll/core_imports/torched-sdk не обнаружено.

Новое предложение — машинная карта соответствий, а не ручное чтение второй DLL:

- якоря: экспорты, RTTI, уникальные строки, подтверждённые константы и вызываемые библиотечные методы;
- затем сходство функций и соседей по графу вызовов;
- затем соответствия участков, если одна сборка содержит отдельный helper, а другая встроила его;
- передавать в Linux-анализ только проверяемые сведения, не смещения Windows-объектов и не редакторские ветви.

BSim штатно ищет структурно похожие функции между компиляторами и архитектурами, но его score не доказывает одинаковое поведение. Финальный арбитр — целевой Linux ELF. Core.dll может быть другой ревизией и редакторской конфигурацией. P/Invoke также нужно интерпретировать с учётом marshaling, а не считать все управляемые объявления точным ABI-заголовком.

Цель пилота: на 20 трудных Linux-функциях проверить, помогает ли другая сборка разрешить конкретные неизвестные — границу helper, тип результата, структуру обхода. Не выдавать долю автоматически сопоставленных имён за процент готовности исходника.

## 5. Подтверждённые ограничения автоматической приёмки

### Длинные строковые литералы

`objdiff.literal_token`, строка 83, оставляет `text[:80]`. Две функции передают в sink строки из 80 A и разных последних символов X/Y. Реальные object-файлы обработаны настоящей `objdiff.object_functions`.

Результат:

- нормализованные инструкции равны;
- code_digest равны;
- изменение первого символа контрольного примера корректно обнаруживается.

То есть проблема не в неспособности теста вообще распознавать строки. Условия равенства, используемые `compare_source` для MATCH, действительно теряют различие после 80-го символа.

Нужен полный проверенный диапазон литерала или хеш полного содержимого с длиной и представлением. Сокращать можно отображаемый текст, но не ключ сравнения. При недоказанном размере диапазона безопаснее не засчитывать полное совпадение данных.

### Типы catch находятся вне сравниваемого потока инструкций

Собраны две функции, отличающиеся `catch(int)` и `catch(double)`, с одинаковым обработчиком `return 7`. Вызываемая функция бросает int; внешний драйвер перехватывает всё не обработанное и возвращает 99.

Результат:

- нормализованные инструкции probe совпадают полностью;
- code_digest совпадают;
- первая программа выводит 7;
- вторая программа выводит 99;
- в ссылках таблиц исключений различаются `_ZTIi` и `_ZTId`.

Это не утверждение, что реальная Torchlight-функция уже ошибочно принята. Это воспроизводимый контрпример достаточности сравнения только тела для произвольной C++-функции. Полный запуск compare_source против целевого ELF не выполнялся.

Нужна нормализация поведения таблиц исключений: область вызова, обработчик, типы и действия. Буквальное равенство размещения байтов не обязательно, но различие перехватываемых типов нельзя игнорировать. Отпечатки для повторного использования тестов тоже должны зависеть от этих данных.

### Отдельная граница гибрида

Гибрид намеренно использует оригинальные глобальные данные и vtables и отбрасывает повторные статические инициализаторы. Это полезно для изолированной проверки функций, но не подтверждает самостоятельность будущего исполняемого файла.

Практическое дополнение без нового бюрократического реестра: автоматически учитывать не только восстановленные тела, но и то, какие таблицы, RTTI, vtables, глобальные объекты и инициализаторы ещё предоставляются оригиналом. MATCH отдельного тела должен оставаться локальным утверждением с явными предпосылками.

## Приоритет

Сначала исправить ложные совпадения и импорт уже известных типов. Затем проверить межпроцедурный вывод типов и экспорт исключений на небольшой контрольной выборке крупных методов. Вторую сборку использовать для конкретных неразрешённых участков. После этого развивать словарь встроенных компиляторных конструкций, предложенный в первом проходе.

Это не отменяет идею компиляторного словаря. Улучшенный вход уменьшает число шаблонов, которые приходится писать, а более сильная приёмка позволяет безопаснее публиковать автоматически восстановленные тела.

## Воспроизведение

```sh
python3 probe_pipeline.py /path/to/OpenTorchlight --out probe-results.json
```

Скрипт ничего не изменяет в исходниках проекта. Временные C++/object-файлы создаются в системном временном каталоге и удаляются. Результат содержит 5 групп диагностик и перечень 23 найденных объявлений множественного наследования. Это диагностические воспроизведения; инструмент не маркирует уязвимости как исправленные.
