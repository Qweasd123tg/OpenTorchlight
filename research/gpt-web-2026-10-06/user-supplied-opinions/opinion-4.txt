Обработка заняла 21m 44s

Нашёл ещё один существенный резерв: часть ручной работы у тебя создаёт сам преобразователь черновиков. Он не только оставляет непонятный код, но в некоторых случаях меняет поведение уже понятного. Это удалось воспроизвести.

Кроме этого, сделал два новых прототипа без LLM: проверку виртуальных слотов по одним объявлениям, без реализаций методов, и автоматическое сокращение ошибки компиляции до минимального примера.

1. Исправлять правила преобразования, а не их последствия в каждой функции

В tools/decomp/ghidra_cpp.py нашёл три разных случая, когда автоматическое «улучшение» кода меняет его смысл.

Прямой вызов превращается в виртуальный

Преобразователь получает такую запись вызова из черновика:

CBase::step(object);

И превращает её в:

object->step();

Проблема: это не всегда один и тот же вызов.

Когда исходная машинная инструкция вызывает именно реализацию CBase::step, соответствующая запись на C++ должна сохранять эту цель:

object->CBase::step();

А object->step() может вызвать переопределение из производного класса. Явная квалификация именем класса и виртуальный выбор реализации имеют разную семантику. 

Проверка настоящего преобразователя: базовая реализация возвращает 11, производная — 22. Контроль с сохранённым прямым вызовом возвращает 11, автоматически преобразованный вариант — 22. Обе программы компилируются.

То есть возникает неприятный сценарий:

Цель вызова уже известна.
        ↓
Преобразователь стирает эту информацию.
        ↓
Получается собирающийся, но другой код.
        ↓
Человек снова разбирает функцию и ищет расхождение.

Исправление должно учитывать исходный вид вызова, а не просто сохранять или убирать квалификацию везде. Настоящий виртуальный вызов должен остаться виртуальным.

«Упрощение условия» меняет возвращаемое значение

В tidy_expressions() есть замена:

x != false

на:

x

Она применяется без проверки, где находится выражение.

Поэтому:

int normalize(int x) {
    return x != false;
}

становится:

int normalize(int x) {
    return x;
}

На входах -3, 0, 2 получено:

Вариант	Результаты

До преобразования	1, 0, 1
После преобразования	-3, 0, 2


Здесь перепутаны одинаковая истинность условия и одинаковое значение выражения. Встроенный оператор != возвращает bool, а не исходное число. 

Замена типов затрагивает содержимое строк

Этот пример особенно показательный. Преобразователь меняет:

"bad UTF-8 continuation byte"

на:

"bad UTF-8 continuation unsigned char"

Потому что правило замены типа byte применяется ко всему тексту, включая строковые литералы.

Исходную строку я не придумал: она встречается в трёх архивных черновиках — generic_model.c, path_controller.c и trigger_unit.c. Минимальный пример с этой строкой пропущен через настоящий convert(), скомпилирован и запущен: вывод действительно изменился. Результаты всех трёх проверок.

Это не утверждение, что три принятые игровые функции уже повреждены. Подтверждены ошибочное правило и реальные архивные входы, на которых оно применимо.

Что здесь даст ускорение

Не добавлять ещё десятки глобальных регулярных выражений, а разделить преобразования по уровню ответственности.

Сначала отделять код от строк, символов и комментариев. Затем применять изменения только к нужным токенам. Упрощения, зависящие от типов и контекста, выполнять на структурированном представлении. Для уже синтаксически корректного C++ можно использовать инструменты Clang для анализа и преобразования дерева программы; сырой вывод Ghidra не обязательно сразу пригоден для них. 

И проверять весь convert(), а не только отдельные помощники. Существующий тест сохранности литералов проверяет другой, более узкий участок — поэтому не обнаруживает показанную подмену.

Потенциальный выигрыш здесь тиражируемый: исправленное общее правило перестаёт создавать одну и ту же проблему во всех следующих черновиках. Сколько реальных функций это затрагивает, ещё нужно измерить.

2. Точные сигнатуры уже известны, но генератор их теряет

Это не повтор прошлого пункта про импорт типов в Ghidra. Здесь информация теряется при создании C++-объявлений и определений, после её извлечения.

const записан в одном формате, а читается в другом

elfdb правильно сохраняет квалификатор текстом:

cv = "const"

А генератор заголовков проверяет наличие буквы K — обозначения из другого представления имени. Поэтому известный const пропадает.

Отдельно ghidra_cpp.convert() при восстановлении заголовка функции тоже не дописывает этот квалификатор.

На настоящих функциях инструментов получил:

// Из символа известно:
int CProbe::get() const;

// Генератор выдаёт:
int get();

// Преобразователь определения выдаёт:
int CProbe::get()

Последнее не компилируется против правильного объявления. Возврат одного const исправляет проверку.

Для этого подготовлен небольшой отдельный патч. Он проверен во временной копии: обычный метод, const, volatile, const volatile собираются правильно; 21 существующий модульный тест проходит до и после изменения. Это тесты инструментов, не игры. Проверка патча.

Одна перегрузка принимается за все перегрузки

В headers.Gen.trial_include() наличие метода проверяется преимущественно по имени.

Допустим, известно, что существуют:

int read(int);
int read(double);

Но в рукописном заголовке пока есть только read(int). Генератор видит имя read и не добавляет read(double).

Проверка настоящего генератора это подтвердила: добавлено ноль объявлений.

Дальше возникает не только ошибка компиляции. В моём примере:

object.read(1.5);

успешно компилируется с обоими заголовками, но с неполным вызывает read(int) и возвращает 11, а с полным — read(double) и возвращает 22.

Есть и соседний случай: наличие CNoise::parse(int) в одном заголовке подавляет генерацию отдельной TOOLS::parse(int), потому что ищется короткое имя без учёта области видимости. Воспроизведения.

Что автоматизировать

Использовать единое представление идентичности метода: полная область видимости, имя, параметры, квалификаторы и категория метода, со связью с исходным символом.

Не спрашивать «есть ли где-нибудь read». Спрашивать «объявлена ли именно эта функция».

В ограниченной выборке архивных символов игровых классов нашлись 123 имени с несколькими вариантами параметров или квалификаторов, включая конструкторы. Это не число сломанных функций, но показывает, что перегрузки здесь не редкая теоретическая особенность. Подсчёт и его ограничения включены в отчёт.

3. Новый способ: проверять виртуальные слоты, не восстанавливая тела методов

Компилятор может сообщить положение конкретного виртуального метода в таблице по одному заголовку. Я сделал работающий прототип.

Подаём ему:

struct COver {
    virtual int f(int);
    virtual int f(long);
};

int (COver::*first)(int) = &COver::f;
int (COver::*second)(long) = &COver::f;

Здесь точный тип указателя однозначно выбирает перегрузку.

В использованном варианте Itanium C++ ABI представление указателя на виртуальный метод содержит смещение соответствующего слота, закодированное с добавлением единицы, и отдельную поправку к this. 

В проверочной программе нет реализаций f() и нет экземпляра COver. Тем не менее она собирается, а из представления указателей получаются позиции:

Порядок объявлений	Слот f(int)	Слот f(long)

int, затем long	0	1
long, затем int	1	0


Результаты прототипа.

Зачем это именно твоему проекту

В текущем разборе виртуальных таблиц есть потеря информации: некоторые записи сокращаются до COver::f, без параметров. Две переставленные перегрузки тогда выглядят одинаково. Подробности проверки, включая различие формата дампов GCC 14 и ожидаемого старого формата, вынесены в отчёт.

Предлагаемый путь:

Подтверждённые сигнатуры из заголовка
                  ↓
Автоматически созданные указатели на точные перегрузки
                  ↓
Компилятор выдаёт позиции слотов
                  ↓
Сопоставление с таблицей оригинального ELF

Так можно отсеивать часть ошибок заголовка до написания всех методов, вместо выяснения причин падения после запуска гибрида.

Это ещё не универсальный валидатор: проверен простой случай x86-64. Сложное наследование, деструкторы, ковариантные возвращаемые типы и исходный GCC 4.4.7 требуют отдельных проверок. Неизвестные сигнатуры этот способ сам не восстанавливает.

Но основная возможность уже подтверждена: для получения точного слота реализации метода не понадобились.

4. Массовая очередь исключает частично написанные и крупные файлы

Это ограничение охвата, которое легко принять за отсутствие подходящей работы.

В parallel.candidates() исходный файл не попадает в очередь, когда:

decomp/src/<имя>.cpp уже существует

Либо когда суммарный размер соответствующих функций превышает:

60 000 байт

При первой проверке не выясняется, сколько функций файла уже восстановлено и принято.

У draft_trial.py --all похожее ограничение: он рассматривает файлы, которых ещё нет среди существующих .cpp. Явно указать конкретный файл можно; проблема именно в поведении массового режима. Кодовые ссылки и проверка очереди.

Что это означает

Если в большом файле восстановлено несколько функций, сам факт появления файла может исключить весь остальной его объём из автоматического выбора.

А после улучшения преобразователя --all не обязательно попробует новые правила на оставшихся функциях частично написанных файлов.

В исторической выборке из 666 крупных функций под объединение этих двух ограничений по расположению файлов попадают 348 записей, или около 1,4 МБ машинного кода. Среди крупных единиц — character.cpp, level.cpp, gameui.cpp, inventorymenu.cpp.

Это не 348 новых свободных задач и не текущий остаток. Часть могла быть восстановлена; актуальных результатов других работников в архиве нет. Числа показывают, почему эта очередь не представляет всю оставшуюся игру.

Как изменить подход

Вычислять остаток по разности:

Ожидаемые функции исходного файла
                минус
Свежие подтверждённые определения и результаты приёмки

А не по наличию имени .cpp.

Сам файл нужно сохранить единицей компиляции и интеграции: не разрушать исходный контекст, не добавлять заглушки и не разрешать нескольким работникам одновременно его переписывать. Функциональную разность использовать внутри автоматического планирования, без нового ручного реестра стадий.

Это не ускорение одного преобразования, а расширение объёма работы, до которого автоматизация вообще добирается.

5. Автоматически сокращать неудачные черновики до причины ошибки

Ещё одна идея, которую удалось проверить небольшим прототипом: не просматривать огромную диагностику целиком, а заставить инструмент оставить минимальный фрагмент, вызывающий именно эту ошибку.

Процесс:

Неудачный черновик
        ↓
Автоматическое удаление ненужных частей
        ↓
После каждого удаления — проверка сохранения конкретной ошибки
        ↓
Короткий воспроизводимый пример
        ↓
Группировка повторяющихся причин и исправление общего правила

Я написал простой сокращатель без LLM. Подал ему 82 строки: 80 посторонних объявлений и показанную ошибку с const.

Получились две строки:

struct CProbe { int x; int get() const; };
int CProbe::get() { return x; }

Потребовалось 34 вызова компилятора для проверок условия, включая контрольные. Удаление любой оставшейся строки уже не сохраняет нужную ошибку. Возвращение const исправляет сборку. Результат сокращения.

Ключевое условие: проверялось не просто «компилятор завершился с ошибкой», а конкретное несоответствие объявления CProbe::get(). Иначе сокращатель мог бы оставить любую синтаксическую поломку.

Для более серьёзного сокращения C/C++ существует C-Reduce, предназначенный именно для уменьшения программы с сохранением заданного свойства. В этом проходе я использовал собственный ограниченный прототип, не запускал C-Reduce. 

Где здесь большой практический смысл

Вместо:

Сотни неудачных функций → сотни отдельных разборов

получить:

Сотни неудачных функций
        ↓
Короткие примеры
        ↓
Несколько повторяющихся причин
        ↓
Несколько исправлений генератора
        ↓
Автоматический повтор затронутых функций

Это пока предлагаемый процесс, а не измеренное распределение твоих ошибок. Но показанные случаи с квалификаторами, перегрузками и переписыванием выражений — конкретные причины, которые имеет смысл искать таким способом.

Что я бы поставил следующим

Сначала — перестать терять известную информацию и создавать новые расхождения при преобразовании. Затем проверять заголовки до массовой генерации и расширить очередь на реальный остаток частично восстановленных файлов.

Следующая автоматизация — сохранять и сокращать неудачные случаи, чтобы исправлять причины централизованно. Это дополнение к прежним идеям про распознавание контейнерных конструкций и проверку эквивалентности, а не их замена.

Главный вывод этого прохода: ускорять нужно не только получение правильного кода, но и устранять механизмы, которые повторно превращают уже известные сведения в ручную задачу.

Скачать четвёртый отчёт, четыре сценария проверки и патч сохранения квалификаторов.

Все компиляционные эксперименты выполнены на синтетическом C++98 с системным GCC 14.2. Исходные файлы архива побайтно не изменились; полного запуска игры и измерения общего ускорения не было.
