# OpenTorchlight: седьмой проход — восстановление операций из библиотечного исходника и данных

## Границы проверки

Исходный материал: `OpenTorchlight-main(4)(1).zip`. Анализ выполнен над распакованной копией, без правок проекта. Сопоставление SHA-256 всех 2285 файлов с ZIP не выявило изменений; повторный запуск также не изменил входную папку. Оригинальный ELF, исходный GCC 4.4.7 и игра здесь не запускались. Все компиляционные эксперименты выполнены системным GCC 14.2, режим GNU C++98. Ни одной новой игровой функции в принятом состоянии этот проход не объявляет.

Это развитие предыдущих идей о структурном распознавании операций, но с новыми конкретными целями и прототипами. Не предлагается новая архитектура игры, универсальный runtime или помещение непроверенных реализаций в `decomp/src`.

| Новый узкий этап | Что получено | Что ещё не получено |
|---|---|---|
| Библиотечный адаптер → штатное C++-выражение | 89 полных заготовок, 81 типизированный кандидат с точным callback-символом; проверка настоящим CEGUI | Эквивалентность оригинальной подписки, её времени жизни и исключений |
| Чтение ресурса → ключ, default, назначение | 558 ассоциаций с ключами, 18 кандидатов сохранения текущего bool-поля | Доказательство достигающего определения по CFG/SSA и приёмка игрового кода |
| Глобальные справочники → логические значения → C++ | 10 связанных таблиц с вероятной общей размерностью 145; работающий генератор и обратная проверка на синтетике | Значения оригинальных таблиц и эквивалентность их инициализации |

## 1. Библиотечный исходник как обратный шаблон для объектов-адаптеров

### Чем отличается от существующих инструментов

В проекте уже есть `tools/extract_menu_wiring.py`, который извлекает сведения о подписках для исторического анализа. Не следует объявлять поиск подписок новой идеей. Новый шаг — восстановить конкретное выражение штатного C++ из содержимого объекта-адаптера, пользуясь закреплённым библиотечным исходником, и отдельно проверить это выражение компилятором.

Опорные файлы:

- `third_party/cegui-0.6.2/include/CEGUIMemberFunctionSlot.h`, класс `MemberFunctionSlot<T>`: `d_function`, `d_object`, конструктор и `operator()`.
- `third_party/cegui-0.6.2/include/CEGUISubscriberSlot.h:106–109`: шаблонный конструктор сам создаёт `new MemberFunctionSlot<T>(function, obj)`.
- `third_party/cegui-0.6.2/src/CEGUISubscriberSlot.cpp`: деструктор пуст; удаление выполняет `cleanup()`. Нельзя автоматически трактовать конец области видимости SubscriberSlot как освобождение адаптера.
- `CEGUIEvent.cpp` и `CEGUIBoundSlot.cpp`: копирование подписчика, хранение соединения и освобождение требуют отдельного анализа.

В `research/decompiled-core/inventory_menu.c:8892–8901` видны выделение 32 байт, запись vptr адаптера, указателя на `handle_CloseButton`, нулевой поправки к `this`, затем самого `this`. Символы оригинала позволяют установить специализацию `MemberFunctionSlot<CInventoryMenu>`.

Кандидат только на создание соответствующего подписчика:

```cpp
CEGUI::SubscriberSlot(&CInventoryMenu::handle_CloseButton, this)
```

Это не автоматически восстановленная вся строка `subscribeEvent`, не доказанное владение и не разрешение удалить все соседние конструкторы/деструкторы.

### Прототип и покрытие

`tools/binding_recipes.py` ищет выделение `operator_new(0x20)` и четыре непосредственно следующие уникальные записи полей, не переходя через ветвления или блоки. Поддерживает разный порядок четырёх записей; неполные и дублирующиеся записи отвергает. Vptr сопоставляется с `original-symbols.txt`, а не с похожестью имени функции.

В архиве:

- 2630 уникальных экспортированных функций;
- 18 найденных специализаций vtable;
- 107 маркеров vptr в черновиках;
- 89 полных заготовок в 17 функциях;
- 81 именованный callback и 8 закодированных виртуальных указателей на метод;
- 81 кандидат на выражение, для каждого найдена точная сигнатура `Owner::method(CEGUI::EventArgs const&)` в символах оригинала;
- 9 классов-получателей среди выражений.

Наиболее многочисленные места: `CGameUI::create` — 17, `CInventoryMenu::createMenus` — 16, `CPetMenu::createMenus` — 16, Merchant/Stash — по 8. Это количество адаптеров в исторических черновиках, а не новых функций и не актуальная очередь работ.

### Виртуальные методы и поправка к this

В `inventory_menu.c:2697–2708` есть числовое представление `0x59`. Для стандартного x86-64 представления Itanium ABI виртуальный указатель на метод хранит 1 плюс байтовое смещение слота. Здесь это `0x58 / 8 = 11`. Прототип сохраняет этот факт, но не придумывает имя метода.

При множественном наследовании отдельная поправка к `this` может быть ненулевой. В синтетической проверке с реальным CEGUI получены поправка 16, код виртуального указателя 17, правильный вызов производного переопределения и правильный прямой вызов. Это проверка ABI-класса случая, не layout оригинальных игровых классов.

`tools/check_cegui_recipes.py` компилирует все 81 выражение с настоящими заголовками и `CEGUISubscriberSlot.cpp` из архива. Классы-получатели и тела callback — специально созданные тестовые реализации. Два результата EventArgs для каждого выражения дали 162 проверки, ошибок 0. Проверено соответствие структуры выражения интерфейсу библиотеки и диспетчеризация на синтетических объектах, а не поведение реальных игровых обработчиков.

Следующий производственный этап: связать рецепт с точными SSA-значениями, подпиской, владением и exceptional edges, затем проверять кандидат исходным компилятором/гибридом. Применять такое сворачивание по одному объекту без проверки всех использований нельзя.

## 2. Восстановление схемы чтения ресурсов внутри игровой логики

### Не просто словарь строк

Полезный результат содержит не только ключ, а также источник данных, реальный default, поле назначения, выбранную перегрузку, порядок и условие выполнения. Это позволяет автоматически получить обычные C++-операции чтения вместо повторного ручного разбора временных строк и локальных переменных.

`tools/resource_recipes.py` связывает `GetDataValue` с последним предшествующим конструктором **той же локальной строки**, а не ближайшим любым литералом. Аргументы разбираются со скобками; строки/комментарии не принимаются за код. Но это текстовый прототип: связь через ветвления и повторное использование stack slot ещё не доказана. Поэтому все строки имеют статус CANDIDATE_ONLY.

Результат: 581 распознаваемый вызов с тремя явными аргументами, 558 кандидатов связи с литеральным ключом, 421 различный литерал, 80 функций, 18 случаев копирования текущего bool-поля в default с последующей записью в то же поле. Не все встречающиеся в архиве GetDataValue имеют распознанную сигнатуру; 581 — покрытие именно данного детектора.

В агрегировании по имени функции: `CLevelTemplateData::load` — 78 ключевых чтений, `CGameGlobals::reload` — 55, `CCharacter::unitInit` — 50, `CSkillEvent::CSkillEvent` — 41. Перегрузки в таком отображении могут объединяться; JSON сохраняет адрес каждого места.

### Конкретный пример CEffect

`research/decompiled-core/effect.c:4178–4183`:

```cpp
CVar17 = this[0x33];
std::wstring::wstring(local_108, L"SAVE", ...);
CVar17 = CDataGroup::GetDataValue(param_1, local_108, (bool)CVar17);
this[0x33] = CVar17;
```

Аналогичные случаи: `USEOWNERLEVEL`, смещение 0x36, строки 4195–4200; `EXCLUSIVE`, смещение 0x31, около 4212–4217.

Выданные кандидаты:

```cpp
field_33 = param_1->GetDataValue(L"SAVE", field_33);
field_36 = param_1->GetDataValue(L"USEOWNERLEVEL", field_36);
field_31 = param_1->GetDataValue(L"EXCLUSIVE", field_31);
```

Имена field_XX технические, не утверждение о первоначальном названии поля. Перегрузку, размер поля, implicit temporary, исключения и initValues требуется подтвердить. Default здесь берётся из текущего состояния, а не автоматически равен false. Значение могло быть установлено конструктором или предшествующими настройками.

### Ограниченная исполняемая проверка

`examples/resource_default_test.cpp` содержит три выданные строки; `run_checks.py` проверяет наличие этих выражений среди рецептов реального CEffect. Реализация Group — синтетическая модель bool-lookup, не оригинальный CDataGroup.

Для трёх ключей есть состояния отсутствует/false/true, а для трёх полей — восемь начальных комбинаций: 27 × 8 = 216. Сохранённый default: 0 расхождений. Подмена каждого default на false: 91 расхождение. Это исчерпывающий тест конечной модели, не доказательство всего игрового конструктора.

Рабочий этап должен переносить связь по графу данных: какой конструктор строки действительно достигает вызова, какие записи памяти и вызовы могут менять default, при каком условии производится запись. Чтения нельзя переставлять, объединять по одинаковому ключу или переименовывать поля исключительно по тексту ключа.

## 3. Сначала восстановить данные, которые управляют кодом

### Конкретный непокрытый класс таблиц

`decomp/include/EffectDefines.h:18–21` оставляет EEFFECT_TYPE пустым. `decomp/src/EffectsHeader.cpp` не содержит исследуемые таблицы. Текущий `tools/decomp/name_tables.py:39` выбирает глобальные записи с `bind == local`; десять ниже — глобальные BSS-символы с типом nm `B`, так что этот механизм их не охватывает. Это граница охвата, а не автоматически ошибка инструмента.

В `research/original-symbols.txt:29531–29540`:

| Имена | Размер каждого | Гипотеза формы |
|---|---:|---|
| gEFFECT_TYPE_NAMES; четыре DESCRIPTIONS_GOOD/BAD и их OT-варианта | 0x488 | 145 строк |
| gEFFECT_TYPE_MIN_VALUES, MAX_VALUES, BONUS | 0x244 | 145 32-битных значений |
| gEFFECT_TYPE_PROPERTY_TAGS, GRAPHS | 0x16a8 | 145 × 5 строк |

Суммарно 19140 байт хранения объектов/чисел, **не полный объём их строковых данных**. Для строк использована гипотеза sizeof(std::wstring)==8 в старом ABI; для чисел гипотеза int32. Типы и данные требуют проверки.

Независимые признаки в `effect.c`:

- 4015–4026: последовательный поиск по gEFFECT_TYPE_NAMES с пределом `0x91`, то есть 145;
- 4021: найденный индекс записывается в поле типа эффекта; при неуспехе сохраняется предыдущее значение;
- 4420–4422: индексирование GRAPHS как `type * 5 + column`;
- 4450–4454: PROPERTY_TAGS индексируется так же и используется именно как ключ GetDataValue.

Это связывает строки таблиц, числовые типы и ключи параметров. Но фактические 145 названий **не извлечены**: в отчёте JSON у значений `null`. Символ `global constructors keyed to gEFFECT_TYPE_NAMES`, адрес 0xd603f0, указывает на связанный этап статической инициализации; наличие имени не доказывает, что всё содержимое неизменно или вычисляется только этой короткой функцией.

### Предлагаемый новый этап

1. В контролируемом оригинальном/hybrid окружении установить точку после нужной статической инициализации.
2. Выгрузить известные типы как логические значения: содержимое строк плюс длина, числа, порядок, размеры таблиц. Не копировать сырые указатели std::wstring.
3. Проверить, какие записи/внешние данные влияют на инициализацию и изменяются ли таблицы позднее.
4. Сгенерировать естественные C++-определения в исходном TU и проверить результат собственной сборки обратной выгрузкой.
5. Использовать подтверждённые соответствия строк и индексов как факты для анализа кода. Если конструкторы имеют значимые побочные эффекты, восстановление значений не заменяет восстановление этих конструкторов.

BSS в файле не содержит уже созданные объекты строк. Снимок одного запуска тоже не доказывает независимость от locale, ресурсов, порядка инициализации, файлов и окружения. При неопределённости данные пригодны как проверочные наблюдения, а не автоматически принятый исходник.

### Проверенный генератор и что он не делает

`tools/snapshot_to_cpp.py` принимает **готовый логический JSON**, а не адрес процесса. Поддерживает wstring/int32 и до трёх измерений. Сохраняет пустые строки, встроенный NUL через явную длину, управляющие символы, кириллицу, non-BMP, порядок и signed int32 endpoints. Неизвестные ячейки, указатели, неверные code points и неподдержанные типы отвергаются. Это не новый runtime игры.

`tools/check_snapshot_roundtrip.py`: синтетические C++-таблицы проходят настоящую статическую инициализацию → JSON → генерацию C++ → новую статическую инициализацию → JSON. Для трёх таблиц и 18 ячеек (14 строк) получено точное совпадение. GCC14.2 с `_GLIBCXX_USE_CXX11_ABI=0` дал sizeof(wstring)=8, sizeof(wchar_t)=4. Этот переключатель включает старый интерфейс libstdc++, **не превращает GCC14.2 в GCC4.4.7** и не обеспечивает бинарную эквивалентность.

Игра при этой проверке не выполнялась. Захват реальных gEFFECT_TYPE_* ещё нужно реализовать/выполнить там, где есть оригинал.

## 4. Порядок внедрения и критерий полезности

Первый небольшой пилот — три чтения CEffect и несколько аналогичных шаблонов: перенести прототип в типизированный граф, сохранить default/условия/перегрузку, проверить весь окружающий метод. Второй — один адаптер CInventoryMenu до полной подписки и владения, затем те же правила на остальные формы. Третий — связанный набор gEFFECT_TYPE_*, поскольку он разрешит не только определения данных, но и часть динамических ключей и числовых ветвей.

Результат следует измерять новыми принятыми реализациями и остатком ручных решений. Число найденных рецептов и синтетические проверки не дают общего коэффициента ускорения. Для неподдержанных случаев обязательны отказ от преобразования или UNKNOWN, а не догадка.

Непроверенные файлы не помещать в decomp/src: существующий гибрид подставляет определения оттуда. Интеграция должна сохранять исходные TU, классическую C++-форму и существующие механизмы приёмки.

## 5. Воспроизведение

Из каталога этого отчёта:

```sh
python3 tools/run_checks.py /полный/путь/OpenTorchlight-main
```

Нужны Python 3.10+ и GNU g++. CEGUI берётся из исходного архива пользователя, в поставку прототипов не копируется. Команда пишет только собственный results; входная папка проверяется хешами до и после. Игра не запускается. В архив поставки включены исходники и JSON, но не скомпилированные исполняемые файлы.

28 unit-тестов покрывают отбрасывание неполных адаптеров, виртуальные смещения/поправки, строки с псевдокодом, выбор правильной локальной строки, сохранение default, ошибки типов и размеров логического снимка. Исполняемые C++-проверки описаны отдельно выше. Исходные JSON сохранены без округления или ручной подмены результатов.
