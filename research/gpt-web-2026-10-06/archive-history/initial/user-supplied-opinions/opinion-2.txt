Да. **После второго прохода я бы изменил порядок работ: прежде чем строить большой генератор шаблонов, стоит перестать терять уже имеющуюся информацию о C++ — и научиться автоматически связывать её между функциями.**

Нашёл несколько новых направлений, а также конкретные ограничения инструментов. Часть проверил отдельными воспроизводимыми примерами, а не только чтением кода.

## 1. Самый близкий резерв: полноценная передача типов в Ghidra

В предыдущем ответе я отметил, что импорт прототипов у тебя уже существует. Это верно, **но наличие импортёра ещё не означает, что вся важная информация доходит до декомпилятора.**

В текущем архиве обнаружились такие потери:

| Что уже известно | Что происходит при передаче в Ghidra |
|---|---|
| Таблицы виртуальных методов | Слоты создаются как `void*`, без сигнатуры функции |
| Несколько таблиц у класса с несколькими базами | Экспортируется только первая группа |
| Полное имя типа с пространством имён | Экспортёр использует короткое имя, возможны столкновения |
| Размер `long` из отладочной информации | Одна из веток импортёра превращает его в 32-битный `int`, игнорируя размер |

Это установлено по `types_export.py` и `DecompDrafts.java`; воспроизведения и конкретные места собраны в REPORT_RU.md[отчёте второго прохода](sandbox:/mnt/data/OpenTorchlight_deeper_no_llm/REPORT_RU.md).

### Почему это влияет именно на скорость восстановления

Допустим, внутри большой функции вызывается виртуальный метод. Известен объект, известно положение метода в таблице, известен его прототип. Но если слот передан декомпилятору как `void*`, **часть этой информации приходится восстанавливать заново на месте вызова**.

Я бы передавал не просто название слота, а его полноценное описание: параметры, результат, скрытые параметры, положение базового подобъекта и необходимые поправки к `this`. Для представления указателей на функции в Ghidra уже есть `FunctionDefinitionDataType`; отдельный механизм типов изобретать не требуется. [Ghidra](https://ghidra.re/ghidra_docs/api/ghidra/program/model/data/FunctionDefinitionDataType.html)

Причём речь не только про UI. В актуальных заголовках я нашёл **23 объявления классов с несколькими базами**, включая `CCharacter`, `CEquipment`, `CSkill`, `CDamageShape` и `CGameClient`. Поэтому ограничение первичной таблицей потенциально затрагивает и игровые механики.

При этом нельзя заменять виртуальный вызов конкретной реализацией только потому, что найден один подходящий класс: динамический тип объекта может быть другим. Нужно восстанавливать типизированный виртуальный вызов, а не произвольно убирать виртуальность.

### Проверка со столкновением типов

Я скомпилировал небольшой пример:

```cpp
namespace First  { struct Cell { int a; }; }
namespace Second { struct Cell { double b; long c; }; }
```

В настоящей отладочной информации это два разных типа размером **4 и 16 байт**. Твой экспортёр оставил один `Cell` размером 16, а указатели на оба типа записал как `Cell*`.

Это **не доказательство, что в уже восстановленной игре есть именно такой конфликт**. Но воспроизводимое ограничение схемы экспорта есть.

**Мой вывод: сначала сделать передачу типов без потерь. Это более прицельная работа, чем исправлять последствия плохих типов отдельно в сотнях черновиков.**

## 2. Восстанавливать типы не по одной функции, а как систему взаимосвязанных ограничений

Это уже не просто ремонт импортёра, а самостоятельное направление автоматизации без LLM.

Сейчас `layout.py` собирает полезные подсказки по обращениям к полям, размерам операций и вызовам. Я бы дополнил это **общим анализом связей между полями, параметрами и результатами нескольких функций**.

Условный пример:

```text
В функции A из неизвестного поля загружается указатель.

В функции B этот указатель передают в подтверждённый метод CInventory.

В функции C в то же поле записывается результат создания CInventory.

В функции D через него вызывают известный виртуальный метод.
```

По отдельности каждый фрагмент оставляет неопределённость. Вместе они могут однозначно определить тип поля — либо обнаружить, что первоначальная гипотеза неверна.

Дальше возникает полезный цикл:

```text
Уточнили поле
     ↓
Улучшились типы в нескольких функциях
     ↓
Стали понятнее их параметры и результаты
     ↓
Уточнились другие поля и вызовы
     ↓
Повторная декомпиляция зависимых функций
```

**Вместо тысячи независимых догадок получается одна связанная задача.**

Для такого подхода уже существуют ненейросетевые реализации: **Retypd** и **BTIGhidra**. Retypd работает с ограничениями типов, а его Ghidra-плагин извлекает их из высокоуровневого p-code и возвращает выведенные типы в базу. BTIGhidra также предназначен для восстановления и применения типов с учётом подтипов и полиморфизма. [GitHub](https://github.com/GrammaTech/retypd)

Я бы не подключал их сразу ко всей рабочей базе. Сначала — копия проекта и ограниченная группа взаимосвязанных классов. Совместимость с твоей версией Ghidra и качество на Torchlight здесь не проверены.

### Дополнительный источник ограничений у тебя уже есть

Существующие `AddProperty`, `Get_…` и `Set_…` можно использовать **не только для генерации дескрипторов, но и для восстановления остальных классов**.

Например, связать название свойства, тип значения, getter/setter и обращения к конкретному смещению объекта. Полученные сведения затем распространять на все методы, работающие с этим полем.

Новое здесь — не ещё один генератор однотипных функций, а использование уже разобранных свойств как опорных данных для всего остального кода.

Важное ограничение: конфликтующие факты должны оставаться конфликтующими. Автоматический анализ не должен выбирать «самый похожий тип» и незаметно объявлять его правильным.

## 3. Существенно недооценённый источник: таблицы исключений и время жизни объектов

**В бинарнике есть сведения не только о том, что функция делает, но и о том, что она обязана уничтожить при ошибке.** Для восстановления C++ это может быть очень полезно.

Механизм исключений использует обработчики и пути очистки; соответствующие таблицы вместе с машинным кодом позволяют установить, какие действия выполняются при выходе через исключение. Это часть ABI, а не эвристика декомпилятора. [itanium-cxx-abi.github.io](https://itanium-cxx-abi.github.io/cxx-abi/abi-eh.html)

Почему я обращаю на это внимание: в твоём конвейере сейчас есть текстовая очистка обслуживания строк и удаление комментариев из вывода Ghidra. Но **убрать служебный код из текста и восстановить исходную структуру владения объектами — разные задачи**.

Я бы делал следующее:

```text
Конструкторы и обращения к объектам
                  +
Таблицы исключений и пути очистки
                  +
Граф переходов
                  ↓
Кандидат на области жизни локальных объектов
                  ↓
Обычные C++-объекты, области видимости и try/catch
                  ↓
Компилятор сам создаёт обслуживающий код
```

Это особенно интересно для больших функций, где много временных строк, контейнеров и последовательного создания объектов.

### Здесь у тебя уже есть подтверждённый пример

В `research/ui-function-bindings.md` сохранён разбор `CGameUI::mapToFunctions`: по таблице исключений установлен `catch (...)`, причём рекурсивный обход находится **вне** защищённой области работы со свойством.

Это важное различие: внешне похожие варианты расположения `try` будут по-разному обрабатывать ошибки. Получается, нужная информация уже однажды извлекалась вручную. Следующий шаг — систематизировать её извлечение.

В Ghidra уже есть классы для разбора `LSDATable`, таблицы защищённых вызовов, действий и типов исключений. **Парсер формата необязательно писать с нуля.** Но готового восстановления областей жизни объектов эти классы сами по себе не дают — эту часть нужно связывать с анализом кода. [GitHub](https://github.com/NationalSecurityAgency/ghidra/blob/master/Ghidra/Features/Base/src/main/java/ghidra/app/plugin/exceptionhandlers/gcc/structures/gccexcepttable/LSDATable.java)

Я бы добавил к экспорту черновика структурированные сведения об исключениях, а не оставлял их только в комментариях и отдельных исследовательских документах.

Здесь нельзя просто удалять всё, что выглядит как «хвост функции»: общий код очистки может использоваться несколькими путями, а одна стековая ячейка — разными объектами в разные моменты.

**Из новых направлений это один из наиболее интересных кандидатов на автоматическое сокращение сложности больших функций.** Не ускорение чтения длинного псевдокода, а восстановление компактных C++-конструкций, которые этот псевдокод породили.

## 4. Автоматически сопоставлять две сборки движка — у тебя уже есть основа

В предыдущем ответе я недооценил содержимое `research/torched-sdk.*`.

В архиве сохранён разбор второй сборки: **`Core.dll` из TorchED**. В JSON зафиксированы:

- **302 класса движка**, имена которых найдены и в Linux-оригинале;
- **193 экспорта** родной DLL;
- **196 записей P/Invoke** из управляемой оболочки редактора.

Это не новые измерения бинарников: я перечитал сохранённые результаты. Самих `Core.dll` и оригинального ELF в присланном архиве нет.

Главная идея — **использовать вторую сборку как ещё одно представление исходной программы**, а не просто вручную читать её при затруднениях.

Например, гипотетически:

```text
В Linux большой метод содержит встроенный обход контейнера.

В другой сборке аналогичный обход остался отдельным helper.

Сопоставление помогает выделить границу операции в Linux-методе.
```

Или другая сборка позволяет лучше увидеть, как значение проходит между вызовами и какой тип результата действительно используется.

Для автоматического поиска кандидатов подходит BSim: он штатно ищет структурно похожие функции между архитектурами, компиляторами и небольшими изменениями исходника. Но сходство — лишь способ найти кандидата, не доказательство одинакового поведения. [Ghidra](https://ghidra.re/ghidra_docs/GhidraClass/BSim/README.html)

### Как я бы использовал это именно у тебя

Начинать с надёжных опорных точек: экспортов, RTTI, уникальных строк, констант и уже известных вызовов. Затем распространять соответствия по соседям в графе вызовов.

Дальше искать не только соответствие «функция целиком — функция целиком», но и случаи, где отдельная функция одной сборки соответствует участку другой.

**Не нужно восстанавливать Windows-версию целиком.** Она нужна как вспомогательный источник для конкретных трудных мест Linux-версии.

Ограничения существенные: редакторская конфигурация, возможная другая ревизия, другая архитектура и ABI. Нельзя переносить Windows-смещения полей в Linux или считать редакторскую ветвь игровым поведением. Метаданные P/Invoke тоже нужно интерпретировать с учётом правил передачи данных между управляемым и родным кодом.

В проверенных инструментах действующего `decomp` я не обнаружил прямой интеграции этих SDK-данных. **То есть это уже не идея «найти ещё какой-нибудь источник», а возможность лучше использовать источник, который у тебя ранее исследован.**

## 5. Перед массовой автоматизацией нужно усилить проверку правильности — здесь нашлись реальные контрпримеры

Это не отдельная придирка к качеству. **Без надёжной автоматической приёмки любой генератор начнёт экономить время на написании кода и тратить его обратно на поиск незаметных расхождений.**

В прошлом ответе я слишком безоговорочно опирался на существующий `MATCH`. После проверки это нужно уточнить.

### Разные длинные строки могут считаться одинаковыми

В `objdiff.py::literal_token` в токен сравнения попадают только первые **80 символов** строки.

Я собрал две функции, которые передают в `sink` разные строки:

```text
80 букв A + X
80 букв A + Y
```

И пропустил полученные object-файлы через настоящий `objdiff.object_functions` из твоего архива.

Результат: **нормализованные тела и `code_digest` совпали**. Контрольное изменение первого символа инструмент обнаружил.

Исправление принципиальное, но локальное: сокращать строку можно для отображения, **не для сравнения**. В ключе должны участвовать полное содержимое либо его хеш, длина и необходимая информация о представлении.

### Одинаковые инструкции не гарантируют одинаковую обработку исключений

Второй пример:

```cpp
try {
    raise_value();
} catch (int) {
    return 7;
}
```

И аналогичная функция с `catch (double)`.

Я скомпилировал обе. Вызываемая функция бросает `int`; внешний проверочный код ловит неперехваченное исключение и выдаёт 99.

| Проверка | Результат |
|---|---|
| Нормализованные инструкции исследуемой функции | Совпали |
| `code_digest` | Совпал |
| Выполнение варианта `catch(int)` | 7 |
| Выполнение варианта `catch(double)` | 99 |

Различие находится в данных обработки исключений, вне сравниваемого потока инструкций. Механизм выбора обработчика действительно опирается на такие сведения. [itanium-cxx-abi.github.io](https://itanium-cxx-abi.github.io/cxx-abi/abi-eh.html)

**Оба примера воспроизведены системным GCC 14.2 на синтетическом коде. Это не запуск оригинальной Torchlight и не доказательство ошибки в конкретной уже принятой игровой функции.** Проверены именно функции нормализации, по равенству результатов которых `compare_source` принимает решение о `MATCH`. probe-results.json[Результаты проверок](sandbox:/mnt/data/OpenTorchlight_deeper_no_llm/probe-results.json).

Следовательно, для функций с исключениями нужно учитывать и нормализованные таблицы обработчиков. А отпечаток, разрешающий повторно использовать прежний результат тестирования, тоже не должен игнорировать их изменения.

### Ещё одна граница: гибрид и самостоятельный исходник

Твой гибрид намеренно использует оригинальные глобальные данные и виртуальные таблицы. Это удобно для проверки восстановленных методов, но **успех в гибриде не подтверждает, что восстановлены данные и инициализация для самостоятельной сборки**.

Я бы автоматически показывал, какие зависимости ещё предоставляет оригинал: таблицы, глобальные объекты, RTTI, виртуальные таблицы, инициализаторы. Не новый ручной реестр на каждую функцию, а машинный отчёт по реальным ссылкам.

Иначе можно быстро восстановить множество тел, а в конце обнаружить большой неучтённый остаток.
