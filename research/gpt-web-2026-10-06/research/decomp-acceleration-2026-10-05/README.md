# Эксперимент: точные сигнатуры импортов Ogre/CEGUI

Дата: 5 октября 2026. Основа: проверенное объединение 1f53aaa, исходный ELF
91b41ae9dfea30aab6bc14dbbfcceaee096d600f39635b8507f5a88b5d41724b.

## Короткий вывод

Найдено полезное автоматизируемое исправление подготовки черновиков. Оно
восстанавливает потерянные аргументы библиотечных вызовов, но пока НЕ доказывает
двукратного ускорения ручного восстановления и не принимает целые функции.

Новый конвейер 2464d59 экспортирует прототипы игровых методов, но не покрывает
1004 импортированных PLT-адреса. В этом эксперименте рассмотрены 491 импорт
Ogre/CEGUI: из исходных заголовков извлечены 418 деклараций, 399 допущены фильтром поддерживаемых ABI-форм, 398 дополнительно применились в Ghidra. Прочие импорты
(например, FMOD/libc) здесь не обрабатывались.

## Результат на фиксированном наборе

Четыре ещё не принятые функции, всего 29534 байта оригинала:
- CGenericModel::reInitialize, 0x8ac190, 11058 байт
- CAutomap::setFullMap, 0x92b4b0, 2676 байт
- CPetMenu::updateLayout, 0xba26b0, 10957 байт
- CShape::updateVisual, 0xa06b30, 4843 байта

Отрицательный контроль: принятая CEquipment::getMaxSockets, 0x87f880, без SDK-вызовов.
Её экспорт остался побайтовно неизменным.

В 263 вызовах с однозначно сопоставленными SDK-именами (66 разных имён) число
аргументов соответствовало декларации лишь в 17 случаях исходного экспорта.
После обогащения все 263 соответствуют ожидаемому числу: 246 несовпадений → 0.
Это проверка формы вызова, НЕ доказательство корректности всех значений,
времени жизни объектов или функции целиком.

Конкретный пример CPetMenu: исходный Ghidra-текст выводил getSize() вообще без
аргументов; новый вывод содержит адрес результата и окно. Возврат UDim/UVector2
через скрытый указатель проверен также сборкой небольших вызовов оригинальным
GCC по настоящим SDK-заголовкам. Проверены примеры обычного this, статического
вызова, скрытого возврата, float и возврата ссылки.

Время последнего экспорта пяти функций: около 13.76 с для исходного варианта и
12.65 с для обогащённого. Это один последовательный замер с возможным эффектом
прогрева, поэтому процент ускорения из него НЕ выводится. Суммарный сырой текст
четырёх функций изменился с 3682 до 3677 строк; существенного сокращения нет.
После прежнего C++-преобразователя текст даже немного длиннее (2313 → 2343 строк).

## Проверка пути к C++

Существующий преобразователь не всегда превращает восстановленные SDK-вызовы
в правильные C++-вызовы методов. Добавлен отдельный узкий rewrite_geometry.py:
- только getWidth/getHeight/getSize/setSize/setPosition у CEGUI::Window
- только ожидаемое число аргументов и простые выражения без побочных эффектов
- скрытый результат превращается в присваивание
- явная квалификация сохраняет прямой вызов, не вводит виртуальную диспетчеризацию
- неоднозначные случаи, комментарии и строки не трогаются

На CPetMenu автоматически исправляются 13 таких вызовов. Микропример с пятью
вызовами не компилируется до исправления и компилируется после него настоящим
GCC/SDK; проходит и после существующего ghidra_cpp.convert. Шесть отрицательных
примеров остаются неизменными. Это НЕ компиляция и не приёмка четырёх полных
функций: для трёх из них даже нет законченного игрового заголовка/тела.

## Ошибки, которые нельзя пропустить

Первые два пилотных варианта были отброшены:
1. Квалифицированные пространства имён ошибочно делали static-вызовы методами
   с this. Исправлено чтением искусственного this-параметра непосредственно из DWARF
2. Псевдоним Ogre::Real оставался непрозрачным 4-байтовым типом; Ghidra принимала
   его за целое и теряла XMM-результаты. Теперь typedef разворачивается до float

В окончательном варианте лишние extraout-маркеры не появились ни в одной из
четырёх функций. Добавлены проверки этих двух ошибок. Имена завершённых GCC DIE
восстанавливаются через DW_AT_specification. Весь SDK-layout не подставляется:
ограниченный набор небольших структур избегает неоднозначных имён и массивов.
Неизвестные объекты, передаваемые по значению, и возвраты малых структур без
проверенного layout исключаются, чтобы не гадать о SSE-регистрах и скрытых ссылках.
Перечень 19 исключённых деклараций записан отдельно.

## Что стоит внедрять

Использовать такой экспорт как дополнительную подготовку черновиков с отдельным
списком применённых сигнатур и ABI-проверками. Самую узкую часть — геометрию CEGUI —
можно обсуждать для включения после ревью и расширения отрицательных тестов.
Сейчас tools/decomp не изменены этим экспериментом, автоматическая приёмка
отключена: никакие новые игровые функции по этим результатам не зачтены.

Следующий кандидат для отдельного опыта — распознавание конкретных встроенных
конструкторов CEGUI::String по исходникам именно 0.6.2 и исходному GCC. Прежняя
чистка в основном ориентирована на std::string; нельзя заменять всё подряд
регулярными выражениями и терять деструкторы, исключения или UTF-8-семантику.

## Воспроизведение

Из корня проекта с настроенными исходным ELF, SDK и GCC:
1. python3 research/decomp-acceleration-2026-10-05/export_sdk.py
2. python3 research/decomp-acceleration-2026-10-05/prepare_ab.py
3. python3 research/decomp-acceleration-2026-10-05/run_ab.py --project-dir PATH --project-name NAME --ghidra-home PATH --java-home PATH
4. python3 research/decomp-acceleration-2026-10-05/measure_calls.py
5. python3 research/decomp-acceleration-2026-10-05/convert_ab.py
6. python3 research/decomp-acceleration-2026-10-05/test_geometry.py

Обе ветки используют один сохранённый Ghidra-проект в read-only режиме, одинаковый
таймаут 600 с и предел ответа 128 МиБ. Базовый код DecompDrafts одинаков. Проверка
protoType(void), у которой есть отдельный вопрос к обработке нулевого размера,
не менялась ни в одной ветке, чтобы не смешивать два улучшения.

results/final содержит входы, экспорты, журнал и ASM; JSON рядом — измерения.
Пилотные неудачи сохранены отдельно. Проверки компиляции — локальные; запуск
игры/сохранений и изменения чужих TU не требовались.
