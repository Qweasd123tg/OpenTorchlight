# Инвалидация compiler cache при появлении заголовка, 6 октября 2026

Исследование сохранённого кода0abcd3c, без изменений production. Особенно связано с текущим ремонтом include-gen, но не дублирует генератор заголовков.

## Подтверждённый контрпример

Порядок поиска: -Ihand -Igenerated. Source включает Value.h. Сначала hand пуст, generated/Value.h задаёт VALUE=1. Компилятор выдаёт return1. Cache хранит source и реально использованный generated/Value.h.

Затем появляется hand/Value.h с VALUE=2. Ни команда, ни source, ни старый dependency-файл не изменились. Настоящие toolchain._cache_lookup/_digest возвращают старый object. Свежая компиляция той же командой выдаёт return2.

Использованы системный GCC14.2 и настоящий cache-reader проекта. Cache-index создан по существующей схеме в отдельной временной папке; production-cache не затрагивался. Оригинальный GCC4.4.7 для этого контрпримера не запускался. Результат доказывает недостаточность ключа cache, не наличие конкретного повреждённого игрового object-файла.

## Почему обычной перегенерации недостаточно

Кэш учитывает содержимое старого выбранного dependency, но не факт, что по новому порядку разрешения include должен выбираться другой файл. Перегенерация может случайно вызвать cache-miss, если изменит старый dependency; гарантии нет, когда тот остаётся побайтно тем же.

Поэтому возможна цепочка: headers исправлены → include-gen обновлён → компиляторный кэш вернул старый object → повторная диагностика опять видит старую ошибку или старое поведение.

## Варианты исправления

Быстрый консервативный: включать в compiler-cache key версию/контентный manifest снимка hand/include-gen/include-trial и toolchain identity. Manifest учитывает имена и добавление/удаление файлов, не только содержимое тех, что использовались ранее. Не менять его в процессе обработки одного снимка исполнителя.

Более точный: перед reuse заново получать dependency-graph текущим препроцессором и сравнивать разрешённые пути с содержимым, либо использовать fingerprint актуального препроцессированного входа. Цена - дополнительная работа препроцессора; выигрыш надо профилировать. Просто добавить mtime папки или хешировать прежний depfile недостаточно.

Это не рекомендация удалять кэш перед каждой функцией. Важно сделать его привязанным к корректному снимку и проверяемому разрешению include.

## Регрессионная проверка для агента на ПК

1. Собрать с единственным нижеприоритетным заголовком
2. Подтвердить cache-hit без изменений
3. Добавить одноимённый заголовок в более приоритетный каталог
4. Следующая компиляция должна дать cache-miss и новый результат
5. Проверить обратное удаление/переименование и неизменный повтор

probe_include_shadow.py проверяет пункты1-3 и демонстрирует ошибку пункта4 текущего сохранённого reader. Новая реализация кэша здесь не написана. Вывод инструкции приведён в include-shadow-results.json; бинарные объекты не приложены.
