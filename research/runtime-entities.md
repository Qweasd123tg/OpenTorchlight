# Сущности времени выполнения

> **Current combat-action patch:** ordinary player/enemy attacks now share
> description/clip/HIT execution; the old enemy `100 / ATTACKSPEED` gate is gone.
> Signed AI cooldown remains independent. See `ordinary-attack-action.md` and
> `../COMBAT_ACTION_RESULT_RU.md` for current code, test results and limitations.
> Earlier descriptions/test counts below are historical unless explicitly updated.


`RuntimeEntityWorld` превращает запросы объектов `Unit Spawner` в сущности с
устойчивым ID, исходным GUID мастер-ресурса, типом, именем, позицией и признаком
жизни. У монстра также сохраняются текущие и максимальные HP из полного
унаследованного определения `UNIT`. Для `GROUP=Spawn Class` сначала исполняется
рекурсивный класс создания,
после чего каждый конкретный лист `UNIT` связывается с
`MASTERRESOURCEUNITS`. Лист `UNITTYPE` выбирает конкретный допустимый ресурс
через исходную иерархию, диапазон уровня и вес редкости. Прямые группы
`Monsters`, `Items` и `Props` разрешаются в соответствующем разделе
мастер-таблицы без учёта регистра.

Сущность появляется в мировой позиции своего `Unit Spawner`. После обработки
всей выдачи исполнитель сообщает логическому объекту фактическое число живых
монстров. Оно считается по всем волнам этого спавнера, поэтому несколько
последовательных запросов не могут преждевременно вызвать `All Monsters Dead`.
Урон уменьшает HP, смерть монстра отправляет `Monster Killed`, а смерть
последнего — `All Monsters Dead`. Подбор предмета отправляет `Item Picked Up`.

## Управление существами спавнера

Запросы спавнера сохраняют порядок не только для создания, но и для команд
`Hide And Disable Spawned Units` и `Destroy Spawned Units`. Мир различает
существование сущности, её включённость и видимость. Скрытие оставляет живое
существо во владении спавнера, одновременно исключая его из выбора цели,
получения урона, AI и рендера. Уничтожение удаляет все принадлежащие спавнеру
сущности и синхронизирует его счётчик, не выдавая события обычного убийства.

Это следует из `CUnitSpawner::hideAndDisableUnits(bool)` по адресу `0xa0aeb0`:
оригинал проходит по массиву safe-pointer, вызывает для каждого персонажа
виртуальное переключение enabled и отдельно `CCharacter::setVisible`.
`CUnitSpawnerDescriptor::InputLogicEvent @0x652850` напрямую передаёт `true`
этому методу (`0x6528b0–0x6528b9`) и не отключает сам объект спавнера. Поэтому
после скрытия детей владелец остаётся доступен для нового `Spawn Units`. Это
`original-code` для Linux ELF SHA-256
`91b41ae9dfea30aab6bc14dbbfcceaee096d600f39635b8507f5a88b5d41724b`.
Инструкции входного обработчика сохранены в
`research/disassembly/652850-spawner-input.asm`.

В
`CUnitSpawner::destroyUnits()` по адресу `0xa147f0` оригинал вызывает у каждого
объекта виртуальное удаление, останавливает связанные layout и освобождает оба
массива safe-pointer. Соответствующие машинные инструкции сохранены в
`disassembly/a0aeb0.asm` и `disassembly/a147f0.asm`; декомпиляции находятся в
`decompiled-core/unit_spawner.c`.

## Проверка на исходном уровне

Интеграционный тест загружает `media/layouts/test/LOGICTEST.LAYOUT.adm` и
активирует исходный рычаг `4789864698297979358`. Его граф формирует запрос
спавнеру `4789864784197325278`; запрос создаёт `Skeletal Warrior` с исходным
GUID в точной мировой позиции спавнера. Убийство сущности продолжает исходный
граф до входа `Play` связанной временной шкалы. Отдельная проверка создаёт две
волны `SKELETONS` и подтверждает, что завершение наступает только после смерти
всех четырёх существ.

Wayland-приложение обрабатывает возникающие запросы до исчерпания цепочки и
выводит количество созданных сущностей, разрешённых и отсутствующих
`UNITTYPE`, моделей и отсутствующих ресурсов. Для конкретного ресурса
загружаются унаследованные
`RESOURCEDIRECTORY` и `MESHFILE`; модель добавляется в сцену с ID сущности, а
одинаковые пути используют один OGRE mesh. После появления новых моделей
приложение пересобирает GPU-представление сцены, не закрывая Wayland-окно и
сохраняя камеру. Это промежуточное корректное поведение; после восстановления
боя его можно заменить точечной потоковой загрузкой без изменения мира
сущностей.

## Размещённые сущности

Объекты с редакторским дескриптором `Monster` импортируются при создании мира
и сохраняют ID исходного объекта layout. Этот дескриптор в данных Torchlight
также применяется к NPC, торговцам и неподвижным телам. Поэтому возможность
атаки определяется по `UNITTYPE=MONSTER` и исходным флагам `ENABLED`,
`TARGETABLE`, `INVINCIBLE`, а не по одному дескриптору.

Геометрия размещённого объекта сохраняет его исходные поворот и масштаб и
получает ID runtime-сущности. При смерти видимость меняется у уже существующего
экземпляра без дублирования модели. У такого монстра нет `Unit Spawner`, поэтому
его смерть не посылает события вымышленному спавнеру. Проверка на раскрытом
городском layout импортирует все 44 объекта, выделяет четыре активные боевые
цели и связывает все 44 модели с runtime ID.

## Общая анимация моделей

Для каждого уникального скелетного mesh загрузчик находит одноимённый исходный
`.animation` манифест модели, читает перечисленные в нём клипы и связывает их с
bind-скелетом mesh. Если точного одноимённого файла нет, допустима только
единственная однозначная привязка по `FILE` bind-скелета; при равенстве
кандидатов загрузчик отказывается выбирать. В раскрытом городе этот путь без
таблицы исключений находит и исполняет idle-анимации всех 26 уникальных классов
скелетных моделей.
Он также повторно индексирует ресурсы после появления монстров во время
выполнения. Позы вычисляются на каждом отображаемом кадре; экземпляры одного
mesh могут использовать независимое время состояния.

Модель игрока исключена из общего прохода, но её отдельная машина состояний
получает `Idle`, `Run` и семейство атаки стартового оружия из того же манифеста
модели. Для посоха это исходные `Polearm1/2/3`, выбираемые алгоритмом
`CGenericModel::findRandomAnimation`. Для боевого
врага загрузчик выбирает `Run` и атаку из его манифеста; событие `HIT` служит
исходным признаком атакующего клипа, если его имя не начинается с `Attack`.
Рендерер создаёт
динамические position/normal-буферы только при первой индивидуальной позе,
поэтому несколько экземпляров общего mesh могут одновременно находиться в
разных кадрах и состояниях. Состояние `chasing` выбирает бег, событие удара —
атаку, а ожидание после завершения клипа возвращает idle. Направление модели
обновляется по вектору движения и вектору к игроку перед атакой.

При смене состояния игрока desktop-runtime за исходные 0,2 секунды линейно
смешивает два OGRE `AnimationState` на костях, затем один раз выполняет CPU
skinning. Отдельный bind-скелет каждого клипа сначала приводится к bind-позе
модели по `Skeleton::_mergeSkeletonAnimations`. Стартовый посох прикреплён к
`tag_righthand` и следует за рассчитанной позой с `WEAPON_SCALE=0.8`.

Тот же манифест разрешает семейство `Hit` для реакции на урон и семейства
`Die`/`Death` для смерти. Живая сущность возвращается в idle после
одноразового hit-клипа. Убитая сущность сразу исключается из боя и логики, но
её экземпляр остаётся видимым до последнего кадра death-клипа и скрывается
только после его длительности. При отсутствии подходящей анимации остаётся
безопасный путь с немедленным скрытием.

Момент нанесения урона врага пока совпадает с началом логической атаки, а не
с маркером внутри клипа. Независимый AI cooldown из UNIT монстра и выбранного
оружия восстановлен отдельно; он не заменяет время исполнения атаки.
См. [monster-ai-cooldown.md](monster-ai-cooldown.md). Синхронизация попадания
остаётся следующим этапом.
Происхождение и точные границы анимационной части описаны в
[animation-runtime.md](animation-runtime.md).
