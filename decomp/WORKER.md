# Инструкция исполнителя decomp

Документ для агента, который восстанавливает один пакет TU в отдельной копии
репозитория (`git worktree`). Общие правила — [AGENTS.md](../AGENTS.md),
устройство трека — [README.md](README.md).

## Рабочая папка

- Работай только в своей копии `/tmp/opencode/decomp-wt/<slug>`. Каждой
  команде задавай её рабочей папкой. Основную копию репозитория не трогай.
- Ветка `decomp/<slug>` уже создана. База `build-decomp/db` и пакеты
  `build-decomp/scaffold/<TU>/` уже подготовлены.
- В конце закоммить результат в свою ветку. Сливает ветку координатор.

## Цель

Для каждого TU пакета написать `decomp/src/<TU>` и нужные заголовки в
`decomp/include/`. Код должен быть чистым, читаемым, на C++98 (GCC 4.4.7) и
собираться в функции оригинала. Функция принята, когда:
1. `python3 tools/decomp/objdiff.py decomp/src/<TU>` показывает MATCH, или
2. её сравнивает с оригиналом самотест в `decomp/hybrid/tests/`, и он проходит
   на входах, покрывающих её ветви.

TU считается закрытым, когда приняты все его функции.

## Цикл

1. `build-decomp/scaffold/<TU>/PACKET.md`: функции, классы, базы, vtable,
   TU-данные. ASM каждой функции лежит в `asm/`; литералы подписаны. Для
   крупных функций можно взять черновик Ghidra из `research/decompiled-core/`
   (это только черновик).
2. Напиши заголовки и TU. Сверяйся:
   `python3 tools/decomp/objdiff.py decomp/src/<TU> [--show <mangled>|all]`.
3. Если функция не совпадает, подбирай форму исходника не дольше ~10 минут.
   Различия в порядке операндов `cmp` и раскладке блоков при верной логике
   закрывай самотестом.
4. Самотест: `decomp/hybrid/tests/<Имя>Test.cpp`. Образцы:
   `LogicObjectsTest.cpp` (объекты, фальшивые глобалы, запись виртуальных
   вызовов через копию vtable), `RandomizerTest.cpp` (зерно ГСЧ, граничные
   входы), `RunicCoreTest.cpp`.
5. Мутации: для каждой функции, принятой самотестом, временно испорти ветвь
   (условие, константу, порядок вызовов) и убедись, что тест падает. Потом
   верни код.
6. `python3 tools/decomp/check.py` должен пройти: сборка, сравнение,
   самотест.
7. `git add decomp tools && git commit -m "Decompile <TU…>"`.

## Правила кода

- Имена классов и методов и сигнатуры — из символов. Поля, параметры,
  локальные переменные и enumerator'ы называем сами: `m_` и префикс типа (`b`,
  `i`, `f`, `p`, `s`, `e`). Имя должно описывать смысл, установленный по
  машинному коду.
- Тип возврата и `static` в mangled-имени не кодируются. Проверяй их по
  вызывающим и по `rax`/`xmm0`.
- **В `decomp/src` нет заглушек.** Всё, что там определено, гибрид подставляет
  в игру. Функции чужих TU только объявляй.
- Комментарии — только для неочевидного. Происхождение каждой функции не
  расписывай.
- Не запускай игру с окном (`hybrid.py run`). Только `check.py` или
  `hybrid.py selftest`.

## Заголовки

- Один класс — один заголовок `decomp/include/<Class>.h`, имя по классу без
  `C`.
- Класс из чужого TU объявляй с полной и верной раскладкой: все поля, все
  виртуальные методы в порядке vtable. Невиртуальные методы — только нужные.
  Пометь его комментарием «Partial: …».
- Существующие общие заголовки только дополняй. Не переименовывай и не
  переставляй чужие члены. Если раскладка неверна, исправь и напиши об этом в
  отчёте.
- Таблицы строк из заголовков восстанавливай через
  `python3 tools/decomp/name_tables.py --tu <TU>`. Уже есть `OutputEvents.h`,
  `AIDefines.h`, `ParticleUniverseConstants.h` (включается через
  `ResourceManager.h`).

## Что известно о компиляторе и исходнике

- В начале каждого TU стоит `#include "EmptyStrings.h"`. Порядок `#include`
  виден в статическом инициализаторе: сначала `EMPTY_STRING`, затем
  `<iostream>` (через OGRE), затем таблицы заголовков в порядке включения.
  Сверяй его с ASM `global constructors keyed to …`.
- `_GLOBAL__I_<имя>` берёт имя первого глобального определения в исходнике.
  Если имя не совпадает, переставь определения.
- Inline-методы из заголовков попадают в объект TU как weak и сравниваются с
  копиями оригинала. В выводе `objdiff` они помечены `(inline)`.
- `TArrayList`: `operator[]` при индексе за ёмкостью возвращает элемент 0,
  `removeAt` проверяет индекс, `clear()` освобождает память.
- Неочевидные ветви `m_pData[0]` в машинном коде — следствие `operator[]`.
- `std::wstring` в конструкторе виден как запись адреса `0x1424558`
  (`_S_empty_rep_storage+0x18`), `std::string` — как `0x1423a38`.

## Отчёт

Последнее сообщение — короткий отчёт:
- TU и итог по каждому: MATCH, DIFF, принято самотестом, не закрыто и почему;
- какие общие заголовки созданы или изменены (важно для слияния);
- открытые вопросы и находки, полезные другим исполнителям;
- хеш коммита.
