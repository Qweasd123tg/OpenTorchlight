# Трек decomp: чистый исходник оригинальной игры

Цель — C++98 исходник первой Torchlight с исходными TU, классами, раскладками
и функциями, собираемый GCC 4.4.7-3.el6 с `-O2 -fno-strict-aliasing`.
Общие правила — [AGENTS.md](../AGENTS.md). Android — последующий этап.

## Исходные входы и раскладка

Оригинальный `Torchlight.bin.x86_64` имеет SHA-256
`91b41ae9dfea30aab6bc14dbbfcceaee096d600f39635b8507f5a88b5d41724b`.
ELF и ресурсы используются только для чтения и не попадают в git.
База ELF содержит 516 групп STT_FILE; игровой код — 5247 функций в 309 TU.
Имена файлов следуют исходным единицам трансляции.

| Путь | Назначение |
|---|---|
| `decomp/src/<TU>.cpp` | восстановленный исходник; заглушки запрещены |
| `decomp/include/` | принятые заголовки C++98 |
| `decomp/hybrid/` | загрузчик и сравнения в оригинальном процессе |
| `decomp/owners.json` | владение TU; проверять перед работой |
| `tools/decomp/` | инструменты восстановления и проверки |
| `build-decomp/` | ignored база, черновики, попытки, отчёты |

Тулчейн и рантайм находятся в `~/.cache/opentorchlight/decomp`
(`OTL_DECOMP_CACHE`); путь этого кэша должен быть без пробелов.
Закреплены OGRE 1.6.5, CEGUI 0.6.2 и FMOD Ex 4.36.21.
ParticleUniverse, FLTK, lodepng и ConvertUTF подключаются исходниками.

## Рабочий цикл

Единица работы — исходный TU или класс. Сначала проверить владельца TU,
имеющиеся исходники и входы; затем подготовить пакет и полный кандидат.

```sh
python3 tools/decomp/toolchain.py setup
python3 tools/decomp/elfdb.py
python3 tools/decomp/scaffold.py AIFlag.cpp
python3 tools/decomp/ghidra_draft.py stale
python3 tools/decomp/ghidra_draft.py drafts AIFlag.cpp
python3 tools/decomp/candidate.py AIFlag.cpp --input build-decomp/candidates/AIFlag.cpp
```

Файл `--input` создаёт исполнитель: это полный TU с сохранёнными прежними
определениями. Команда не генерирует произвольное новое поведение.
Пакет `build-decomp/scaffold/<TU>/` содержит ASM, символы, классы, данные
и подсказки раскладок. Ghidra — вход для навигации; полный свежий черновик
требует COMPLETE для ожидаемых целей. TIMEOUT, TYPE_ERROR и NO_BODY не
считаются готовыми входами. Подробнее —
[экспорт Ghidra](../research/decompiler-workflow.md).

`candidate.py` работает в `publication.Stage` внутри ignored попытки и
собирает конечный TU без trial-флагов и generated include paths. Сильные
определения требуют MATCH или свежего выполненного сравнения конечного объекта
(`BEHAVIORAL`). Прежний DIFF сохраняется только при неизменном полном объекте
и теле либо новой приёмке; равенство двух непроверенных EH-метаданных недостаточно.
Общие заголовки проверяются по всем TU: ранее принятые функции должны сохранить
MATCH или получить новое поведенческое доказательство.

`--publish` требует полный headless-прогон. Источники, заголовки, тесты,
runtime и конфигурация публикуются из одного проверенного снимка с журналом
восстановления после остановки процесса. Следующий инструмент под блокировкой
восстанавливает незавершённую запись. Конечные живые объекты также проверяются;
изменение инструментов внутри Stage публиковать нельзя. Диагностика и кандидаты
остаются в `build-decomp/attempts/`. `Stage.resume`/`rebase` сохраняют кандидат,
но требуют новой проверки; при смене базы candidate повторяет интеграцию один раз.

Для уже реализованных генераторов есть ограниченный маршрут без модели:

```sh
python3 tools/decomp/no_llm_loop.py LogicTimerDescriptor.cpp --provider properties
python3 tools/decomp/no_llm_loop.py --provider descriptor --limit 3
python3 tools/decomp/no_llm_loop.py Equipment.cpp --provider candidate --input-dir build-decomp/candidates
```

Он использует существующие генераторы свойств/дескрипторов либо полный готовый
кандидат явно выбранного игрового TU и проверяет его через incremental-маршрут.
Причины отказов сохраняются; cached failures не расходуют лимит новых попыток.
Режим и версия правил входят в ключ отказа. Это не универсальный
синтез всех крупных методов. По умолчанию
публикации нет; `--publish` включает конечную проверку и запись.
Модель подключается к оставшимся неоднозначным участкам после проверки входов,
типов и сборки. `llm_loop.py` также изолирует попытки через Stage.

Stage используют общий кэш backend-компиляции полного свежего preprocessed input
со стабильным путём и проверенными зависимостями. Неподдерживаемые режимы
остаются на исходном маршруте сборки; произвольные абсолютные пути из ключей
не удаляются.

## Приёмка

1. **MATCH** — совпадение нормализованного объекта с оригиналом, включая
   релокации, полные ключи литералов, таблицы переходов и поддерживаемые
   EH-метаданные. Неподтверждённые границы/цели таблиц и неподдерживаемая LSDA
   блокируют этот путь.
2. **Дифференциальный самотест** — оригинал и восстановленная функция
   исполняются на одинаковых входах, покрывающих её ветви; сравнения полны.
3. **DIFF n%** — диагностическая близость инструкций, не приёмка.

`TL_ORIGINAL` только объявляет адрес для навигации. Общий PASS оснастки не
принимает все перечисленные в ней функции. Для учёта DIFF `check.py`
требует успешное исполнение конкретной оснастки и её отчёт `coverage` для
конкретного адреса: минимум 20 завершённых сравнений, ноль `different`
и `incomplete`. Старые ручные оснастки без такого отчёта продолжают работать
как регрессии, но их объявления не повышают счётчик принятого исходника.
`AutoTest::invoke` регистрирует фактический вызов каждой стороны, loader проверяет
пару по hooks, а `Coverage` считает реальные исходы. Первый ручной адаптер —
`CWarper::activate`: 146 сравнений в оригинальном процессе. Пустой тест,
чужая функция, вызов оригинала с обеих сторон и неполнота не дают приёмку.

Сгенерированный тест не заменяет проверку ветвей. Для сильного мутационного
результата нужны минимум три валидных мутанта двух категорий и не менее 80%
изолированно подтверждённых убийств. Несобирающиеся и идентичные исходному
объекту мутанты не учитываются. Неполнота, переполнение наблюдателя, timeout
и одинаковые падения обеих сторон не считаются равенством или убийством.

Принятые автоматические результаты связаны с версией evidence и отпечатками
объекта, ELF, библиотек, тулчейна, типов, исходников/заголовков, оснастки и
параметров запуска. Старый результат нельзя присвоить изменённым входам.
`autotest.py` и `mutate.py` используются для выбранных функций; ограничения
наблюдателя нужно учитывать при подготовке оснастки.

После пары естественных правок формы исходника продолжать через сравнение
поведения. Новые текстовые контракты, стадии и реестры на каждую функцию
не требуются.

## Проверка и границы гибрида

```sh
python3 tools/decomp/objdiff.py decomp/src/AIFlag.cpp
python3 tools/decomp/check.py
```

Перед коммитом обязателен полный `check.py`: сборка, сравнение и самотест.
Самотест работает без дисплея и звука, завершая игру до `main`. Пустой выбор
тестов, аварийный процесс и неполный отчёт дают отказ. GUI, клики и скриншоты
запускаются только по явной просьбе пользователя через `hybrid.py run`.

Гибрид выполняется в оригинальном процессе. Его функции, данные, RTTI,
vtable и библиотечные зависимости могут оставаться оригинальными.
Прошедший гибрид не доказывает самостоятельную сборку восстановленной игры.
`standalone.py` проверяет обычную линковку без redirects и заглушек;
даже замкнутый link-only срез не доказывает работоспособную отдельную игру.

Для некоторых UI-тестов уже есть
[HeadlessGui.h](hybrid/HeadlessGui.h) с настоящими CEGUI/OGRE и null renderer.
Он не сравнивает GPU/пиксели и не является общим тестом всех UI-функций.

Тип возврата и static проверяются по ASM и вызывающим: mangled-имя их
не кодирует. Generated headers, совпавшие sizeof/offset и trial MATCH не
доказывают корректность всех типов, ABI и конечного объекта. Неподдерживаемые
secondary this-adjustments, aggregate ABI и lifetime-преобразования требуют
отдельного доказательства; опасная автоматическая очистка выключена.
Для скрытого указателя возврата конвертер требует точную ELF family и доверенный
прототип по адресу. Raw C не хранит цель перегруженного вызова: неоднозначные
вызовы остаются целиком без преобразования.

## Проверенный срез и материалы

После нового ремонта **7 октября 2026**: 894 строгих MATCH и одна функция
по выполненному сравнению — всего 895 из 5247, 53036 исходных байт;
103 самотеста и 164 теста инструментов прошли. Прежние зачёты по одним
объявлениям ручных тестов больше не принимаются автоматически.
11 новых property definitions получили MATCH только в staged пилоте;
крупные черновики Merchant/Stash получили COMPLETE. Эти результаты ещё
не являются опубликованным игровым исходником. Новых опубликованных
функций в ремонте инструментов нет, общего ускорения не измерено.
