# Трек decomp: чистый исходник оригинальной игры

Цель — исходный код на C++, который собирается оригинальным компилятором в
работающую игру с теми же классами, раскладками, функциями и файлами `.cpp`.
Android вторичен и собирается позже из этого же исходника.

## Почему прежние направления заморожены (2026-10-03)

| Направление | Почему не ведёт к цели |
|---|---|
| Параллельная реализация `src/` (свой runtime, рендер, UI, `.otc`) | Это другая программа. В оригинальную игру она не собирается, а её тесты не проверяют исходную структуру |
| Code-first контракты, стадии, `coverage.tsv`, `function-transfer.json` | Приёмка текстом: за три недели полностью закрыто 18 функций из ~5 тыс. |
| P-code лифтинг (`shared_machine`, `lift_pcode.py`) | Выдаёт код эмулятора (`machine.read(56, 8, …)`), читаемым исходником он не станет |

Что из прежней работы стоит переиспользовать:
- `research/` как справочник по поведению: формулы, форматы ресурсов,
  разобранные ветви и адреса;
- headless-проект Ghidra и экспорт декомпиляции для навигации;
- закреплённые исходники CEGUI 0.6.2 и OGRE 1.6.5.

Код `src/` в decomp не переносится. Он лишь подсказывает, где искать.

## Что известно о бинарнике (`original-code`)

- `Torchlight.bin.x86_64` SHA-256 `91b41ae9…5d41724b`: ELF `EXEC` (не PIE),
  символы не вырезаны.
- Компилятор игрового кода — **GCC 4.4.7 (Red Hat 4.4.7-3, CentOS 6.4)**:
  - в `.comment` по порядку линковки идут объединённые записи 4.4.6 (crt glibc)
    и 4.4.7, затем 61 необъединённая запись 4.1.2 — это готовые статические
    библиотеки;
  - есть суффиксы `[clone .clone.N]` (IPA-CP появился в GCC 4.4);
  - деструкторы регистрируются прямым `__cxa_atexit(dtor)`, без `__tcf`.
  
  GCC 4.1.2 на `RunicCore.cpp` генерирует `__tcf_N`, которых в оригинале нет.
- Флаги `-O2 -fno-strict-aliasing`: без второго флага не воспроизводится
  перечитывание `m_pSafePointers` в `CRunicCore::removeSafePointer`.
- 516 групп `STT_FILE` в `.symtab` дают исходные TU и порядок линковки.
  Разбиение `.text` получилось без инверсий; лишь 4 из 326 игровых классов
  разнесены по нескольким TU.
- Ручная работа: **309 игровых TU, 5247 функций, ~3,7 МБ кода**.
  - Не считаются: inline/шаблоны (их порождает компилятор из заголовков) и
    статические инициализаторы (таблицы имён в заголовках).
  - Из исходников подключаются: ParticleUniverse (139 TU), FLTK (38),
    lodepng, ConvertUTF.

## Раскладка

| Путь | Назначение |
|---|---|
| `decomp/src/<TU>` | восстановленный TU; имя файла = имя `STT_FILE` оригинала |
| `decomp/include/` | заголовки классов (C++98, как у GCC 4.4 по умолчанию) |
| `decomp/config.json` | флаги и пути заголовков оригинальной сборки |
| `decomp/hybrid/` | загрузчик, ABI таблиц, самотесты в процессе игры |
| `tools/decomp/` | база ELF, тулчейн, сравнение, гибридная сборка, пакеты |

Генерируемое лежит в ignored `build-decomp/`. Тулчейн и рантайм гибрида — в
`~/.cache/opentorchlight/decomp` (`OTL_DECOMP_CACHE`): в путях не должно быть
пробелов.

## Рабочий цикл

```sh
python3 tools/decomp/toolchain.py setup         # один раз: GCC 4.4.7-3.el6, binutils, заголовки
python3 tools/decomp/elfdb.py                   # база: функции, TU, классы, vtable, RTTI
python3 tools/decomp/scaffold.py --list --max-functions 10
python3 tools/decomp/scaffold.py AIFlag.cpp     # build-decomp/scaffold/AIFlag.cpp/PACKET.md
# пишем decomp/src/AIFlag.cpp и заголовки
python3 tools/decomp/objdiff.py decomp/src/AIFlag.cpp [--show NAME|all]
python3 tools/decomp/name_tables.py --tu LogicTimer.cpp   # таблицы строк из инициализатора
python3 tools/decomp/check.py                   # всё вместе + самотест в процессе игры
```

`name_tables.py` восстанавливает определения таблиц вида
`static const std::wstring g_…_NAMES[] = {…}` по статическому инициализатору
TU, который их владеет. Такие таблицы живут в заголовках и повторяются в
десятках TU (`gOUTPUT_EVENTS_NAMES` — в 128), поэтому их не набирают вручную.

Пакет TU содержит:
- функции в исходном порядке;
- классы с базами и смещениями из RTTI, раскладку vtable по слотам и подсказки
  размера;
- TU-локальные данные и ASM каждой функции;
- список целей для `tools/ghidra/ExportTargetDecompilations.java`.

## Что считается доказательством

1. **MATCH** (`objdiff.py`): поток инструкций, собранный тем же компилятором,
   совпадает с оригиналом после нормализации. Нормализация:
   - перед ассемблированием локальные символы объявляются глобальными, чтобы
     релокации остались в форме «символ + смещение»;
   - каждая ссылка (символ + смещение) переводится в адрес оригинала через базу
     и печатается так же, как на стороне оригинала. Поэтому совпадают алиасы
     C1/C2 и D1/D2, указатели «за конец массива», TU-локальные данные;
   - строковые литералы (`char` и `wchar_t`) заменяются содержимым, константы
     из `.rodata` и `.LC*` — байтами;
   - внутренние переходы — индексами инструкций.
2. **DIFF n%** — метрика близости, а не приёмка.
3. **Самотест гибрида** (`decomp/hybrid/tests/*.cpp`): оригинальный машинный
   код и восстановленная функция выполняются в настоящем процессе игры (её
   heap, libstdc++, OGRE) на одних и тех же входах.
   - Запуск без дисплея и звука; процесс завершается до `main` игры.
   - Мутационная проверка пилота: испорченный `removeSafePointer` даёт FAIL.

Функция считается перенесённой, когда у неё MATCH или пройден самотест,
покрывающий её ветви. Текстовые контракты для этого не нужны.

Главный критерий — та же игра по поведению (решение 2026-10-03). Побайтное
совпадение желательно, но не обязательно. Ручной подбор формы ограничен
парой естественных правок; дальше функцию принимают самотестом.

`check.py` считает принятыми MATCH и DIFF-функции, которые самотесты объявляют
через `TL_ORIGINAL`, если весь самотест прошёл. Поэтому `TL_ORIGINAL`
объявляют только функции, которые тест действительно сравнивает. Покрытие
ветвей проверяется мутациями: каждую испорченную ветвь тест должен ловить.
Граничные сравнения (`<=` против `<`, `>` против `>=`) случайными входами не
ловятся, для них нужны отдельно подобранные входы (см. `RandomizerTest.cpp`).

### Генерируемые тесты и мутации

Ручной тест нужен не всегда. `tools/decomp/autotest.py` сам строит
дифференциальный тест любой DIFF-функции класса с заголовком:
- объект собирается по раскладке из `types.json`: случайные числа, строки,
  списки `TArrayList`, фейковые объекты за указателями, оригинальная vtable;
- аргументы-указатели иногда берутся из уже созданных объектов, поэтому поиск
  и удаление находят то, что ищут;
- `decomp/hybrid/AutoTest.h` выполняет оригинал и нашу функцию в двух
  дочерних процессах (`fork`) от одного состояния и сравнивает результат,
  байты объектов, содержимое списков и строк и занятый объём кучи;
- падение или зависание в обоих процессах не засчитывается ни в одну сторону,
  в одном из них — расхождение.

`tools/decomp/mutate.py` проверяет, что тест чего-то стоит. Он портит копию
`decomp/src`: переворачивает сравнения и логические операторы, меняет `+` и
`-`, прибавляет единицу к литералам, убирает `!` и операторы. Мутанты, которые
не собираются или дают тот же машинный код, отбрасываются. Остальные
проверяются пачками, и тест должен поймать не меньше 80 % из них.

```sh
python3 tools/decomp/autotest.py --run            # тесты всех DIFF-функций
python3 tools/decomp/mutate.py --accept 0x988020  # мутации; сильные — в decomp/autotests.json
```

`check.py` генерирует тесты функций из `decomp/autotests.json` и засчитывает
их, если тест прошёл и машинный код функции не менялся после мутаций. Полный
прогон мутаций по 27 функциям занимает около 35 минут процессора. Слабыми
выходят тесты функций, которым нужны синглтоны (`gEditor`,
`CResourceManager`) или осмысленные объекты за виртуальными вызовами.

## Гибридная сборка

`tools/decomp/hybrid.py build`:

1. Компилирует каждый TU в ассемблер оригинальным GCC.
2. Перенаправляет на исходные адреса данные, которые есть в оригинале:
   - глобальные и TU-локальные переменные (`_ZL…`, `_ZZ…`, guard-переменные);
   - vtable, typeinfo, `DW.ref` personality.
   
   Восстановленный код работает с настоящими объектами игры, а созданные им
   объекты получают оригинальные vtable.
3. Отбрасывает `.ctors` восстановленных TU: оригинал уже сконструировал свои
   объекты.
4. Связывает объекты по фиксированному адресу `0x60000000`, в пределах rel32
   от исполняемого файла. Адрес выше кучи `brk`: ядро x86-64 размещает её
   случайно в пределах 1 ГиБ после `.bss`, и с базой `0x40000000` загрузка
   изредка падала с `EEXIST`. Остальные символы разрешаются через сгенерированный
   `originals.ld` в оригинальные функции, данные и PLT-записи игры. Импорты,
   которых у игры нет, загрузчик заполняет через `dlsym`.

`decomp/hybrid/loader.c` подключается через `LD_PRELOAD` и перехватывает
`__libc_start_main`. После статической инициализации игры он:
1. отображает blob в память;
2. регистрирует его `.eh_frame`;
3. выполняет самотесты или ставит `jmp rel32` на все функции восстановленных TU
   (заодно проверяя первые 8 байт оригинала).

- `hybrid.py selftest` — проверки без окна.
- `hybrid.py run` запускает игру с восстановленным кодом. Это отдельная,
  явно запрошенная задача.

## Пилот: `RunicCore.cpp`

`CRunicCore` — общая база CGame, CLevel, CInventory, CDropdownMenu и других
классов. Восстановлены:
- `decomp/src/RunicCore.cpp`;
- шаблоны `TArrayList` (по внестрочным `TArrayList<T>::add/~TArrayList`) и
  `TSafePointer`;
- общий заголовок `EmptyStrings.h`.

Результат:
- **MATCH**: конструктор, deleting-деструктор, статический инициализатор TU;
- **DIFF**: `addSafePointer` 97%, деструктор 95%, `removeSafePointer` 74% —
  различаются раскладка ветвлений и распределение регистров;
- **самотест PASS**: 64 раунда по 400 случайных операций, плюс деструкция,
  счётчик объектов и совпадение vtable.

Вместе с пилотом — 63 из 5247 функций (26 КБ из 3,7 МБ), из них 8 приняты
самотестом. Пачка заняла около 40 минут, включая доработку инструментов. Эти
TU мелкие: оценку на крупных классах нужно мерить отдельно.

Что выяснилось о компиляторе и исходнике:
- `_GLOBAL__I_<имя>` берёт имя первого глобального определения в исходнике
  (конструктор, переменная). Порядок функций в бинарнике с порядком в
  исходнике напрямую не совпадает.
- Порядок `#include` виден в статическом инициализаторе: `EMPTY_STRING`,
  затем `<iostream>` (через OGRE), затем таблицы заголовков в порядке
  включения.
- `TArrayList::operator[]` при индексе за ёмкостью возвращает элемент 0;
  `removeAt` проверяет индекс; `clear()` освобождает память. Отсюда ветви
  `m_pData[0]` в машинном коде.
- Различия DIFF в оставшихся функциях — порядок операндов `cmp` и раскладка
  блоков. Логика подтверждена самотестами. Для `CRandomizer::getRandom` есть
  вариант, ближе к машинному коду (88 %), но с неестественной записью
  `m_Odds[-1]`. Выбран естественный вариант (50 %).

## Первая параллельная волна (2026-10-03)

Пять исполнителей в отдельных копиях (`tools/decomp/parallel.py`,
`decomp/WORKER.md`) закрыли 21 TU: редакторные объекты, AI, `utilities`,
`UtilitiesMath`, `StringTranslate`, `FileSystem`, `Descriptor`. Итог в `main`:
260 принятых функций, 63 КБ (1,7 % написанного вручную кода), из них 50
самотестом. Ещё совпадают 169 статических инициализаторов и деструкторов
глобальных объектов (187 КБ), которые компилятор строит из определений
глобалов. Раньше `check.py` прибавлял их к функциям и показывал 433 функции и
6,9 %. Теперь они выводятся отдельной строкой.

Находки о компиляторе:
- GCC 4.4 переставляет `field && param` так, что параметр проверяется первым.
  Исходный порядок дают ранние `return` или вложенные `if`.
- `if` по двум значениям enum с общим хвостовым вызовом — это `switch` с двумя
  метками (`CCounter::add`/`subtract`).
- Временный объект OGRE в аргументе и именованная локальная переменная по-разному
  размещают загрузку адреса виртуального вызова. В оригинале встречаются обе
  формы.
- Порядок определений в исходнике влияет на распределение регистров: помогает
  порядок, при котором GCC выдаёт функции в порядке оригинала.
- `_GLOBAL__I_<имя>` бывает ключом и по переменной (`Percentage`,
  `g_iTotalCountOfObjects`), и по функции (`createUniqueGuid`).
- В оригинале нет `assert`: сборка идёт с `-DNDEBUG` (`decomp/config.json`).

Находки об исходнике и библиотеках:
- OGRE у Runic изменён: у `ResourceGroupManager` есть лишний флаг по смещению
  +0x110, а `ScriptCompiler::getBasePath()` в стоковом 1.6.5 нет.
- Шаблоны OGRE вроде `any_cast` содержат в тексте исключения путь сборочной
  машины, поэтому побайтно не совпадут никогда.
- Дескрипторы:
  - аргументы `AddProperty(category, name, description, set, get, type, flags)`;
  - функции свойств — inline-статики класса: геттер
    `UNIONDATA8BIT* (CEditorBaseObject*, unsigned int& bytes)`, сеттер
    `(CEditorBaseObject*, const UNIONDATA8BIT*, unsigned int count)`;
  - `gUnionOf32BitData[3]` — своя копия в каждом TU.
- 27 функций `MATH::` относятся к `UtilitiesMath.cpp`. `elfdb.py` раньше относил
  их к `MouseHandler.cpp` (исправлено).

Доработки `objdiff.py`:
- таблицы `switch` сравниваются по целям переходов;
- вызов функцией самой себя считается переходом на её начало;
- метки ветвлений не зависят от выравнивания;
- пустые строковые литералы сравниваются как литералы.

Незакрытое:
- `CFileSystem::CFileSystem` и `buildMassiveDataGroup` — DIFF без самотеста:
  им нужны `resources.cfg` и синглтоны, которых до `main` нет;
- три функции мешей в `UtilitiesMath.cpp` — нужен настоящий меш OGRE;
- `CDescriptor::deleteAllObjects` гибрид не перехватывает: в оригинале есть
  переход внутрь байтов, которые занял бы патч.

## Сгенерированные заголовки и пробная сборка черновиков

`tools/decomp/headers.py` пишет в `build-decomp/include-gen/` заголовки всех
классов игры, у которых нет рукописного:
- базы и их смещения берутся из RTTI;
- виртуальные методы объявляются в порядке слотов vtable, переопределение
  получает тип возврата базы (рукописной или из OGRE);
- типы возврата остальных методов берутся из прототипов Ghidra, поля — из
  `types.json`, неизвестные поля заменяются массивами байт того же размера.

`GenTypes.h` объявляет перечисления и типы, `GenGlobals.h` — глобальные данные.
`--check` компилирует каждый заголовок и сверяет `sizeof` и смещения полей с
оригиналом: сходятся 303 класса из 321.

`tools/decomp/draft_trial.py --all` собирает черновики Ghidra каждого
нетронутого TU с этими заголовками и выбрасывает функции, на которых падает
компилятор. Итог по 4281 функции (2026-10-03):

| итог | функций | объём |
|---|---|---|
| MATCH | 349 | 8 КБ |
| DIFF | 189 | 19 КБ |
| не собралось | 3285 | 2,5 МБ |
| ошибка в заголовке | 446 | 514 КБ |

Автоматически совпадают только крошечные функции (в среднем 23 байта).
Крупный код черновик Ghidra сам не даёт: его нужно переписывать, и
черновик служит входом, а не результатом.

## `astarpathfinder.cpp`

Все 26 исходных методов приняты: 16 MATCH, 10 самотестом. Отдельные
deleting-деструктор и статический инициализатор также MATCH.

## Обвязка для моделей (2026-10-04)

Приёмка:
- Сильный сгенерированный тест (`decomp/autotests.json`) привязан к
  нормализованному машинному коду функции (`objdiff.code_digest`), а не к
  тексту её тела. Правка inline-функции в заголовке, меняющая код, снимает
  приёмку; правка текста без изменения кода — нет.
- vtable сверяется слот в слот, со всеми вторичными базами и thunk'ами, по
  дампу `-fdump-class-hierarchy` (`headers.vtable_mismatch`). Проверка стоит в
  `headers.py --check` и в проверке заголовка в `llm_loop.py`. На рукописных
  заголовках расходятся только частичные `CDataValue` и `CHierarchy`: в них нет
  виртуального деструктора оригинала.
- Генератор заголовков давал чисто виртуальным слотам базы имена-заглушки
  `pureVirtualSlotN`, и методы производных классов их не переопределяли. Теперь
  слот получает имя и сигнатуру переопределения из производного класса.
  Строгую проверку проходят 298 сгенерированных заголовков из 320 (было 238);
  остальные — размеры из выведенных раскладок. Классы FLTK больше не
  генерируются.

Цикл `llm_loop.py`:
- компилирует черновую работу со сгенерированными заголовками через
  `OTL_EXTRA_INCLUDE`; закоммиченный исходник их не видит;
- в конце `promote.py` переносит в `decomp/include` то, что TU использует:
  заголовки классов (частичные, `CFoo.h` → `Foo.h`), перечисления, глобалы и
  функции пространств имён (`GameEnums.h`, `GameVariables.h`,
  `GameNamespaces.h`). Затем TU собирается без сгенерированных заголовков, и
  статусы функций должны совпасть. Раньше результаты пилотов `check.py` не
  собирал;
- промпт: `tools/decomp/prompts/idioms.md` (одинаковый для всех вызовов, поэтому
  кэшируется), заголовок класса, похожие принятые функции рядом с их
  черновиками (`examples.py`, 230 примеров), затем ASM и черновик;
- модели идут цепочкой: бесплатная Space Bunny, затем DeepSeek V4.1 Flash.

`ghidra_cpp.py` удаляет мёртвые присваивания временных переменных, которые
остаются после свёртки идиом. `hybrid.py` берёт недостающие системные

## Известные границы

- Тип возврата и `static` в mangled-имени не кодируются: `return_hint` — по
  чтению `rax`/`xmm0` вызывающими. Размеры классов — подсказки по аллокации
  перед конструктором. Принадлежность к TU вне групп `local-symbol`/`bracketed`
  эвристическая.
- Имена встроенных сущностей без символов (поля, параметры) даём сами.
- Гибрид не перехватывает inline/шаблонные функции: оригинал и восстановленный
  код пользуются каждый своей копией.
- Трамплины для сравнения в живой игре (оригинал и замена в одном кадре) ещё не
  сделаны. Самотесты вызывают оригинал до установки перехватов.
- Импорты, отсутствующие у игры, поддержаны только для функций.

### Точный тип возврата в автотестах

Исправлена отдельная ABI-проблема `autotest.py`: GNU `__typeof__(call)`
снимает ссылку с результата выражения. Для `ReadWChar`, возвращающего
`wchar_t&`, оригинал поэтому ошибочно вызывался как возвращающий wchar_t
по значению. На пустом тестовом buffer оригинальная сторона записывала
часть адреса, а наша разыменовывала ссылку и падала: ложное расхождение.
Теперь тип R выводится из точного function/member-pointer signature,
с учётом аргументов, const и static; сохраняются R& и const R&.
Перегруженный operator, для записи возвращаемого значения не менялся.

`python3 tools/decomp/test_autotest_returns.py` проверяет шесть типов/форм
методов компиляцией C++98 на оригинальном GCC и исполняемым тестом алиаса
ссылки. Полный прогон прежней принятой базы после изменения: 53 теста PASS,
323 функции, ни один сгенерированный тест не потерян. Случай ReadWChar с
неподготовленным buffer теперь симметрично не выполняется у обеих сторон;
это не приёмка функции и требует настоящих входных данных.

`autotest::runChild` теперь использует локальный Capture в дочернем процессе,
поэтому ручные тесты могут переиспользовать fork/timeout/transport без
подключения глобалов сгенерированного runtime. Добавлен отдельный
исполняемый regression: успешный payload и ненулевой exit без payload.
Оба tooling-теста проходят; прежняя принятая база сохраняет 53 PASS и 323
функции. Это изменение само по себе не расширяет приёмку игровых функций.

### FileReader: чтение строк, токенизация и определение кодировки

строки, очередь токенов, состояние/буфер reader, позиция FILE и сообщения
