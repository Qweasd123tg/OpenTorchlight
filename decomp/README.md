# Трек decomp: чистый исходник оригинальной игры

Цель — исходный код на C++, который собирается оригинальным компилятором в
работающую игру с теми же классами, раскладками, функциями и файлами `.cpp`.
Android вторичен и собирается позже из этого же исходника.

## Почему прежние направления заморожены (2026-10-03)

| Направление | Почему не ведёт к цели |
|---|---|
| Параллельная реализация `src/` (свой runtime, рендер, UI, `.otc`) | Это другая программа. В оригинальную игру она не собирается, а её тесты не проверяют исходную структуру |
| Code-first контракты, стадии, `coverage.tsv`, `function-transfer.json` | Приёмка текстом: за три недели полностью закрыто 18 функций из ~5 тыс. |
| P-code лифтинг (`shared_machine`, `lift_pcode.py`) | Выдаёт код эмулятора (`machine.read(56, 8, …)`), читаемым исходником он не станет |

Что из прежней работы стоит переиспользовать:
- `research/` как справочник по поведению: формулы, форматы ресурсов,
  разобранные ветви и адреса;
- headless-проект Ghidra и экспорт декомпиляции для навигации;
- закреплённые исходники CEGUI 0.6.2 и OGRE 1.6.5.

Код `src/` в decomp не переносится. Он лишь подсказывает, где искать.

## Что известно о бинарнике (`original-code`)

- `Torchlight.bin.x86_64` SHA-256 `91b41ae9…5d41724b`: ELF `EXEC` (не PIE),
  символы не вырезаны.
- Компилятор игрового кода — **GCC 4.4.7 (Red Hat 4.4.7-3, CentOS 6.4)**:
  - в `.comment` по порядку линковки идут объединённые записи 4.4.6 (crt glibc)
    и 4.4.7, затем 61 необъединённая запись 4.1.2 — это готовые статические
    библиотеки;
  - есть суффиксы `[clone .clone.N]` (IPA-CP появился в GCC 4.4);
  - деструкторы регистрируются прямым `__cxa_atexit(dtor)`, без `__tcf`.
  
  GCC 4.1.2 на `RunicCore.cpp` генерирует `__tcf_N`, которых в оригинале нет.
- Флаги `-O2 -fno-strict-aliasing`: без второго флага не воспроизводится
  перечитывание `m_pSafePointers` в `CRunicCore::removeSafePointer`.
- 516 групп `STT_FILE` в `.symtab` дают исходные TU и порядок линковки.
  Разбиение `.text` получилось без инверсий; лишь 4 из 326 игровых классов
  разнесены по нескольким TU.
- Ручная работа: **309 игровых TU, 5247 функций, ~3,7 МБ кода**.
  - Не считаются: inline/шаблоны (их порождает компилятор из заголовков) и
    статические инициализаторы (таблицы имён в заголовках).
  - Из исходников подключаются: ParticleUniverse (139 TU), FLTK (38),
    lodepng, ConvertUTF.

## Раскладка

| Путь | Назначение |
|---|---|
| `decomp/src/<TU>` | восстановленный TU; имя файла = имя `STT_FILE` оригинала |
| `decomp/include/` | заголовки классов (C++98, как у GCC 4.4 по умолчанию) |
| `decomp/config.json` | флаги и пути заголовков оригинальной сборки |
| `decomp/hybrid/` | загрузчик, ABI таблиц, самотесты в процессе игры |
| `tools/decomp/` | база ELF, тулчейн, сравнение, гибридная сборка, пакеты |

Генерируемое лежит в ignored `build-decomp/`. Тулчейн и рантайм гибрида — в
`~/.cache/opentorchlight/decomp` (`OTL_DECOMP_CACHE`): в путях не должно быть
пробелов.

## Рабочий цикл

```sh
python3 tools/decomp/toolchain.py setup         # один раз: GCC 4.4.7-3.el6, binutils, заголовки
python3 tools/decomp/elfdb.py                   # база: функции, TU, классы, vtable, RTTI
python3 tools/decomp/scaffold.py --list --max-functions 10
python3 tools/decomp/scaffold.py AIFlag.cpp     # build-decomp/scaffold/AIFlag.cpp/PACKET.md
# пишем decomp/src/AIFlag.cpp и заголовки
python3 tools/decomp/objdiff.py decomp/src/AIFlag.cpp [--show NAME|all]
python3 tools/decomp/check.py                   # всё вместе + самотест в процессе игры
```

Пакет TU содержит:
- функции в исходном порядке;
- классы с базами и смещениями из RTTI, раскладку vtable по слотам и подсказки
  размера;
- TU-локальные данные и ASM каждой функции;
- список целей для `tools/ghidra/ExportTargetDecompilations.java`.

## Что считается доказательством

1. **MATCH** (`objdiff.py`): поток инструкций, собранный тем же компилятором,
   совпадает с оригиналом после нормализации. Нормализация:
   - перемещаемые операнды и абсолютные адреса заменяются именами символов;
   - строковые литералы — их содержимым, константы — байтами;
   - внутренние переходы — индексами инструкций.
2. **DIFF n%** — метрика близости, а не приёмка.
3. **Самотест гибрида** (`decomp/hybrid/tests/*.cpp`): оригинальный машинный
   код и восстановленная функция выполняются в настоящем процессе игры (её
   heap, libstdc++, OGRE) на одних и тех же входах.
   - Запуск без дисплея и звука; процесс завершается до `main` игры.
   - Мутационная проверка пилота: испорченный `removeSafePointer` даёт FAIL.

Функция считается перенесённой, когда у неё MATCH или пройден самотест,
покрывающий её ветви. Текстовые контракты для этого не нужны.

## Гибридная сборка

`tools/decomp/hybrid.py build`:

1. Компилирует каждый TU в ассемблер оригинальным GCC.
2. Перенаправляет на исходные адреса данные, которые есть в оригинале:
   - глобальные и TU-локальные переменные (`_ZL…`, `_ZZ…`, guard-переменные);
   - vtable, typeinfo, `DW.ref` personality.
   
   Восстановленный код работает с настоящими объектами игры, а созданные им
   объекты получают оригинальные vtable.
3. Отбрасывает `.ctors` восстановленных TU: оригинал уже сконструировал свои
   объекты.
4. Связывает объекты по фиксированному адресу `0x40000000`, в пределах rel32
   от исполняемого файла. Остальные символы разрешаются через сгенерированный
   `originals.ld` в оригинальные функции, данные и PLT-записи игры. Импорты,
   которых у игры нет, загрузчик заполняет через `dlsym`.

`decomp/hybrid/loader.c` подключается через `LD_PRELOAD` и перехватывает
`__libc_start_main`. После статической инициализации игры он:
1. отображает blob в память;
2. регистрирует его `.eh_frame`;
3. выполняет самотесты или ставит `jmp rel32` на все функции восстановленных TU
   (заодно проверяя первые 8 байт оригинала).

- `hybrid.py selftest` — проверки без окна.
- `hybrid.py run` запускает игру с восстановленным кодом. Это отдельная,
  явно запрошенная задача.

## Пилот: `RunicCore.cpp`

`CRunicCore` — общая база CGame, CLevel, CInventory, CDropdownMenu и других
классов. Восстановлены:
- `decomp/src/RunicCore.cpp`;
- шаблоны `TArrayList` (по внестрочным `TArrayList<T>::add/~TArrayList`) и
  `TSafePointer`;
- общий заголовок `EmptyStrings.h`.

Результат:
- **MATCH**: конструктор, deleting-деструктор, статический инициализатор TU;
- **DIFF**: `addSafePointer` 97%, деструктор 95%, `removeSafePointer` 67% —
  различаются раскладка ветвлений и распределение регистров;
- **самотест PASS**: 64 раунда по 400 случайных операций, плюс деструкция,
  счётчик объектов и совпадение vtable.

## Известные границы

- Тип возврата и `static` в mangled-имени не кодируются: `return_hint` — по
  чтению `rax`/`xmm0` вызывающими. Размеры классов — подсказки по аллокации
  перед конструктором. Принадлежность к TU вне групп `local-symbol`/`bracketed`
  эвристическая.
- Имена встроенных сущностей без символов (поля, параметры) даём сами.
- Гибрид не перехватывает inline/шаблонные функции: оригинал и восстановленный
  код пользуются каждый своей копией.
- Трамплины для сравнения в живой игре (оригинал и замена в одном кадре) ещё не
  сделаны. Самотесты вызывают оригинал до установки перехватов.
- Импорты, отсутствующие у игры, поддержаны только для функций.
