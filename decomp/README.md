# Трек decomp: чистый исходник оригинальной игры

Цель — C++98 исходник первой Torchlight с исходными TU, классами, раскладками
и функциями, собираемый GCC 4.4.7-3.el6 с `-O2 -fno-strict-aliasing`.
Общие правила — [AGENTS.md](../AGENTS.md). Android — последующий этап.

## Исходные входы и раскладка

Оригинальный `Torchlight.bin.x86_64` имеет SHA-256
`91b41ae9dfea30aab6bc14dbbfcceaee096d600f39635b8507f5a88b5d41724b`.
ELF и ресурсы используются только для чтения и не попадают в git.
База ELF содержит 516 групп STT_FILE; игровой код — 5247 функций в 309 TU.
Имена файлов следуют исходным единицам трансляции.

| Путь | Назначение |
|---|---|
| `decomp/src/<TU>.cpp` | восстановленный исходник; заглушки запрещены |
| `decomp/include/` | принятые заголовки C++98 |
| `decomp/hybrid/` | загрузчик и сравнения в оригинальном процессе |
| `decomp/owners.json` | владение TU; проверять перед работой |
| `tools/decomp/` | инструменты восстановления и проверки |
| `build-decomp/` | ignored база, черновики, попытки, отчёты |

Тулчейн и рантайм находятся в `~/.cache/opentorchlight/decomp`
(`OTL_DECOMP_CACHE`); путь этого кэша должен быть без пробелов.
Закреплены OGRE 1.6.5, CEGUI 0.6.2 и FMOD Ex 4.36.21.
ParticleUniverse, FLTK, lodepng и ConvertUTF подключаются исходниками.

## Рабочий цикл

Единица работы — исходный TU или класс. Сначала проверить владельца TU,
имеющиеся исходники и входы; затем подготовить пакет и полный кандидат.

Планируй общую интеграцию примерно на 100–200 кандидатов, сгруппированных по TU.
Во время восстановления используй сравнение изменённых TU и адресные headless-
фикстуры. Полный `check.py` запускай один раз после интеграции пакета, перед
коммитом и обновлением PR. При старте следующего пакета не повторяй уже успешный
полный прогон, если HEAD и его входы не изменились. Изменения общих заголовков,
ABI или runtime могут потребовать более ранней широкой проверки. Размер пакета
не заменяет приёмку: заблокированные кандидаты не получают зачёта ради числа.

```sh
python3 tools/decomp/toolchain.py setup
python3 tools/decomp/elfdb.py
python3 tools/decomp/scaffold.py AIFlag.cpp
python3 tools/decomp/ghidra_draft.py stale
python3 tools/decomp/ghidra_draft.py drafts AIFlag.cpp
python3 tools/decomp/candidate.py AIFlag.cpp --input build-decomp/candidates/AIFlag.cpp
```

Файл `--input` создаёт исполнитель: это полный TU с сохранёнными прежними
определениями. Команда не генерирует произвольное новое поведение.
Пакет `build-decomp/scaffold/<TU>/` содержит ASM, символы, классы, данные
и подсказки раскладок. Ghidra — вход для навигации; полный свежий черновик
требует COMPLETE для ожидаемых целей. TIMEOUT, TYPE_ERROR и NO_BODY не
считаются готовыми входами. Подробнее —
[экспорт Ghidra](../research/decompiler-workflow.md).

`candidate.py` работает в `publication.Stage` внутри ignored попытки и
собирает конечный TU без trial-флагов и generated include paths. Сильные
определения требуют MATCH или свежего выполненного сравнения конечного объекта
(`BEHAVIORAL`). Прежний DIFF сохраняется только при неизменном полном объекте
и теле либо новой приёмке; равенство двух непроверенных EH-метаданных недостаточно.
Общие заголовки проверяются по всем TU: ранее принятые функции должны сохранить
MATCH или получить новое поведенческое доказательство.

`--publish` требует полный headless-прогон. Источники, заголовки, тесты,
runtime и конфигурация публикуются из одного проверенного снимка с журналом
восстановления после остановки процесса. Следующий инструмент под блокировкой
восстанавливает незавершённую запись. Конечные живые объекты также проверяются;
изменение инструментов внутри Stage публиковать нельзя. Диагностика и кандидаты
остаются в `build-decomp/attempts/`. `Stage.resume`/`rebase` сохраняют кандидат,
но требуют новой проверки; при смене базы candidate повторяет интеграцию один раз.

Для уже реализованных генераторов есть ограниченный маршрут без модели:

```sh
python3 tools/decomp/no_llm_loop.py LogicTimerDescriptor.cpp --provider properties
python3 tools/decomp/no_llm_loop.py --provider descriptor --limit 3
python3 tools/decomp/no_llm_loop.py Equipment.cpp --provider candidate --input-dir build-decomp/candidates
```

Он использует существующие генераторы свойств/дескрипторов либо полный готовый
кандидат явно выбранного игрового TU и проверяет его через incremental-маршрут.
Причины отказов сохраняются; cached failures не расходуют лимит новых попыток.
Режим и версия правил входят в ключ отказа. Это не универсальный
синтез всех крупных методов. По умолчанию
публикации нет; `--publish` включает конечную проверку и запись.
Модель подключается к оставшимся неоднозначным участкам после проверки входов,
типов и сборки. `llm_loop.py` также изолирует попытки через Stage.

### Модельный конвейер

Один процесс ведёт один TU; внутри него `--jobs` ограничивает параллельные
запросы к модели. Она получает готовый пакет и **не имеет инструментов**:
не запускает Ghidra, компилятор или игру и не редактирует checkout.
По умолчанию используется только бесплатная `opencode/space-bunny-free`;
платная цепочка включается исключительно явным `--models`.
Лимита шагов у кодовой модели нет. Бюджет пакета по умолчанию — 131072 символа,
для более крупного ASM/заголовка он регулируется `--max-prompt-chars`;
обязательные входы не обрезаются молча.
Автосбор использует один индекс текущего снимка TU: по тому же ASM он добавляет
полные заголовки прямых игровых вызовов, объявления используемых данных,
безопасные локальные типы TU и read-only байты ELF. Неизвестное представление
показывается как явно помеченный hex-prefix, а не угаданный тип или строка.
Отсутствующие объявления блокируют запрос до модели. Пакеты повторно используются
в раундах; обязательный код и feedback при исправлении не обрезаются.

```sh
# Подготовка и диагностика: без публикации, DIFF остаются в ignored попытке.
python3 tools/decomp/llm_loop.py inventorymenu.cpp --jobs 16 --limit 16 --no-autotest

# Точный срез: адрес или mangled-имя, флаг повторяется.
python3 tools/decomp/llm_loop.py inventorymenu.cpp --address 0xb457a0 --address 0xb457c0 --address 0xb457e0 --jobs 3 --no-autotest --prepare-only

# Продолжение того же снимка: повторить параметры выбора и добавить --attempt.
python3 tools/decomp/llm_loop.py inventorymenu.cpp --address 0xb457a0 --address 0xb457c0 --address 0xb457e0 --jobs 3 --no-autotest --attempt build-decomp/attempts/tu-ИМЯ
```

Настройки и входы возобновляемой попытки должны совпадать. Изменённый исходник,
тулчейн/пакет или другой checkout требует новой попытки. Артефакты, prompts,
checkpoint и причины отказов лежат в `build-decomp/attempts/`; успешная
диагностика не равна публикации. Для записи добавить `--publish`: тогда один
конечный снимок проверяется по всем TU и полному headless-набору. Прежние
определения не заменяются, лишние определения и непроверенные ABI-варианты
не проходят шлюз. `--no-autotest` — быстрый MATCH-only режим; неподдержанные
DIFF требуют исследования или дифференциальной оснастки, а не заглушек.

Для субагентов (включая GPT-6 Luna) `--prepare-only` обязателен перед написанием
кода. Для передачи пакета одним вызовом добавьте `--json`:

```sh
OTL_OWNER=opencode python3 tools/decomp/llm_loop.py inventorymenu.cpp --address 0xb457a0 --address 0xb457c0 --prepare-only --json
```

В stdout будет один JSON с `result_path` и сохранённым `external_handoff`,
журнал подготовки уйдёт в stderr. Повторно собирать пути и хеши вручную не нужно.
Код завершения не заменяет проверку `external_handoff.status` и `blockers`:
заблокированная подготовка тоже выдаёт JSON. Флаг доступен только с
`--prepare-only`, публикация с ним запрещена.

Без этого флага субагент получает файлы из строки `isolated attempt:`: сначала читает
`build-decomp/llm-loop/<TU>/result.json`, проверяет отсутствие блокировок каждого
назначенного адреса и наличие `prompts/<address>.md`, затем работает над своим
кандидатом полного TU. Это использование подготовки без OpenCode-запросов;
модель субагента выбирается при его запуске, а `--models` для такой подготовки
не переключает её. Чужие исходники и общие заголовки остаются вне его владения.
`result.json.external_handoff` описывает сдачу внешнего агента (например,
самостоятельно запущенного OpenCode): `status: ready` означает только готовность
пакета, не приёмку кода или разрешение на gate. При `blocked`/`unprepared`
`cycle_argv_template` отсутствует (null); причины находятся в `blockers`.
`targets` содержит точные пути и SHA256 пакетов, `prepared_checkpoint_sha256`
и `stage_metadata_sha256` закрепляют подготовку. В `submission` записаны путь
полного TU и его hash/exists **до редактирования**; существующие определения
надо сохранить. Отсутствующий исходник разрешено создать в указанном месте.
Правило «одно определение в C++ block» внутри prompt относится к встроенному
модельному transport; внешний агент сдаёт полный TU в `submission.source`.
Fixtures кладутся в указанную папку, а содержательный cycle spec агент задаёт
сам: тесты и отрицательные контроли не придумываются подготовителем.

В `cycle_argv_template` замените отдельный аргумент `{cycle_spec_path}` абсолютным
путём к этому spec и запустите argv из `cwd` с согласованным `OTL_OWNER`.
Не добавляйте `--input`: цикл читает уже записанный исходник prepared Stage.
Команда не включает gate/release и не запускает внешнюю модель. Хеши handoff
не являются `identity_sha256` цикла: он вычислит и проверит собственную identity
после сдачи кандидата. Смена заголовков/tools требует новой подготовки; после
редактирования TU не возобновляйте `llm_loop --attempt`, используйте cycle.

Для крупной пачки сначала завершите общие заголовки и инструменты, затем
готовьте пакеты одного снимка. Обнаруженный новый ABI требует отдельной правки
и свежей подготовки затронутых пакетов. Результат передавайте путями и хешами
из handoff, журналы открывайте при отказе. Адресные проверки выполняйте по
затронутым TU; единую полную приёмку запускайте после окончательной интеграции
и до коммита. Одно-TU cycle не требует отдельного полного прогона для каждого
TU общей пачки; финальный canonical gate остаётся обязательным.

Для исправления **уже определённого, но непринятого** тела есть отдельный явный
режим того же подготовителя:

```sh
python3 tools/decomp/llm_loop.py QuestRequirements.cpp --prepare-only --repair-address 0xdfe5d0
```

`--repair-address` повторяемый; не смешивается с обычным `--address`, модельным
запуском или `--publish`. Отсутствующие определения по-прежнему готовятся обычным
способом. Repair требует сильную DIFF-definition своего TU в свежем сравнении и
полный совместимый canonical progress с тем же digest всего объекта TU, что и
свежее сравнение; устаревший объект progress блокирует подготовку. MATCH, accepted и прежние behavioral
receipts (даже устаревшие), включая body/ctor/dtor aliases, запрещают такой repair.
Две строки исходных C1/C2 или D1/D2 допускаются как одно тело, только если
имена образуют точную пару оригинальных ABI aliases, а статус DIFF, размер,
нормализованный код, digest объекта и прочие поля сравнения совпадают.
Это не разрешает ремонт принятого alias или отдельного D0.
Единственное исключение внутри closure — отдельно выпущенный non-virtual
adjustment thunk: он должен оставаться сильным MATCH с тем же нормализованным
кодом в canonical progress, свежем baseline и окончательном сравнении cycle.
Тело при этом остаётся непринятым до собственного MATCH или парного теста;
пропуск или изменение защищённого thunk отклоняет кандидата.
Отсутствующий/повреждённый progress не означает отсутствие защиты.

Исходный TU не удаляется и не переписывается ради подготовки. В handoff target
имеет `kind: repair_existing_unaccepted`; checkpoint сохраняет исходный полный TU,
его hash, baseline comparison и hash полного progress. Внешний агент заменяет
только назначенные тела, сохраняя остальной TU побайтно, включая сигнатуры,
includes и соседние определения. Тело связывается с точной сигнатурой; неоднозначные
или неподдерживаемые сложные declarators блокируются. Заголовки и нужные includes подготовьте **до**
пакета; после него расширения прав на контекст нет. Семантические fixtures/spec
остаются явным входом внешнего агента. Используется обычный `candidate --cycle-spec`.

При prepare-resume и входе в Cycle сверяются исходная база, protection snapshot и
live/Stage progress; изменение требует новой подготовки. После редактирования
кандидата используйте Cycle, а не prepare-resume. Режим не выдаёт acceptance и не
восстанавливает saved validation: изменённому DIFF всё ещё нужны новые проверки
и неизменённый canonical gate. Обычная подготовка existing definitions сохраняет
прежнее поведение.

Главный агент собирает результаты и проверяет их через `candidate.py`/Stage.
При DIFF требуется сравнение именно нового адреса: общий PASS старых тестов
не является его приёмкой. Старые попытки другого снимка не возобновляются.
В Stage свежесть Ghidra проверяется по её собственным types/receipt и выбранным
адресам без переписывания живого `types.json`. Неподтверждённый raw не попадает
в prompt; при отсутствии свежего COMPLETE остаются ASM и заголовки.
`types.json` привязан к заголовкам, SDK, закреплённому компилятору, ELF,
настройкам и MATCH-входам доверенных прототипов. Stage сохраняет эти MATCH-входы;
изменение диагностического процента DIFF само по себе не меняет их. Реальный
режим поиска generated-заголовков входит в отпечаток: включённый fallback
может перекрыть SDK-заголовок и не считается эквивалентным выключенному.

Экспорт типов включает библиотечные/private классы, достижимые по полям-значениям
и базам восстановленных классов. Их размеры и смещения берутся из DWARF GCC
4.4.7; зависимости заполняются раньше владельцев. Шаблоны сохраняют точные
datatype-имена отдельно от namespace символов Ghidra. Неизвестные смещения,
bitfields и конфликтные/циклические value-layout блокируют типизированный
экспорт, а не заменяются придуманным контейнером.

Пределы локальных тяжёлых процессов общие для всех worktree на машине:
по умолчанию максимум **два компилятора и два headless-процесса** (на
одноядерной машине — один). При необходимости настроить до запуска workers:

```sh
python3 tools/decomp/resource_slots.py compiler 2
python3 tools/decomp/resource_slots.py selftest 1
```

Настройка активного пула запрещена; остановка процесса автоматически
освобождает слот. Лимиты хранятся под `OTL_DECOMP_CACHE`; workers должны
использовать один кэш. `OTL_JOBS` управляет потоками подготовки сборки,
не снимая общего лимита. Для отдельных фаз доступны `OTL_COMPARE_JOBS`
(сравнение и проверка кандидата), `OTL_BUILD_JOBS` (hybrid/standalone-сборка)
и `OTL_SELFTEST_JOBS` (headless-самотест). Если переменная не задана или пуста,
фаза использует прежний `OTL_JOBS`; значение должно быть положительным целым.
Эти настройки также не расширяют общий пул `resource_slots`. Результаты
возвращаются в прежнем порядке, ошибки не скрываются. Число удалённых модельных запросов можно увеличивать
отдельно, с учётом квот провайдера; производительность десятков агентов пока
не измерена. Для долгих полных проверок этой машины использовался
`OTL_SELFTEST_TIMEOUT=1800`.

Для адресной проверки собирай все production TU, но только нужные фикстуры и
общий AutoTestRuntime. Отдельный ignored-каталог сохраняет полную сборку:

```sh
python3 -B - <<'PY'
import sys
from pathlib import Path
sys.path.insert(0, 'tools/decomp')
import autotest, hybrid
fixtures = [hybrid.HYBRID / 'tests' / 'TimelineControlsTest.cpp']
runtime = autotest.write_runtime(hybrid.OUT / 'autotests')
blob, loader = hybrid.build(out=Path('build-decomp/focused').resolve(),
                            tests=fixtures + [runtime])
code, report = hybrid.selftest(blob, loader, shards=1)
print('\n'.join(report))
sys.exit(code)
PY
```

Замени список фикстур своим срезом. Это сокращает подготовку адресного прогона;
перед коммитом по-прежнему нужен полный `python3 tools/decomp/check.py`.
Production TU используют тот же ключ backend-кэша, что и objdiff; путь заголовков
фикстур добавляется только при их компиляции. Свежее препроцессирование и
проверка зависимостей сохраняются.

Stage используют общий кэш backend-компиляции полного свежего preprocessed input
со стабильным путём и проверенными зависимостями. Неподдерживаемые режимы
остаются на исходном маршруте сборки; произвольные абсолютные пути из ключей
не удаляются.

## Приёмка

1. **MATCH** — совпадение нормализованного объекта с оригиналом, включая
   релокации, полные ключи литералов, таблицы переходов и поддерживаемые
   EH-метаданные. Неподтверждённые границы/цели таблиц и неподдерживаемая LSDA
   блокируют этот путь.
2. **Дифференциальный самотест** — оригинал и восстановленная функция
   исполняются на одинаковых входах, покрывающих её ветви; сравнения полны.
3. **DIFF n%** — диагностическая близость инструкций, не приёмка.

`TL_ORIGINAL` только объявляет адрес для навигации. Общий PASS оснастки не
принимает все перечисленные в ней функции. Для учёта DIFF `check.py`
требует успешное исполнение конкретной оснастки и её отчёт `coverage` для
конкретного адреса: минимум 20 завершённых сравнений, ноль `different`
и `incomplete`. Старые ручные оснастки без такого отчёта продолжают работать
как регрессии, но их объявления не повышают счётчик принятого исходника.
`AutoTest::invoke` регистрирует фактический вызов каждой стороны, loader проверяет
пару по hooks, а `Coverage` считает реальные исходы. Первый ручной адаптер —
`CWarper::activate`: 146 сравнений в оригинальном процессе. Пустой тест,
чужая функция, вызов оригинала с обеих сторон и неполнота не дают приёмку.

Сгенерированный тест не заменяет проверку ветвей. Для сильного мутационного
результата нужны минимум три валидных мутанта двух категорий и не менее 80%
изолированно подтверждённых убийств. Несобирающиеся и идентичные исходному
объекту мутанты не учитываются. Неполнота, переполнение наблюдателя, timeout
и одинаковые падения обеих сторон не считаются равенством или убийством.

Принятые автоматические результаты связаны с версией evidence и отпечатками
объекта, ELF, библиотек, тулчейна, типов, исходников/заголовков, оснастки и
параметров запуска. Старый результат нельзя присвоить изменённым входам.
`autotest.py` и `mutate.py` используются для выбранных функций; ограничения
наблюдателя нужно учитывать при подготовке оснастки.

После пары естественных правок формы исходника продолжать через сравнение
поведения. Новые текстовые контракты, стадии и реестры на каждую функцию
не требуются.

## Проверка и границы гибрида

```sh
python3 tools/decomp/objdiff.py decomp/src/AIFlag.cpp
python3 tools/decomp/check.py
```

Перед коммитом обязателен полный `check.py`: сборка, сравнение и самотест.
Внутри пачки выполняются адресные сравнения и focused-самотесты; полная
приёмка запускается один раз после объединения пачки и фиксации её входов.
Размер пачки сам по себе не заменяет этот завершающий проход.

Для массового исследования уже написанных игровых DIFF без приёмки:

```sh
python3 tools/decomp/bulk_autotest.py --out build-decomp/bulk-probe-001 --run
```

Команда собирает доступные автоматические оснастки в один гибрид со всеми
production TU, сохраняет ошибки генерации/компиляции и результаты по адресам.
Каждый запуск требует новой пустой ignored-папки. Код возврата 0 означает
завершённую диагностику; расхождения остаются в `report.json`. `PASSED_PROBE`
тоже требует проверки законности входов, времени жизни объектов и ветвей:
случайный объект с пустой картой не проверяет поиск существующего элемента.
Команда не изменяет реестр приёмки и не заменяет завершающий `check.py`.
Она проверяет неизменность полных входов и отдельно созданных оснасток.

Планировщик самотеста сохраняет длительности как подсказки порядка запуска.
При добавлении или изменении fixture он переиспользует оценки неизменившихся
объектов по SHA и реальным ELF-регистрациям. Общий runtime и тестовые объекты
без регистраций входят в общий ключ; новые тесты получают медианную оценку.
При отсутствии пригодных оценок действует порядок индексов. В любом случае
все части запускаются заново, а состав, modulo-распределение и полнота отчётов
проверяются прежними правилами. Профили не содержат результатов приёмки.

Служебные проверки не считают дорогой процент похожести DIFF: это не критерий
приёмки. Для диагностики он доступен через `check.py --scores` или `objdiff.py`.
Проверка опубликованных путей сравнивает полные байты объектов с уже проверенным
снимком, включая данные/EH/relocations, без повторного анализа каждой функции.
Поиск EH использует индекс неизменяемых диапазонов, сохраняющий консервативные
отказы по пересечениям. Обработка ASM пропускает заведомо неподходящие строки
перед regex; это уменьшает CPU-расход, а не ослабляет сравнения.
Самотест работает без дисплея и звука, завершая игру до `main`. Пустой выбор
тестов, аварийный процесс и неполный отчёт дают отказ. GUI, клики и скриншоты
запускаются только по явной просьбе пользователя через `hybrid.py run`.

Многие ошибки восстановления будут выявляться именно при попытке живого запуска
и дальнейшем прохождении игры. Отдельные самотесты проверяют выбранные входы, но
не исчерпывают ABI, раскладки данных, время жизни объектов и взаимодействие разных
TU на настоящих ресурсах и игровом состоянии. Поэтому даже полный PASS `check.py`
не означает, что гибрид уже играбелен. Обнаруженный живым запуском сбой — вход
для следующей правки: причину сверяем с оригинальным кодом, исправление закрепляем
MATCH или адресным сравнительным регрессионным тестом. Сам факт запуска игры не
заменяет приёмку функций и не отменяет требование явного разрешения на GUI.

Гибрид выполняется в оригинальном процессе. Его функции, данные, RTTI,
vtable и библиотечные зависимости могут оставаться оригинальными.
Прошедший гибрид не доказывает самостоятельную сборку восстановленной игры.
`standalone.py` проверяет обычную линковку без redirects и заглушек;
даже замкнутый link-only срез не доказывает работоспособную отдельную игру.

Для некоторых UI-тестов уже есть
[HeadlessGui.h](hybrid/HeadlessGui.h) с настоящими CEGUI/OGRE и null renderer.
Он не сравнивает GPU/пиксели и не является общим тестом всех UI-функций.

Тип возврата и static проверяются по ASM и вызывающим: mangled-имя их
не кодирует. Generated headers, совпавшие sizeof/offset и trial MATCH не
доказывают корректность всех типов, ABI и конечного объекта. Неподдерживаемые
secondary this-adjustments, aggregate ABI и lifetime-преобразования требуют
отдельного доказательства; опасная автоматическая очистка выключена.
Для скрытого указателя возврата конвертер требует точную ELF family и доверенный
прототип по адресу. Raw C не хранит цель перегруженного вызова: неоднозначные
вызовы остаются целиком без преобразования.

### Продолжение подготовленной попытки без вызовов модели

`candidate.py --cycle-spec spec.json --attempt <Stage>` продолжает **существующую**
попытку `llm_loop.py --prepare-only` после подготовки кода и самотестов. Это адаптер
над `objdiff`, `hybrid` и неизменённым `Stage.validate`, не новый способ приёмки.
Заголовки и контекст надо подготовить до пакета; после пакета допустимы изменения
назначенного TU и файлов тестов. Владелец TU проверяется через `OTL_OWNER`.

Минимальная спецификация (пути тестов относительно `decomp/hybrid/tests`):

```json
{
  "schema": 1,
  "tu": "Example.cpp",
  "addresses": ["0x123456"],
  "focused": ["ExampleCompare.cpp"],
  "regression": ["ExampleCompare.cpp", "ExampleRegression.cpp"],
  "controls": [{
    "name": "changed-boundary",
    "old": "value > 19", "new": "value >= 19", "count": 1,
    "test": "example_compare", "address": "0x123456"
  }]
}
```

Спецификация не содержит команд, Python-кода или внешних провайдеров. Контроль
заменяет точно указанное число вхождений только в своём TU. Его успех требует
полного результата загрузчика, завершённого сравнения original/candidate с
`different > 0`, `incomplete == 0`, и отказа именно заданного теста. Падение,
таймаут, ошибка сборки или отсутствие сравнения не считаются пойманным мутантом.
Исходник восстанавливается в `finally`; журнал позволяет восстановить его после
аварийного завершения, но не перезаписывает постороннее изменение.

```sh
OTL_OWNER=dot python3 tools/decomp/candidate.py Example.cpp \
  --attempt build-decomp/attempts/tu-EXAMPLE --cycle-spec spec.json
```

Последовательно выполняются сравнение, focused, отрицательные контроли и
регрессия; первая ошибка останавливает цикл. Повтор той же команды пропускает
только успешные фазы с неизменными исходниками, пакетами, контекстом и целыми
артефактами. Ошибочная или прерванная фаза не перезапускается автоматически.
`READY_FOR_GATE` разрешает планировщику отдельно выделить ресурс для единственного
полного прохода. Настройки compiler/selftest pools и порядок тестов не меняются.

```sh
OTL_OWNER=dot python3 tools/decomp/candidate.py Example.cpp \
  --attempt build-decomp/attempts/tu-EXAMPLE --cycle-spec spec.json \
  --gate --release-request /absolute/path/to/release.json
```

После `Stage.validate()` процесс остаётся в `AWAITING_RELEASE`, сохраняя тот же
живой `Stage`. Разрешение существующего процесса публикации передаётся атомарно
записанным JSON с `action: "publish"`, точным `identity_sha256` из checkpoint и
`inputs_digest` из `gate.json`. Отмена: `action: "cancel"` и тот же
`identity_sha256`. Не оставляйте файл разрешения от другой попытки. Это локальная
публикация через `Stage.publish()`, не remote push, PR, merge или обход отмены.

`build-decomp/candidate-cycle/checkpoint.json` и соседние отчёты являются
восстанавливаемым журналом работы, а не реестром принятых функций. Там сохранены
хеши входов и отчётов, время фаз, существующие compiler/cache counters и доступные
build/selftest timings. Stage переиспользуется без копирования. Ошибка записи
после успешного gate сохраняет живой объект в `RECEIPT_ERROR`: повторяется лишь
сохранение отчёта, никогда сборка/самотест. Некорректное разрешение не уничтожает
живую проверку. После выхода процесса checkpoint gate даёт
`REVALIDATION_REQUIRED`; он не восстанавливает `validated` из JSON. Решение о новой
проверке принимается явно, с новой подготовленной попыткой, а не повтором «до зелёного».

Проверка самого адаптера без игры и компилятора:
`python3 -m unittest discover -s tools/decomp -p test_candidate_cycle.py`.

Контракт модели: вход — уже подготовленные `result.json`, `checkpoint.json` и
`prompts/<address>.md`; выход — полный кандидат TU, сравнительные fixture-файлы
и указанная выше спецификация. После этого достаточно одной команды с `--gate`
и разрешённым планировщиком ресурсом. Известные фазы не требуют отдельных решений
модели. JSON-результат содержит остановившуюся фазу, сохранённый хеш входов, пути
пакета, исходника, checkpoint, точных диагностических артефактов и diff кандидата.
Начальный отказ admission также выдаёт JSON. Seed/minimized case не выдумываются:
автоматического минимизатора нет; его отсутствие указано явно. Подробности входа
и сравнения, если они есть, остаются в тестовом логе.

Существующий пакет уже включает ASM, полные заголовки владельца и прямых
зависимостей, доступный Ghidra-черновик, ссылки на данные/литералы, ограничения ABI,
идиомы и доступные примеры. Произвольные исторические исследования автоматически
не собираются. Выбор семантических ветвей, конструкция сравнительных тестов и
мутаций, а также разбор нового отказа остаются работой модели. Успешная запись
ранее заблокированного gate receipt выдаёт обновлённый JSON. Ошибка самой
публикации — отдельный `PUBLICATION_FAILED`: живой Stage удерживается, но ни
публикация, ни gate автоматически не повторяются; точная отмена завершает ожидание.
При исключении из `Stage.publish()` итог может быть неизвестен (например, сбой
очистки уже завершённого журнала): `published: null` требует проверки существующего
publication journal и живого дерева. Автоматического повторного publish нет.
