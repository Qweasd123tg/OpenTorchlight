# Следующие патчи после large-16

> Исторический план large-16, не текущая очередь. Действуют
> [code-first](research/code-first.md) и [UI scope](research/ui-contour.json);
> состояние этого среза не измеряет полное восстановление функций.

Рабочая база — large-16, OTC v6. Перед следующей правкой повторить текущие тесты.
Не накладывать старые large-14/15 UI-пакеты поверх этого архива. Настоящие pak,
ELF и библиотеки уже имеются как внешние read-only входы; запрашивать их заново
для перечисленной работы не требуется.

## 1. Завершать доставку атаки, не рисовать «магический выстрел»

Прямой многоканальный HIT и защита уже подключены; исследование:
`research/large-16-typed-damage.md`. Он не может служить заменой MISSILE/SKILLS.
Следующая независимая граница — `CMissile::initialize @0xd00650`,
`updatePositionByVelocity @0xd02720`, `checkCollision @0xd038a0` и callers
`fireMissiles`/`doWeaponSkill` в цепочке атаки.

Сначала зафиксировать начальную позицию/скорость, lifetime, RNG/разброс и порядок
обновления/столкновения по ресурсам и ASM. Native-проверка отдельной homing-формулы
не закрывает запуск, swept collision или взрыв. Не выбирать скорость и радиус
по виду. Затем сценарий: исходная атака/анимация → появление нужного числа
снарядов → движение → препятствие/жертва → типизированное попадание → смерть/XP.
Проверить собственную цель/хозяина, просроченный снаряд, повторное столкновение и
переход/сохранение. Ember Bolt не переименовывать в огненный одиночный instant hit:
его данные требуют исходных poison/MAGIC, числа снарядов и knockback.

## 2. Требования и настоящие ограничения инвентаря

Они **не реализованы этим проходом**. Ниже проверенные символы исходного ELF,
а не готовая формула для вставки:

| Функция | Адрес |
|---|---|
| `CEquipment::setRequirements()` | `0x880030` |
| `getLevelRequirement(CCharacter*)` | `0x86ddc0` |
| `getStrengthRequirement(CCharacter*)` | `0x86dc50` |
| `getDexterityRequirement(CCharacter*)` | `0x86dae0` |
| `getMagicRequirement(CCharacter*)` | `0x86d970` |
| `getDefenseRequirement(CCharacter*)` | `0x86d800` |
| `CEquipment::canEquip(CCharacter*,bool)` | `0x86f150` |
| `CInventory::canEquip(CEquipment*,bool)` | `0x91bdc0` |
| `canEquipIntoSpecificLocation(CEquipment*,EEQUIP_LOCATIONS,bool)` | `0x91bd10` |
| `CInventory::addSection(EINVENTORY_PANES,unsigned)` | `0x9243b0` |

Исполнять цепочку целиком: исходные графы/процентные значения → округление →
heirloom → снижение требований → фактическая проверка класса/слота/атрибутов.
Не трактовать `STR_REQUIRED=100` как готовое требование STR=100 без исходного
графа и getter. Сохранённый DTO не должен обходить ту же проверку. Вместимость
берётся из исходных панелей/секций, не из числа клеток «по памяти» и не из
защитного лимита 4096 объектов в декодере.

Минимальный проверяемый результат: ниже границы нельзя надеть; ровно на границе
можно; отказ не теряет вещь/старую экипировку/HP; предмет не проверяет себя
собственными ещё не применёнными бонусами, если оригинал их исключает; swap рук,
щит/двуручность и загрузка воспроизводят исходные правила. Перед изменением
контролов исправить эту общую модель, иначе магазин/питомец продолжат использовать
неверный инвентарь.

## 3. Довести общий UI-механизм прежде отдельных новых окон

Предыдущий аудит остаётся действующим: `CGameUI::convertToScreenScale @0xa83ed0`,
жизненный цикл rescaleUI, правила сторон/модальности/паузы, динамическое дерево
HUD. HUD-команды в исследованной цепочке уже срабатывают на MouseButtonDown.
Не возвращать ошибочное release-поведение и не переносить down автоматически
на все остальные меню без их собственных подписок.

Для инвентаря переносить связку `inventory.mesh` + `inventorymenu.layout` +
`CInventoryMenu`, опорные `tag_topinventory/tag_bottominventory`, OPEN/CLOSE и
связанные движущиеся hit regions. Рамка вокруг PORT-списка не является переносом.
Контроль: original CEGUI/контроллер → вычисленные окна/draw commands → кадр,
несколько разрешений и открытие/закрытие. Отдельный стенд исходной CEGUI пока
не создан; собственный screenshot-регрессионный тест не заменяет его.

## 4. Затем услуги, питомец и маршрут кампании

Сначала закрыть зависимости предметов/эффектов/условий. После этого — нормальная
выдача/цели/награды квестов, NPC-диалоги, конечные товары/продажа/выкуп, услуги,
pet inventory/AI/торговля и исходные переходы. Сохранять отдельные статусы:
данные прочитаны, поведение подтверждено, подключено, сохраняется, сравнено.
Числа записей каталога не считать готовыми квестами или вещами.

## Формат следующего результата

Один патч на одну проверяемую границу; точный донор, исходные функции/адреса,
проверка оригиналом, ресурсная интеграция и отрицательные случаи. Сначала добавить
контрпример старой версии, затем исправление. Не держать старый неверный тест
ради зелёного отчёта и не заменять его на более слабый без объяснения. В каждом
пакете фиксировать остающиеся неподдержанные ветви и совместимость OTC.
