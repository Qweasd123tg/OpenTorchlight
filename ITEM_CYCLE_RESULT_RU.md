# OpenTorchlight — связанный этап предметов

## База и результат

Вход: `OpenTorchlight-gpt-pro-large-2.zip`, SHA-256
`8b86ba42587940cf521207dbd3db212f0625a9368f63f8752a85a950763b26d4`.
Прочитаны правила и крупное задание `GPT_PRO_LARGE_TASK.md`; узкий следующий
патч AI заменён заданным циклом предметов. Все изменения локальные, в GitHub
не отправлялись. Готовый ZIP уже содержит применённые изменения; `.patch`
предназначен для чистой распаковки именно указанного входа.

**Реализован и исполняемыми тестами проверен core-цикл:** обычная смерть →
таблица добычи → предмет в мире и загрузка его модели → подбор в сумку →
выбор/снятие/замена экипировки → изменение существующих боевых характеристик →
сохранение вещей, снаряжения и здоровья между этажами. Этот цикл подключён к
настоящему `linux_desktop_main.cpp`, а не только к тестовому приложению.
В среде внешнего автора оконный запуск этой версии не выполнялся; граница его
проверок приведена ниже.

После локального слияния на машине с игрой `torchlight_desktop` полностью собран,
`original_item_cycle` прошёл на настоящем `pak.zip`, а общий результат составил 48/48.
GLES smoke и рендер исходной сцены также прошли. Ручной игровой сценарий с панелью ещё не выполнялся.
Оконный executable отдельно загрузил Main:1 и успешно отрисовал три кадра на исходных ресурсах.

## Что изменено

### Добыча и её жизненный цикл

Новый `TreasureProfile` загружается из первой `TREASURE`-группы после обработки
`BASEFILE`. Поддержаны `SPAWNCLASS`, `MIN/MAX` со значениями по умолчанию 1,
ветка стандартной `BARREL_TREASURE`, вложенные spawnclass, конкретные UNIT и
UNITTYPE через существующий level-aware индекс. Проценты выпадения или новый
заменяющий граф не придуманы. Отсутствующие классы/ресурсы учитываются в
диагностических счётчиках, а не заменяются произвольными вещами.

Обычная смерть создаёт один запрос. Он разворачивается в безопасной фазе
`RuntimeEntityWorld::resolve_death_loot`, чтобы рост вектора мира не инвалидировал
указатели в боевом обработчике. Повторные kill, damage трупу и повторный drain
не дублируют вещи. `Hide/Destroy Spawned Units` не считаются смертью и не создают
добычу. Выпавшая вещь имеет `loot_source_id`, но не становится ребёнком
спавнера умершего: скрытие/уничтожение того спавнера её не удаляет.

Положение берётся у погибшего, mesh — из существующего ресурсного пути UNIT.
Для простых предметов это подтверждённый путь; полёт, разброс, физика, деньги
и специальное позиционирование остальных типов здесь не восстановлены.

### Экземпляры, сумка и слоты

`PlayerInventory` хранит уже созданные `WeaponItem`/`ArmorItem` вместе с именем,
GUID ресурса, типом, моделью и собственным ID экземпляра. Две вещи одного GUID
остаются двумя независимыми объектами. Подбор сначала сохраняет экземпляр,
затем убирает его world-представление; повторный подбор отклоняется.

`CREATEAS` читается из загруженного UNIT с наследованием, не только из
необязательных метаданных master. Предметы, для которых нет поддержанного
слота/эффекта, остаются в сумке как доступные для просмотра. Не реализованное
золото не поглощается сумкой и не мешает выбрать лежащую в той же точке
экипировку. Подбор **не надевает** предмет автоматически.

Поддержаны один оружейный слот и семь существовавших слотов брони. Замена
оставляет прежнюю вещь в сумке; повторное надевание не складывает броню второй
раз и не делает новый случайный бросок. Учтён конфликт щита и двуручного
оружия через исходный ID типа 10. Dual wield, второй комплект и оригинальная
вместимость/стэки не заявляются восстановленными.

### Характеристики и переходы

`PlayerSession` владеет инвентарём и изменяемым состоянием персонажа вне цикла
загрузки этажей. Новое оружие меняет сохранённый диапазон урона, существующую
формулу скорости клипа и дальности. Броня заменяет свой слот в существующем
расчёте защиты. Снятие оружия возвращает прежнюю безоружную базу.

На переходе очищаются локальная цель и активное исполнение атаки, но не HP,
максимум HP, вещи, слоты, их числовые броски и генератор боевой случайности.
Это состояние текущего процесса; **сохранений на диск нет**. Состояние самого
этажа и оставленная на нём добыча также пока не сохраняются для возврата.

### Минимальный интерфейс desktop

`I` открывает панель инвентаря; стрелки вверх/вниз выбирают вещь; `Enter`
надевает; `U` снимает; `I`/`Escape` закрывают панель. Вне панели Escape закрывает
окно. Панель показывает имя, instance ID, состояние BAG/ON, слот, сохранённые
характеристики и причину отказа. Английский ASCII bitmap-интерфейс и его
геометрия — самостоятельный прототип, не копирование Torchlight GUI.

Пока панель открыта, симуляция приостановлена. Активную атаку нужно завершить
перед сменой снаряжения; иначе показан отказ, а не замена урона уже начатого
HIT. При выборе другого оружия перезагружаются соответствующие имеющемуся
resolver клипы и меняется модель в руке. При отсутствии модели/клипов операция
отклоняется без потери предмета. Повторные замены используют кеш mesh-инстансов
на этаже. Внешний вид брони, полный selectAttack и ranged/projectile бой
этим этапом не восстановлены.

## Наблюдаемая разница

Один и тот же синтетический архив использован старым пробником, собранным из
входного проекта, и новым пробником после безопасной фазы:

```text
До:    killed=1 new_world_entities=0
После: resolved_deaths=1 killed=1 new_world_entities=6
```

Это собственная фикстура, не данные/исполнение оригинальной игры. В ней
проверяется шесть предметов из вложенной таблицы, их реальные треугольные
mesh, последующий перенос в сумку и замены. Максимальный урон оружия меняется
20 → 40, скорость проигрывания 2,0 → 0,5, дальность 2,7 → 4,7. При natural armor
3 и ремне 5 замена нагрудника 10 → 30 меняет итоговую броню 18 → 38, а не
суммирует оба нагрудника. Смена этажа эти значения и потерянное HP не сбрасывает.

## Основания и статус доказательств

Исследуется ранее закреплённый Linux ELF с заявленным SHA-256
`91b41ae9dfea30aab6bc14dbbfcceaee096d600f39635b8507f5a88b5d41724b`.
Сам бинарник здесь отсутствует, его хеш не вычислялся заново. Адресные
`research/disassembly/item-cycle-*.asm` — небольшие неизменённые выборки из
ранее предоставленного пользователем текстового дампа архива `(2)`.
Полный дамп и оригинальные ресурсы не включены.

| Основание | Подтверждённая граница |
|---|---|
| `CCharacter::unitInit @0x8529a0` | TREASURE pointer, MIN/MAX, defaults |
| `CDataGroup::GetDataGroupByName @0xc61d30` | Возвращается первая одноимённая группа |
| `CCharacter::die @0x838ed0` | Своя таблица либо стандартная добыча; исходные ограничения выдачи |
| `CLevel::rollTreasure @0x95d0b0` | Один запрос BARREL_TREASURE; отдельный rollMoney |
| `CResourceManager::createUnitsBySpawnClassAtPositionInLevel @0xd79290` | Ранг уровня и путь позиции простого предмета |
| `CInventory::pickupEquipment @0x924bd0`, `unequipEquipment @0x9249b0` | Хранится конкретный экземпляр, а не только GUID; слот отделён от сумки |
| `CInventory::equipEquipmentIntoSpecificLocation @0x9256a0` | Перемещение ссылки, бонусы, конфликт другой руки через ISA(10) |
| `CGameClient::performWarp @0x58d110` | Игрок сохраняется вокруг выгрузки уровня |

Названные структуры вызовов/ветки — `original-code`. Пути и значения из
загружаемого пакета читаются data-driven через прежние парсеры; синтетические
тестовые числа не названы `resource-derived`. Новые ID, owned-value модель и
безопасная очередь — `inferred` инженерная интеграция. Ограничение 4096
роллов/листьев на запрос — защитный предел порта с явной ошибкой, не
восстановленная константа оригинала. UI, пауза и запрет смены в ударе —
`prototype`. Существующая библиотечная обработка mesh/skeleton не переписана.

`desktop_gameplay_syntax` заменяет только оконную обвязку декларацией, проверяя

## Оставшиеся границы

Добыча пока не воспроизводит глобальный RNG-порядок, все условия
alignment/killer, полный ранг этажа, rarity/аффиксы и деньги. Исходный `die`
выдаёт предметы до `broadcastKilled`; новая очередь разворачивается после
логического уведомления. Это явно незакрытый порядок фаз, особенно для
реентрантного death-callback, запускающего spawn/warp.

Флаг runtime `drops_loot` работает, но для layout ещё нужно связать конкретное
имя свойства с `CUnitSpawnerDescriptor::Set_setUnitsGiveLoot @0x65ec30`.
Минимальный запрос: регистрация этого setter в конструкторе
`0x65c410..0x65e3dd`, связанная UTF-32 строка и значение по умолчанию.
Для распределения добычи нужны контекст ранга/RNG в
`CResourceManager::createUnitsBySpawnClass @0xd78ee0` и короткая трасса обычной
смерти; не ещё один полный dump. Требования/эффекты — отдельные
`CInventory::canEquip*`, `verifyEquipment` и `updateBonuses` с конкретными
ресурсами. Item lighting/физика требуют `CLevel::addItem @0x95c970`, а не
распространения Room Piece override на все меши.

Следующая практическая проверка — пройти в окне созданный цикл с двумя оружиями
и двумя предметами одного слота,
затем перейти на этаж и вернуться. Возврат сохранит персонажа, но не обещает
восстановить ещё не реализованное состояние оставленных вещей этажа.

## Применение и повторение

В чистой распаковке входного `OpenTorchlight-gpt-pro-large-2.zip`:

```bash
git apply --check OpenTorchlight-item-cycle.patch
git apply OpenTorchlight-item-cycle.patch
bash tools/check.sh --portable
```

В полном исправленном ZIP патч уже применён; повторно накладывать не нужно.
Проверка с установленной игрой:

```bash
bash tools/check.sh /путь/к/Torchlight/game
# Либо только новый ресурсный тест в уже настроенной сборке:
ctest --test-dir build -R original_item_cycle --output-on-failure -V
```

Независимый повтор ASan/UBSan:

```bash
cmake -S . -B build-item-sanitize -G Ninja \
  -DCMAKE_BUILD_TYPE=Debug -DBUILD_TESTING=ON -DTORCHLIGHT_ORIGINAL= \
  -DCMAKE_CXX_FLAGS='-fsanitize=address,undefined -fno-omit-frame-pointer -fno-pie' \
  -DCMAKE_EXE_LINKER_FLAGS='-fsanitize=address,undefined -no-pie'
cmake --build build-item-sanitize --parallel 4
ASAN_OPTIONS=detect_leaks=1:halt_on_error=1 UBSAN_OPTIONS=halt_on_error=1 \
  ctest --test-dir build-item-sanitize --output-on-failure
```
